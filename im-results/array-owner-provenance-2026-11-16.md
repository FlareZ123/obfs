# Conservative private-owner property renaming through one-slot arrays

**Author:** Agent 5, 2026-11-16. **Status:** Intermediate implementation and bounded reproducibility. Do not promote to `results/` without independent adversarial and performance evidence.

## Motivation and exact admission rule

The existing local and cross-file `proveLocalObject` analyzer follows assignments, known function parameters, identity-return wrappers and read-only consumers. A common private shared-reference pattern escaped the proof:

```js
const owner={secretCount:11,privateDelta:7};
const holder=[owner];
const first=holder[0],second=holder[0];
const output=first.secretCount+second.privateDelta;
```

An array literal normally causes an opaque owner escape because other code might mutate, reflect or export the container. Agent 5 added a **one-slot provable confinement case** in `src/properties.js`:

1. The root object is the already eligible literal private owner; the container is a unique immutable `const holder=[root]`, in the root's exact binding scope. No spreads, holes, second element or unknown initializers are admitted.
2. The holder declaration is not directly exported. An ESM `export const holder=[root]` is a counterexample: another module can observe `holder[0]` and its original field labels.
3. Every read of the holder's identifier within its lexical scope must be exactly the receiver of `holder[0]` with numeric literal index zero and no optional chain. The complete member expression must be the initializer of an ordinary named `const` or `let` binding with a unique declaration. Mutations, opaque calls, exports, dynamic indices, aliasing the holder array, reflection and iteration all conservatively refuse.
4. The resulting value is added to the existing monotonic alias fixed point, and *all* subsequent alias uses are subject to the existing owner no-escape and reflection-proof rules. This includes local function argument and direct field-member uses; private key rewrites use existing one-to-one property mappings.
5. Holder identifier uses are grouped by name before validation to avoid rescanning all program identifiers for each candidate array. The candidate-specific validation cost is linear in its own recorded uses.

This proves a small, auditable ownership trajectory rather than generic collection alias analysis. The proof intentionally declines `holder[variable]`, even when `variable` is provably zero, and a safe direct read `holder[0].secretCount` without a distinct local alias. The conservatism avoids broad assumptions about container mutation and observable property spellings. Nonliteral owners, nested arrays and escaping arrays remain out of scope.

## Attacker interpretation

The local transformation replaces spellings while retaining native executable JavaScript. For COO, any adversary with all distributed bytes can inspect or deobfuscate the source and execute a functional clone; the [existing seedless normalizer](../sims/offline-normalize.js) reconstructs valid code by replacing hashed keys with neutral names without the compiler seed. The new tests explicitly preserve that negative security result. This patch improves correctness and eligible coverage, not a secret-key or remote attestation boundary.

For SCO this proof may rename truly private or public objects depending on where the JS runs; it does not add authentication, source withholding or RPC policy. For SNO a full-filesystem/runtime attacker can instrument the same accessible object values. There is no claim of resistance to dynamic instrumentation, authorization bypass, property-name inference, or LLM-assisted reconstruction.
