# Same-source matched blind affine analysis protocol

**Agent:** 14. **Date:** 22 November 2026. **Status:** intermediate methodology and executable protocol; no blind model observation has been performed. **Security decision:** unchanged, RELEASE-BLOCKED.

## Motivation and pre-registration

The existing `sims/llm-blind-affine-challenge.js` provides an honest one-shot question and private held-out offset verifier for the polyvariant affine backend, but its one-arm design cannot measure any incremental difficulty versus ordinary minification. Earlier public-source GPT-6 probes had no same-source minified arm and were compliance-based blind attempts, as recorded in `im-results/llm-deobfuscation-probe-synthesis-2026-11-22.md`. Agent 8's `communications/agent42/20261122T0228Z_agent8_blind-challenge-method-review.md` specifically requested matched source, model, effort, prompt, and independently committed answers.

The new `sims/llm-matched-affine-challenge.js` implements exactly **two randomized-order ESM artifacts from the same freshly generated hidden source**:

- **Generated:** the current actual COO or SNO `experimentalPolyvariantAffine` pipeline with three positively verified 2-path Int32 arithmetic leaves.
- **Equal-trust control:** ordinary `esbuild.transformSync` with ESM output, Node-compatible ES2022 target and minification enabled, built from the exact original source. Both arms expose the same three public functions and take identical numeric inputs.

The private host samples the ten alternating +/- numeric constants for each of three functions using `crypto.randomInt`. It retains the hidden source, exact additive offsets and a random salted SHA-256 source commitment. The two public questions contain only distributed code, its hash, common source commitment, export names and **identical** answer schema/instructions. Arm order is randomized using `crypto.randomInt(2)`; this prevents deterministic order confounding, although a competent reviewer can often identify the compiler representation from its syntax.

For a future genuine blinded trial, a reviewer should receive one public artifact per isolated, equal-time session and commit each answer without seeing the other arm. The host's current API exposes both questions to the experiment operator and accepts the pair of committed answers through a single `verify` call, which grades each against **3 x 1,024** deterministic unseen Int32 values. The host then calls `reveal` to disclose the private source, salt, offsets and actual arm order, permitting commitment verification.

## Proposed precommitted measurement

Use the **same model family/configuration, prompt, answer format, context/effort allowance, no-tool/no-repository instruction, and time budget** for each arm. Record the exact public bytes/hash, order, all submitted offsets, model metadata, wall-clock duration, tool-use attestations, hidden commitment, 3,072-check arm verdict and any explanation. Evaluate exact offsets and held-out behavior first, then compare success rates and measured effort across enough independently randomized sources. If the two arms receive noticeably different affordances or a reviewer sees both before making its first commitment, record that contamination.

The reviewer must not have separate repository access for a technically isolated trial. Ordinary swarm identities usually have access, so their self-reported no-tools/no-source compliance is **not a technical isolation guarantee**. The source is a narrowly promised Int32 translation family and the question tells the reviewer that form. Successful recovery is functional equivalence for this family only; it does not reconstruct original source syntax, arbitrary JavaScript, digest logic, or client-authority barriers.

## Matched independent source-only reconstruction result

A separate, non-LLM attacker `sims/llm-matched-affine-static-attack.js` parses only delivered code. For actual polyvariant outputs, it reuses the pre-existing seed-independent public-AST interpreter `sims/polyvariant-affine-static-recover.js`; for ordinary esbuild-minified outputs, it first resolves exported function aliases with `sims/polyvariant-app-minified-static-attacker.js`, then symbolically simplifies the independent Acorn AST grammar of `+/-` and explicit Int32 `|0` conversion. It refuses unproved runtime property reads, calls, pre-normalization string additions, multiple parameters, unrelated symbols and non-affine operations. Both source-only lanes use **zero chosen runtime evaluations**, original source, private seed, or compiler internals.

The attack+verifier pair passed in [two-platform workflow 45022512857](https://github.com/FlareZ123/obfs/actions/runs/45022512857), exact source `58a6157aec1a6bddcfa01007ac96426ef1b2cf71`. Each OS generated **eight fresh COO and eight fresh SNO private source programs**. In all 16 programs per OS, both randomized arms yielded exact three-export translations, graded against 3,072 held-out signed Int32 values per arm. Over both OS jobs, that is **32 independent randomly generated source programs**, **64 public code artifacts**, **192 reconstructed public function occurrences**, and **196,608 verified output comparisons with zero mismatches**. This is a conditional bounded grammar result, with *no* blind-model run.

### Soundness boundary of the symbolic-control attack

The minified static interpreter was subsequently tightened to require a terminal `|0` cast and proven prior parameter normalization. It also tracks a conservative absolute-magnitude upper bound across intermediate numeric additions, rejecting forms that might exceed exact JavaScript Number arithmetic, and limits symbolic recursion depth. Negative fixtures reject a final uncoerced expression, unnormalized string-concatenation pathways, bitwise nonzero masks, foreign identifiers, property access, calls, multiplication, and multi-parameter functions. The final source-pinned two-platform run above includes these checks. This preserves the actual numeric/ToInt32 semantics of the admitted translation grammar while allowing a larger hostile input domain than the randomly generated tests alone.

**Finite-observation qualification:** the existing generated-path static interpreter evaluates two representative inputs per emitted switch case to infer an affine offset. A deliberately adversarial non-affine source that coincidentally agrees at those inputs can pass that particular structural/sampling check; the interpreter is a source-only reconstruction attack specialized to the *known compiler-emitted family*, rather than a proof of equivalence for arbitrary JavaScript text. The host's additional 1,024 held-out input comparisons per export, post-grade rebuilt-ESM comparisons, and browser unusual-input checks make the reported instances reproducible and substantially better tested, but finite tests do not establish universal equivalence for every possible non-arithmetic JavaScript program or crafted adversarial input.

For a **black-box-only** attacker that knows the three independent translation functions but cannot read code, one legitimate evaluation of each at zero gives its exact `k`, after which `((input|0)+k)|0` is an offline clone. Three chosen evaluations are sufficient, matching the separate one-query-per-export control. In the worst case, a deterministic exact black-box learner that skips one independent function cannot distinguish two sources differing only in that missing translation offset, so one observation from each export is necessary for guaranteed recovery. This elementary query bound applies to the promised family and a pure black-box oracle; the source-only attacker above succeeds with **zero** oracle evaluations precisely because it has the distributed program text.

Subsequent [Ubuntu+Windows run 45024505268](https://github.com/FlareZ123/obfs/actions/runs/45024505268) additionally rejected asynchronous and generator callable grammars and verified a deterministic well-typed false-offset answer. These stricter rejection checks were added **after** the earlier 45022512857 run and must not be attributed to that earlier commit.

The source-only reconstructed module now also requires **exact, nonduplicated coverage of all three advertised public export names** before emitting ESM. A deliberately incomplete one-export input is refused by the underlying public-function parser, rather than generating a module with invented `undefined` offsets. The new [Ubuntu and Windows run 45025956395](https://github.com/FlareZ123/obfs/actions/runs/45025956395) passed at exact source `66f7b1d6aea50ec1fc8d8bcaaacf027130555a61`, covering the full randomized source-only suite, standalone import checks, uncommon coercion tests, strict JSDoc and the four-way post-init CPU controls. An initial [run 45025846199](https://github.com/FlareZ123/obfs/actions/runs/45025846199) failed only because the new negative fixture expected `TypeError`, while the established parser correctly threw the generic `Error` carrying `Unavailable static function export round2`; the assertion was corrected to require the actual fail-closed diagnostic. This fixes the test contract while preserving and checking the refusal.

### Verified function-object reflection counterexample

A later **separate, full JavaScript observability check** demonstrates that numeric and coercion parity do not imply `Function.prototype.toString` or `.name` parity. On [Ubuntu and Windows run 45023439919](https://github.com/FlareZ123/obfs/actions/runs/45023439919), exact source `ac425b0e19b1f0fb1f016f8d75ff1d000e405e45`, each OS compared the three native exported functions against both public artifact arms in both modes:

| Observed exported-function attribute | COO generated (3) | SNO generated (3) | COO minified (3) | SNO minified (3) |
| --- | ---: | ---: | ---: | ---: |
| Exact `Function.prototype.toString` matches native | 0 | 0 | 0 | 0 |
| Exact `Function.name` matches native | 3 | 3 | 0 | 0 |
| Exact `Function.length` matches native | 3 | 3 | 3 | 3 |

Every count was reproduced on each OS independently, using different cryptographically sampled program source. Both public artifact arms also passed the numeric parity and unusual-input coercion/error tests, while their returned function objects differed visibly under source reflection. Thus a caller executing `f.toString()` can distinguish the obfuscated implementation, and ordinary esbuild also changes source and local function names. The bounded challenge contract explicitly excludes the function-object source/metadata API. A general-purpose **1:1 JavaScript semantic-preservation** claim would need an additional source-observer admission rule or a restricted caller contract; the current matched arithmetic evidence does not satisfy that broader promise.

This externally visible source mismatch is already a known project-wide compatibility pressure point. It is recorded here as an exact limitation of this new same-source challenge, **not** claimed as newly discovered general source-reflection theory or a unique defect against the obfuscator.

### Source-matched repeated-execution CPU tradeoff

The next experiment addresses the distinct **2.5x repeated-compute budget** with `sims/llm-matched-affine-cpu-control.js`. It samples a separate fresh hidden-source three-export program in each mode and each OS run, compiles the actual obfuscated ESM and ordinary esbuild ESM from that single source, commits both three-export answers before revealing the original source, imports all three code variants, validates identical checksums, and warms each function. Thirteen counterbalanced rounds then execute **8,000,000 input-dependent calls per export** for native, generated and minified functions (24 million calls per variant per round). It records CPU and wall milliseconds with full raw samples, hashes, arm identities and source in a per-OS artifact. Startup/JIT costs are excluded in all three arms, so this is a **post-initialization hot-leaf** measurement. For COO it cannot establish a full startup-inclusive budget pass.

Source-pinned two-platform [run 45023836263](https://github.com/FlareZ123/obfs/actions/runs/45023836263) at exact SHA `4cf4d48f8230e07cdda06e87699e223af7f83c3c` passed, with the following observed paired `generated/native` CPU ratios. The interval is the existing `pairedBudgetBound` 95% nominal distribution-free **median-of-paired-ratios** interval (attained confidence 95.3857% under independent stationary rounds), and `supported` means its sample-based upper bound is below the threshold:

| Execution host | Mode | Median generated/native CPU ratio | 95% median interval | Within 2.5x pairs |
| --- | --- | ---: | --- | ---: |
| Ubuntu Node 22 | COO | 1.260x | [1.251, 1.261] | 13/13 |
| Ubuntu Node 22 | SNO | 1.302x | [1.299, 1.304] | 13/13 |
| Windows Node 22 | COO | 1.220x | [1.220, 1.326] | 13/13 |
| Windows Node 22 | SNO | 1.343x | [1.326, 1.496] | 13/13 |

Ordinary same-source esbuild-minified median/native CPU ratios were about 1.0x on both platforms/modes. The Windows `process.cpuUsage()` clock reports coarse intervals; an earlier 1,000,000-call trial [run 45023705232](https://github.com/FlareZ123/obfs/actions/runs/45023705232) failed on Windows when a CPU measurement was reported as zero, despite an approximately 16–32 ms wall-duration sample. The 8,000,000-call trial length mitigated that measurement failure and passed. Windows CPU bounds should still be interpreted with quantization uncertainty, and no OS result is a random sample of all real workloads. Existing whole-app/fresh-process sessions remain necessary for a production release decision.

This is a useful **performance-positive, confidentiality-negative** tradeoff. The backend can run this hot arithmetic family within the sampled post-init CPU threshold, but every public instance in the earlier matched static suite was source-only reconstructed, and all external source-reflection comparisons above differed. Neither CPU result creates a new source secrecy or strong environment-enforcement boundary.

### Independently executable static reconstruction and four-way runtime

The source-only attacker now emits a complete **standalone ESM module**, consisting of the three recovered public exports. After the static answer has been committed to the host verifier, a separate post-grade test actually imports and executes this **reconstructed code**, along with the two published source arms, on 256 deterministic unseen inputs per export per arm. In the new source-pinned [Ubuntu+Windows run 45024144186](https://github.com/FlareZ123/obfs/actions/runs/45024144186), SHA 6a7f24c0a855e21ef7e515c7133b2dcfb77733e8, all 32 randomly sampled source programs passed their original 3,072-case-per-arm private verifier, plus **24,576 rebuilt-ESM vs published-output comparisons per OS**. The reconstructed artifacts, original sources (revealed only after grading), exact source commitments and answer records are preserved in both platform's matched-affine CI archives.

The same source-pinned run incorporated the independently reconstructed ESM as a **fourth** actual executing variant alongside native, ordinary esbuild minification and protected output. The attacker reconstructed the new private source by parsing **only distributed public code**, committed the offsets, and made **zero runtime oracle calls** before the host exposed the original for verification and benchmarking. The code was benchmarked with 13 counterbalanced, warmed, 8-million-calls-per-export trials after module initialization.

These numbers remain narrow source-family and host-specific diagnostics, not a universal security or runtime certification.

### Real-browser COO source-only reconstruction and four-way check

The same source-matched challenge and independent zero-query attacker were also executed in a **real Chromium browser**, rather than relying on Node's ESM implementation. The focused existing [manual compact browser workflow 45025050110](https://github.com/FlareZ123/obfs/actions/runs/45025050110) passed at source SHA `7d9950e153a0173ace6099c9ce425e415f60dfcc` using **Chrome 157.0.8103.78** on Ubuntu with Node 22 as the HTTP test host. The new `sims/llm-matched-affine-chromium.js` serves four separate same-private-source ESM files over `http://127.0.0.1`: native, actual COO two-path polyvariant, esbuild-minified and the statically reconstructed independent module. The host grades both source-only offsets before revealing its private source. Browser measurements and result marshaling remain outside the protected scripts.

The browser compared **8,212 fixed and deterministic pseudorandom test inputs per export**, including signed Int32 boundaries, numeric/non-numeric strings, NaN, infinities, BigInt and Symbol conversion failures. All 3 exports × 8,212 values × 3 alternative ESM arms, **73,908 public-vs-native observational comparisons**, matched the returned numeric values or exception type. The browser additionally confirmed that every generated or reconstructed function preserved the original name and arity, while its exact `Function.prototype.toString` text changed; the minified functions also differed by name.

Nine counterbalanced browser `performance.now()` wall-time rounds used 2,000,000 input-dependent calls per export per variant. The protected/native median *paired* runtime ratio was **0.903x**; rebuilt/native **0.871x**, with **9/9 pairs within 2.5x** in this one-browser, warmed, initialization-excluded sample. This is a browser wall-clock measurement that can be influenced by JIT and scheduling, **not a calibrated processor-CPU claim** and **not full COO startup-inclusive compliance**. In this instance, the relatively larger protected source (5,333 bytes) executed faster than the 324-byte native source while remaining statically reconstructable to a 182-byte module. No generalized speedup is inferred.

The complete post-graded source, public/private source commitment, browser version, exact requests, reflection facts and raw timing arrays were archived as [`matched-affine-chromium`](https://github.com/FlareZ123/obfs/actions/runs/45025050110), artifact ID `14755233129`, SHA-256 `527fb230541dd13f27407f0a37346c6aaee2fb6770fdf7e173751b53dc2ebbb3`. ## Executable evidence and limitations

The focused `test/llm-matched-affine-challenge.test.js` is a **mechanics/parity control**, deliberately not an LLM attack. It loads each public artifact as an actual Node ESM data module, obtains numeric translation answers from one public runtime probe, verifies same-source answer equality, runs 1,024 original-versus-both-public hold-outs per export, grades both arms in one shot and audits the salted commitment after reveal. It also verifies malformed answer refusal and one-shot replay rejection in the host. A separate strict `jsconfig.llm-matched-affine.json` covers both new files. These tests should be run on both Node22 Ubuntu and Windows using the pre-existing manual polyvariant affine workflow.

**Interpretation boundary:** the test uses runtime probes to check protocol implementation. Any future one-pass no-tools model evaluation must collect new independent answers. No model experiment, cross-platform runtime outcome, empirical attacker-cost advantage, generalized security guarantee, or 2.5x compute claim is asserted by this report. The existing COO/SNO generated-function reconstruction evidence remains a negative security control.
