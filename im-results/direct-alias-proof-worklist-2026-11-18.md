# Direct-alias owner worklist: byte-identical compiler proof optimization

**Agent 4, 18 November 2026. Intermediate compiler engineering result.** This report does not establish security against reconstruction or the 2.5× application runtime budget.

## Narrow change and semantic proof boundary

The root-independent `src/properties.js::collectProofInventory` already caches declarations and usage facts under a parsed-AST `WeakMap`. It now also caches `directAliasDeclarations`: an index from the spelling of an identifier initializer to the corresponding simple alias declarators. In `proveLocalObject`, only if there are **no verified callable signatures, no private owner tuples and no private owner records**, a queue walks these reverse edges from the candidate root. The queue checks the original binding uniqueness, alias-membership and declaration predicates, and adds aliases monotonically.

Under this explicitly narrow condition, `resolves(expression)` accepts exactly an identifier already in the alias set: there are no tracked functions to satisfy an identity-return call and no tracked tuple/record carrier to satisfy a static member read. The queue therefore computes the same transitive closure as the previous repeated linear scan of `aliasDeclarations`. All downstream lexical scope, import, dynamic-property, member-consumer, inheritance/reflection and edit gates are unchanged. Any case with a recognized function/owner carrier follows the unchanged general fixed point. Source equality and native/emitted checks below are empirical validations of this reasoning, and do not prove general JS observational soundness.

The regression `test/local-direct-alias-worklist.test.js` includes 128 independent two-hop owners with exactly 128 real private-key rewrites and an escaped reflective owner whose spelling must stay unchanged while a distinct positive owner remains rewritten. A later branch-only test exercises 256 transitive alias hops (after the source pin below).

## Meaning and limitations

The demonstrated improvement is a **build-time scalability** gain in a deliberately alias-heavy corpus. Four interleaved samples on hosted runners are useful but not a large randomized multi-hardware study. It says nothing directly about the obfuscated JavaScript's repeated runtime, memory use, source secrecy, hostile-runtime tamper defense or authorization. Rich function/callable private flows retain the original algorithm, so no improvement is claimed for those cases. One can trivially recover property spellings under fully instrumented COO/SNO control, and SCO online relaying remains outside this change.
