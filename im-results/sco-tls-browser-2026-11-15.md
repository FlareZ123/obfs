# Real Chromium HTTPS execution of the compiler-generated SCO ESM facade

**Status:** intermediate executable browser validation, 2026-11-15. Source [test/sco-real-tls-browser.js](../test/sco-real-tls-browser.js), existing [manual-browser.yml](../.github/workflows/manual-browser.yml), pinned successful [workflow 43762602922](https://github.com/FlareZ123/obfs/actions/runs/43762602922) at immutable commit `9d490fe68a9078b61ba8da74f469a47ecdff9e30`, Ubuntu Google Chrome headless, Node 22.

The test imports the original dedicated private ESM from `examples/sco-private/before-private.mjs` and uses the already-reviewed sample server `examples/sco-private/server.cjs` to serve an **actual compiler-generated public ESM facade** via `partitionScoAsyncModule` and `createScoHandler`. The original sample holds its HMAC key in a runtime environment variable, set to a fresh random value for the test. The endpoint requires HTTP Basic authentication for all public read and private RPC routes. The current sample server itself listens on loopback HTTP only; this experiment adds a loopback HTTPS/TLS 1.3 reverse proxy in front of it. The browser executes the same-origin ESM import and credentialed RPC through HTTPS, then prints the private HMAC output.

The local test certificate is self-signed and published in `sims/fixtures`, so the browser has no default trust anchor. Rather than globally ignore all certificate failures, the test computes that fixture certificate's SHA-256 Subject Public Key Info (SPKI) fingerprint and passes Chromium's **`--ignore-certificate-errors-spki-list=<fixture SPKI hash>`** flag with a dedicated temporary `--user-data-dir`. This flag is a **narrow test-only certificate-error exception**, not general PKI validation or certificate pinning provided by the site's JavaScript. Chromium's upstream documentation explains that the flag allows certificate verification errors for matching public keys: [Chromium source switch history](https://chromium.googlesource.com/chromium/src/+/8402d3c5bc13e018fa75eba650ed881755e0223b). The test explicitly **does not use** `--ignore-certificate-errors`.

A second isolated Chromium profile visits the same HTTPS URL **without the test exception**, and the test asserts that it does not execute the protected 64-digit HMAC result. The profile with the exact fixture SPKI exception must load and run the public ESM over HTTPS and produce the exact same digest as the original private Node module on the chosen 128-bit challenge.

## Verified outcome

- **Untrusted profile:** Cannot return the protected 64-hex result over the untrusted TLS certificate.
- **Test-SPKI allowlisted profile:** Browser's ESM facade produces the exact HMAC output of the private server module; the hosted original source remains outside the public routes.
- **Strict JSDoc checks:** The targeted `jsconfig.sco-tls-browser.json` and the remaining browser integration suite passed in pinned run `43762602922`. The initial attempt failed only for three strict-null-flow warnings in this new test and was corrected before successful validation.

The check is on one CI Ubuntu Chromium runner, one challenge input, local browser+Node process topology, and an intentionally trusted test certificate public key. It is compatible with the broader [Linux/Windows TLS and authorized-relay evidence](sco-tls-generated-facade-relay-2026-11-15.md): the server holds real private implementation, while a legitimate user with unlimited credentials can still relay its functionality. It does **not** show that TLS SPKI exceptions are production security, that code is secure against DevTools/runtime injection, that credentials cannot be relayed, or that whole real-Internet applications meet 2.5× overhead.

Next meaningful step: terminate TLS directly on the application instead of through a local reverse proxy; test standard browser PKI trust on a genuinely trusted origin; measure physical RTT and cross-origin policy; drive an independent hostile browser with instrumentation while preserving the same public API.
