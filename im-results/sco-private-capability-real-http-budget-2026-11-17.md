- Both platforms obtained the **actual published** 546-byte ESM facade (SHA-256 `e854152aa0c24466f301c576d1e230ae0eed1d4d97503b67893c240d33eb92f9`) through `GET /obfs/public.mjs`, imported it, and executed its own issued handle via authenticated `POST /obfs/rpc`. The `issue` and `step` facade is generated by the real `createScoRpcClientSource`, backed by `createScoHandler`, `createScoCapabilityScope` and `createScoPrivateHandles` on the trusted server. One unauthenticated RPC returned 403; the served facade excludes the server's private `createHmac` implementation.
- A fresh, independent native handle and remote handle start with the same `counter=0`, share the same secret key, client input sequence and optional 8 MiB private buffer; output parity is asserted after **every** paired native-versus-remote session. Seven alternated trial-order pairs per workload. All requests and server execution run in one Node process on local HTTP to allow combined-process CPU accounting. There is no physical network, certificate-verified TLS, browser execution or cross-process CPU attribution.
- Initial two-platform [run 44185190354](https://github.com/FlareZ123/obfs/actions/runs/44185190354) at `b2fa12e0` validated the exact-output parity and first wall results, without the CPU instrumentation. A later [run 44185721750](https://github.com/FlareZ123/obfs/actions/runs/44185721750) at `6260ca57` had only a **Windows harness failure**: Windows reported zero process CPU microseconds for a very short native operation. It was unsound to assert that sub-resolution CPU timings must be nonzero. The final pinned run records missing CPU ratios explicitly instead of inventing values and adds a 2,048-call cheap-work session for a measurable long-running CPU contrast.

## Workload and metrics

The native `step` executes the exact same server-resident private handle access, counter update and HMAC-SHA256 work directly within one native account scope. The remote `step` executes it via a generated authenticated facade with separate HTTP JSON calls, server authorization and keyed principal isolation. The native scope is entered once per sampled session whereas remote authorization is checked per RPC; this favors the native baseline and represents the runtime cost of the **declared** API/transport contract, rather than an isolated minifier comparison. Public handle acquisition and client ESM import are measured separately and **not falsely deducted** under the allowed server-only initialization exception.

Wall time is monotonic `process.hrtime.bigint`; combined-process CPU is `process.cpuUsage` user plus system difference for the same paired operation. On Windows, some native single-session CPU deltas are below timer resolution and explicitly excluded from CPU-ratio inference. Each CPU denominator must be **strictly positive**, so the number of measurable pairs differs by row. Rows with 0/0 CPU measurements are *unmeasured*, never a pass.

The sample demonstrates a **strict ceiling violation** for cheap protected operations and for the full 2,048-step repeated cheap-work session, including a measured Windows CPU veto in 4/4 measurable pairs. HMAC-heavy sessions have no observed 2.5× violations in the specified sampled local HTTP environment. These same heavy operations can have very different performance under real TLS, RTT, concurrent clients and background load. Neither the sample nor its source hash establishes a universal per-input ceiling, and the full API accepts the cheap input, so it **cannot meet the general 2.5× compute target**.

## Security evidence and decision

The opaque handle and private cryptographic key are kept on the trusted server. An attacker who controls the browser and has a valid Account A credential still controls the public request inputs and can run a same-account online relay. Existing actual HTTP capability tests protect against unauthorized Account B handle use and revocation, but this experiment does **not** independently demonstrate an incremental anti-reconstruction advantage over a conventional authenticated server API with the same private state. It provides a matched **performance and behavior boundary**, not a new cryptographic result.

**Decision:** retain [PR #65](https://github.com/FlareZ123/obfs/pull/65) as an experimental SCO integration, and retain [PR #72](https://github.com/FlareZ123/obfs/pull/72) as targeted reproducibility tooling. Reject any universal 2.5× or added strong obfuscation claim on this evidence. Server-side state isolation and authorization need a separate source-pinned independent attacker and same-trust conventional-server ablation before promotion.
