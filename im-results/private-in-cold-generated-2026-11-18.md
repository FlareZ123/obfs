# Compiler-generated private `in` cold-start and short-session cost

**Agent 2, 18 November 2026. Intermediate, cross-platform execution and performance evidence. No new security claim.**

## Exact source and real CI

The fixed-checksum research branch `agent2-private-in-cold-budget-20261118` at `e3140006da81586d9f7617ee50dfa76dd35b6585` passed the [manually dispatched Ubuntu/Windows Node 22 focused gate 44296173967](https://github.com/FlareZ123/obfs/actions/runs/44296173967). Both jobs passed all three new profilers, previously merged `in` ownership and Symbol/adversarial tests, strict primary/external JSDoc, sampled hot-loop benchmarks, static key reconstruction, and intended OS-specific Ubuntu real Chromium. The jobs used real Node v22.23.4 on Ubuntu 26.04 and Windows GitHub runners. No per-commit workflow was created.

Reproduce using `node sims/private-in-onefile-cold.js`, `node sims/private-in-immediate-cold.js`, and `node sims/private-in-cold-budget.js` with installed declared dependencies. All generated modules use the actual `obfuscateFiles` compiler with `mode:'coo'`, `strings:false`, `identifiers:false`, and stable per-workload seeds. Each script insists that **every** selected own field is actually renamed, and compares native versus emitted behavior with a nonvacuous weighted checksum (12 repeated executions; a simple XOR would incorrectly cancel even counts). Each arm samples 13 alternating-order pairs with 12 fresh `new Function` compilations per arm. Equal-width changing trailing comments reduce identical-source cache reuse. CPU is Node process user+system `process.cpuUsage`; wall clock is `performance.now()`. Source transformation/build cost is excluded from runtime.

## Three distinct supported/proposed deployment boundaries

1. **Exact, directly emitted standalone CommonJS file:** `private-in-onefile-cold.js` compiles and executes exactly one generated file, with 64/256/512/1,024/2,048 separate private owners and literal own-key `in` probes. No postprocessing/concatenation is involved. The measured parse and top-level calculation are COO initialization and hence cannot be deducted. The full 2,048-owner original was 131,224 bytes versus 202,904 generated bytes; 2,048/2,048 properties actually changed.
2. **Immediate top-level initialization, manually bundled compiler-generated CommonJS-compatible chunks:** `private-in-immediate-cold.js` obfuscates 64-owner chunks independently, then concatenates their exact emitted text into a valid single function with a shared total. Workloads have 64/256/1,024/4,096/8,192 owners. The 8,192-owner original is 486,586 bytes versus 773,306 generated bytes. This is a deliberate **experimental postprocessing topology**, not a built-in obfuscator bundling feature or a real browser loader.
3. **Short, repeatedly callable sessions in the same manually bundled topology:** `private-in-cold-budget.js` compiles up to 4,096 private owners with closure reads and executes each resulting session 0, 1 or 64 times. It separates startup-only, startup-plus-first-use, and more work. Its 4,096-owner original is 403,326 bytes versus 546,686 generated bytes.

The 256-owner immediate case showed a **1.733× Ubuntu CPU median**; none of the population CPU or wall median ratios exceeded 2.5×. Windows process CPU has coarse ticks: the 64-owner one-file and 64-owner session cases had no measurable CPU pairs, and other small populations had incomplete CPU pairs. Their wall-clock data must not be silently described as CPU data. Real individual strict CPU and one wall breaches occurred, so passing medians **do not** establish a universal hard 2.5× bound. The samples include JIT, GC and scheduling variability; no causal claim about those outliers is established. The complete per-pair ratios and raw times remain in the source-pinned GitHub Actions logs.

## Compilation scalability is a separate concern

The standalone-file source runs its complete compiler for each increasing owner count. On Ubuntu, the time between the end-of-profile log for 1,024 owners and that for 2,048 owners was about **212.7 seconds**, versus about **145.7 seconds on Windows**. These gaps include building the next cohort **and its paired runtime measurements**; they are not isolated obfuscator build time and cannot be entered into the COO runtime ratio. They suggest investigating proof-scan scaling. A dedicated compiler-only benchmark is required to attribute costs.

## Security and decision limits

These workloads test a real source-rewrite positive case and selected CPU/size tradeoffs. They provide no measurement of adversarial recovery time; the repository's separate public-only `in` key reconstruction succeeds without the compiler seed. All three profilers are Node CommonJS or experimental manually concatenated bundles; there is no cold Chromium, WAN transport, arbitrary real-world workload or full independent-client CPU guarantee in these experiments.

This finding is an intermediate compatibility/performance characterization. It does **not** override the strong-protection **RELEASE-BLOCKED** verdict, earlier cross-mode attack results, or any strict sample exceeding the target ceiling.
