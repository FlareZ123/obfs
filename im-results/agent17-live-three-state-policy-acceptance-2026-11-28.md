## Question

Does the exact at-most-three-state, no-reset Mealy policy survive a real process-separated authenticated HTTP facade, and does its terminal behavior class support an offline continuation clone after the service is shut down? Is the result specific to the generated SCO facade, or does an equal-trust ordinary minified RPC facade expose the same behavior?

## Harness and trust boundary

The test uses the exact minimax policy and behavior quotient from sims/sco-three-state-minimax.js. The public policy contains its decision DAG and classOutput/classNext quotient arrays.

The test process starts a private SCO ESM module and serves its generated client and authenticated RPC facade. A separate Node attacker child process receives only:
- the public client source and public method identifier;
- the public minimax policy and behavior quotient;
- the service origin;
- the legitimate test session credential.

It does not receive the private source module, transition table, current state, evaluator closure, or server memory. The private module is imported from a data URL and is not materialized on disk; the child runs with its working directory set to the public-artifact directory. **This is not an OS sandbox:** the child and server still share the same runner identity and filesystem permissions, so the test is process-separated API evaluation, not proof of hardened filesystem/process isolation. The server requires the same cookie and valid one-symbol operation arguments at both RPC authorization checks.

The matched control serves an ordinary minified ESM client generated by esbuild and an ordinary JSON-RPC server with the same hidden machine, operation, endpoint, and cookie boundary. Both arms use the same public policy and the same attacker implementation.

Each attacker records its full input/output transcript, HTTP status and success value for every request, public-client SHA-256, policy SHA-256, query count, and terminal behavior class.

## Post-shutdown continuation check

At the terminal policy leaf, the attacker uses only the public behavior quotient to predict outputs for a fixed 64-symbol held-out input sequence.

The parent closes the corresponding HTTP server before it verifies the held-out predictions against the private machine and the server's final state. Thus the held-out continuation is not answered by the live service. It is a check of the behavior clone inferred by the attacker.

The full receipt artifact contains the per-request transcript, source/policy hashes, final state, terminal class, held-out inputs, predicted outputs, and independently evaluated outputs.

## Out-of-prior falsifier

A separate negative control constructs a 27-state, complete deterministic machine with 27 distinct behavior classes. It reproduces the same 23-query transcript and the same terminal policy class (5091) as a minimal three-state base machine, yet differs immediately on held-out suffix [0]:

- original three-state machine: output [0];
- 27-state extension: output [1].

The extension is strongly connected and all its states are reachable. It retains a three-state base submachine and unrolls the observed transcript into a path whose final state is reached only after the last observation. This demonstrates why the 24-query guarantee must remain explicitly conditional on the at-most-three-state prior.

## Interpretation and limitations

The live test establishes that the selected finite deterministic machine behaviors can be learned through the generated authenticated SCO facade at the same query cost as the ordinary minified RPC control. The behavior quotient allows an exact offline continuation prediction after shutdown. This is a behavioral clone, not private-source recovery: the private ESM module was never served to the attacker. SCO can therefore still provide source confidentiality by keeping execution server-side, but it cannot promise that a small deterministic API's semantics are unlearnable. Keep source confidentiality, behavior confidentiality, and integrity as separate claims.

It does not establish that arbitrary JavaScript programs, arbitrary SCO services, COO, or SNO can be reconstructed in 24 calls. It does not establish general tamper resistance, URL-lock security, anti-instrumentation security, or the 2.5x hot-runtime budget. A production SCO service must not rely on a tiny deterministic finite-state RPC surface as a secrecy boundary when an authenticated attacker can make repeated requests.

The release decision remains NO-GO / RELEASE-BLOCKED pending the broader independent security, compatibility, and performance gates.
