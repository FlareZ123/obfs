# SCO trusted authority key: same-label cross-registry state isolation

**28 Nov 2026, experimental stacked reviewer candidate.** This branch stacks on draft [PR #408](https://github.com/FlareZ123/obfs/pull/408), which itself stacks on draft [PR #405](https://github.com/FlareZ123/obfs/pull/405). Scope is trusted server WebAuthn *state configuration*, not JavaScript obfuscation secrecy, authentication of arbitrary application callbacks or a general release gate.

## Motivation and construction

A public `credentialAuthorityId` from #408 distinguishes independently **named** registries even when RP/origin/UV/TTL/capacity policy matches. But two services that accidentally reuse the same label still share the same state configuration hash despite different credential registries, and may cross-admit a separately signed credential and bearer. #408 explicitly includes that residual as a test.

The proposed optional `credentialAuthorityKey?:Buffer` accepts exactly 32 raw bytes of **trusted, high-entropy, application-provisioned, per-registry secret material**. The constructor hashes `'obfs-sco-webauthn-authority-key-v1:' || key` with SHA-256 and embeds the resulting hex digest in the versioned **v3 shared-store policy tuple**. The existing synchronous atomic `assertConfiguration` checks equality of the outer SHA-256 hash; a different secret causes policy mismatch even when the public label is identical. This is not a token MAC; tokens and authorization hot path are unchanged. No key or key digest is intentionally returned to the client; the key exists only in caller memory at gate initialization.

To preserve migration, the **v1 tuple remains identical** when no label and no key; the existing **v2 tuple remains identical** when a label but no key. A key selects v3, with empty-string sentinel for absent label (invalid as an explicit label). Distinct keys are overwhelmingly unlikely to have identical SHA-256 digests if provisioned independently; this **does not** prove the caller actually used independent registries, counter CAS, principal namespaces or clocks. If the same secret and label are reused across separate registries, the original cross-admission still succeeds. A compromised trusted SCO server can lie about registry and key config by design. Planned key rotation needs new state namespace/migration rather than rewriting persisted policy hash.

These selected state API controls are **not** a formal construction of trust boundaries from callbacks. They do not improve COO/SNO reverse engineering resistance, prevent authorized online relay, provide browser attestation or establish universal <=2.5x compute. The only new digest is calculated at trusted SCO **initialization** (the explicitly amortizable regime), while per-request and protected hot-loop code are unchanged. Do not elevate this experiment to a three-mode release GO; independently review key provisioning, migration, application authentication and combined integration.
