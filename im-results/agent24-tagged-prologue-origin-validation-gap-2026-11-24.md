## Reproduction

The harness builds the existing finite direct-`Function.prototype.toString.call` plan, then creates an authentic `SourceEditMap` with two edits:

1. An insertion after the source-reader call, tagged `strings-decoder-prologue`. It declares a string-array helper, contains one permitted `for` loop and `String.fromCharCode` call, and then executes a top-level `throw 0`.
2. A replacement of the unrelated `'safe-literal'` with `_helper[0]`, tagged `strings-decoder-replacement`.

It passes the two labels as `allowedOrigins` to `acceptPlannedPass`. The candidate accepts the pass. Importing the original module succeeds and exports `labelText === 'safe-literal'`; importing the accepted emitted module throws the value `0`.

The insertion is after the reader call, so the current FramePosition check remains satisfied. All protected source spans remain byte-for-byte unchanged and map to current AST nodes. The failure is therefore not a source-map relocation error.

## Cause

At this candidate pin:

- `hasApprovedPassEdits` treats any inserted segment labeled `strings-decoder-prologue` as approved without inspecting its inserted text or complete AST shape.
- `collectStringDecoderContext` checks for one string-array helper and one or two `ForStatement` loops, but does not reject additional top-level statements or side effects inside the tagged prologue range.
- `validatePlanSemantics` does not reject a `ThrowStatement` in that range.
- The map WeakSet brand proves that the map was issued by `applyEditsWithMap`; it does not prove that the supplied origin label truthfully describes a valid decoder prologue.

The source comment correctly calls origin labels compiler provenance rather than cryptographic authentication. The resulting trust boundary must therefore be explicit: pass acceptance relies on trusted code producing truthful labels, and the validator is not an independent semantic-equivalence proof for arbitrary pass producers.

## Scope and interpretation

This does **not** demonstrate that an input author can remotely inject a throw into the current `obfuscateFiles` pipeline. In the current core integration, the allowed labels are supplied by trusted in-process transforms; ordinary source text cannot directly choose the label. The reproduction demonstrates that an authentic map plus an allowed label is sufficient to make the exported pass validator accept a behavior-changing prologue. It is relevant to claims about the validator's independence, robustness to buggy/misbehaving pass producers, and any future reuse of the API across less-trusted transform boundaries.

## Recommended follow-up

1. Add this exact negative fixture to the candidate regression suite and require `acceptPlannedPass(...) === null`.
2. Validate the complete decoder-prologue AST against a narrow whitelist generated by `encodeStrings`; reject extra top-level statements, `ThrowStatement`, `DebuggerStatement`, unapproved assignments/calls, and any node not part of the canonical decoder structure.
3. Keep origin labels as provenance metadata, not as the sole semantic approval proof. A private pass-specific capability bound to the exact output/map could strengthen producer identity, but would not replace AST-shape and behavior validation if buggy producers are in scope.
4. Re-run the exact-pin direct harness and focused producer tests after the repair. Do not infer comprehensive acceptance from this focused result.

This finding remains intermediate material in `im-results/`. It does not change the project's **NO-GO / RELEASE-BLOCKED** status; full compatibility, hostile-runtime behavior, static/dynamic reconstruction resistance, and the 2.5× budget remain separate acceptance obligations.


## Actual encoder reachability

The reproduction deliberately places the tagged prologue after the reader call so that the candidate's FramePosition guard remains satisfied. This is **not** the placement emitted by the current `encodeStrings` implementation at this candidate pin: `src/strings.js` inserts `'\\n'+init` at the beginning of the module body, after only a hashbang/directive prologue. For the direct-reader fixture, that real decoder insertion moves the reader frame and is rejected by the FramePosition guard. Agent 4's exact candidate run `45420260402` also records the real compiler positive output with `literals: 0`.

Consequently, the demonstrated accepted `throw` is not reachable through the current core's ordinary string-encoder placement for this fixture. It is a pass-validator trust-boundary witness: if an allowed-origin producer can place a tagged decoder-shaped range after the reader (or a future transform reuses the API), the validator does not independently establish that the entire prologue is semantics-preserving. Keep this distinction explicit when triaging severity.
