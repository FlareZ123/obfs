# Cost-aware WebAssembly conditional selection: typed semantics, seeded public cloning and first strategy grid

**Status:** Intermediate compiler/application performance evidence. Agent 38, 2026-11-16. This report concerns opt-in COO/SNO `experimentalWasmI32` and direct `lowerWasmI32Functions`. It does not establish any new confidentiality, integrity, or authorization claim.

## Architecture change

An AST-restricted, signed-Int32 Number ternary can be lowered to either: (1) **eager Wasm `select`**, evaluating true and false branch bytecodes, or (2) **lazy structured WebAssembly `if/else`**, evaluating the condition followed by its selected branch only. Wasm uses `0x04 0x7f ... 0x05 ... 0x0b` for an i32-result if/else, matching the [WebAssembly Core binary specification](https://webassembly.github.io/spec/core/binary/instructions.html). All operands are pure typed bitvector expressions. This proof excludes source-level effects and terminal mixed signed/unsigned ternary values, so either lowering returns the original typed result.

Direct research option `conditionalStrategy:'auto'|'select'|'if'` forces the strategy or chooses automatically. The production opt-in pipeline keeps `auto`. Source grammar safety is unchanged from [conditional report](wasm-i32-conditional-2026-11-16.md). The cost heuristic is an empirical proxy based on emitted arm-byte lengths, not a promised 2.5× decision procedure. The original two-to-four-argument grammar and early-import ESM helper remain.

The independent bytecode-only attacker in `sims/wasm-i32-static-recover.js` now symbolically decodes **nested Wasm `if/else` blocks**, preserving expression operands beneath each control-flow frame and rebuilding the original `?:` tree. This defeats static complexity claims for either strategy. `test/wasm-i32-lazy-conditional.test.js` verifies both compiled strategies and attacker-source clones for 4,096 typed asymmetric vectors plus 2×1,024 nested-graph vectors.

## Initial 4×5 strategy/frequency grid and heuristic correction

A separate manually dispatched [cross-platform performance grid 43806488448](https://github.com/FlareZ123/obfs/actions/runs/43806488448), at source `f7f2ba23cd7f0b3b3f5794a8be7a609bcff0e995`, ran `sims/wasm-i32-strategy-grid.js` on **four independent conditional kernels** and five true-input fractions (`0/32,1/32,16/32,31/32,32/32`). Each row validates native/auto/forced-select/forced-if results, warms each function and records 13 alternating 120,000-call timing trials. All **20/20 auto rows per OS** met 2.5× in this finite grid. Auto improved over forced select in **7/20 Ubuntu** and **10/20 Windows** rows, with reversals and jitter; no blanket ranking.

The initial auto policy was asymmetric-bytecode-only: branch lengths totaling at least 48 bytes and at least 3:1 arm imbalance. In the **balanced-heavy** kernel, despite native equivalence, auto incorrectly selected eager `select`. For all five branch frequencies, forcing lazy improved the observed ratios: Ubuntu auto **1.66–1.94×** vs forced lazy **1.35–1.60×**; Windows auto **1.80–1.85×** vs forced lazy **1.58–1.68×**. Both emitted binaries were public and reconstructable, 260 and 263 bytes respectively.

**Policy revision:** Also choose lazy `if/else` whenever combined emitted arm lengths reach **96 bytes**, regardless of imbalance; preserve the 48-byte/3:1 case and select for small balanced arms. This revision is derived from a finite counterexample, is not an optimal policy proof, and awaits more held-out workloads and a final independent grid gate. The new regression checks auto == forced if on the expensive balanced expression and its source-only reconstruction.

## Threat model and limitations

- **COO:** Attacker can recover the complete native ternary from distributed JS/Wasm alone. Module instantiation contributes to chargeable startup and may violate 2.5× for short lifetimes. A static byte heuristic cannot guarantee user-specific mix.
- **SNO:** Eager/lazy backend is pre-obfuscated, but an attacker controlling the filesystem and runtime can lift the binary or replace exported methods.
- **SCO:** This compiler does not withhold server-only code or add cryptographic authorization. Separately hosted backend decisions and server-side enforcement remain necessary for a trusted boundary.
- **Performance:** Warm ratios and the 4×5 grid are empirical Node22 samples only. The selected strategy may be slower on a different CPU, call frequency, branch probability, or JS JIT. Cold-to-hot budget failures already exist in the separate Wasm research report.

**Decision:** Retain cost-aware lazy control flow as opt-in compiler research and continue adversarial validation. Any security promotion requires a new attack-resistant result rather than only syntactic control flow.

## Held-out rerun after the balanced-heavy policy correction

**Verified exact source pin:** `80188666946281cff25d0238ba8580194bfc355b`. Both [focused validation 43806792263](https://github.com/FlareZ123/obfs/actions/runs/43806792263) and the separate [Linux/Windows strategy grid 43806797124](https://github.com/FlareZ123/obfs/actions/runs/43806797124) passed. The focused gate retains exact sampled source, multi-module/cyclic ESM tests, public bytecode extraction and strict JSDoc. This second performance run uses the same four generated kernels and 5 × branch-frequency grid but now auto selects lazy for the expensive balanced case.

- **Ubuntu:** 20/20 auto rows at or below 2.5×, range **1.426–1.883×**. Auto was faster than forced select in **18/20** medians.
- **Windows:** 20/20 auto rows at or below 2.5×, range **1.438–2.377×**. Auto was faster than forced select in **11/20** medians. The maximum approaches the budget, so system-specific optimization and cold-start evidence remain important.
- **Balanced-heavy, 0/32 to 32/32 true frequencies:** Ubuntu auto **1.444–1.569×** vs forced eager **1.649–1.835×**. Windows auto **1.731–1.787×** vs forced eager **1.837–1.925×**. The auto bytecode is **263 bytes**, the structured `if/else` path matching forced lazy's functional output.
- Comparisons are independent warm medians on shared CI hosts; performance variance can reverse close rankings. The grid validates each function's native, automatic, forced-select and forced-if outputs at each branch frequency before measuring.

**Methodological verdict:** The balanced-heavy counterexample prompted a narrow policy improvement that transferred to this subsequent measured CI execution. The policy remains an empirically tuned grammar heuristic with finite coverage. A full-hostile attacker reconstructs all generated ternaries from their published bytes in either strategy, so the security resistance result is unchanged.
