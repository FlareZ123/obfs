Optional chaining does not bypass a TDZ. Every construction reaching the line throws `ReferenceError`. The SQLite fingerprint deliberately binds capacity, so a correct adapter must reject the second constructor before exercising global capacity. Donor commit `e7c731e3d1047f8acb1fd1e57cbb4d70488327c2` aligns both to 1 and separately tests mismatched-capacity refusal. **Source-pinned focused durability and strict JSDoc CI 46144507135 passed Ubuntu/Windows**; 2 focused jobs success, full node22 skipped.

## Bounded expiry-housekeeping performance direction

The default memory state has `purge(now)` which independently scans **all** outstanding challenge and session map entries on every challenge insert and every session mint. With N live rows and N insert/mint operations this performs quadratic scan work, not an inherent cost of WebAuthn cryptographic assertion. An isolated optional donor branch `agent5/webauthn-memory-expiry-index-20261128` at source `8ba1bcec65d25d11174b458c7d424ab93d9b0c98` preserves Map insertion order and tracks whether each map's expiries remain monotonically ordered. On ordered input it purges expired prefixes only; on out-of-order or nonfinite expiries it falls back to the original complete scan until empty. Deletion preserves any nondecreasing subsequence, so a prefix scan stops safely at the first unexpired row. A 6,000-transition seeded differential against the original linear-scan model plus a five-pair equal-work process-CPU receipt are in `test/sco-webauthn-memory-expiry-index.test.js`; focused CI [46145708467](https://github.com/FlareZ123/obfs/actions/runs/46145708467) was queued as of this checkpoint.

An **independent local simplified** Node 22.16 model (not exact production source, and not a release benchmark) ran 50,000 deterministic transitions without difference and measured median linear/ordered housekeeping CPU ratios about 30.4x at 512 live rows, 59.0x at 1,536, and 162.7x at 4,096, each five alternating-order CPU samples. Do not transfer those local ratios to the real SCO HTTP+ECDSA full-session path or treat an optimized-vs-unoptimized speedup as a security advantage versus equally trusted conventional authenticated code. The actual GitHub-runner exact-source result supersedes this model if it differs. Out-of-order expiry disables the fast path and retains old worst-case work.

## Scope and remaining obligations

- **Not general WebAuthn credential enrollment:** application still owns verified account binding, attestation/hardware provenance, credential registration/replacement and atomic sign-counter CAS. Two gates with identical RP/origin/UV/TTL/capacity fingerprints may still use *different* external credential registries; that trust policy is not captured by the hash. Do not claim policy equivalence across distinct callback implementations.
- **Not relay prevention:** the already-published [real Chromium negative](https://github.com/FlareZ123/obfs/actions/runs/46122643625) permits an extracted valid HttpOnly bearer to relay legitimate same-account SCO HTTP work. A browser's origin restriction prevents obtaining a new credential assertion in an untrusted origin; it does not make all authenticated RPC non-replayable under hostile client control.
- **Not multi-host durability:** SQLite WAL state is intended for trusted local filesystem with working OS locking; not a distributed store, crash/restart defense of all semantic variants, or security under the SNO filesystem owner threat. In-flight work cannot be retroactively cancelled by revocation.
- **No global 2.5x proof:** only initialization in allowed server contexts may be amortized; browser authenticator ceremonies, HTTP calls and repeated protected work require source-matched full-session and hot-path cost tests. A strict over-budget observation remains a veto.
