# Alias-aware String prototype admission for the eager decoder

**Date:** 18 November 2026. **Classification:** bounded compiler-correctness evidence, not strong-obfuscation security.

## Source-visible failure envelope

The SNO/COO opt-in eager XOR string decoder reads each encoded character through `raw.charCodeAt(j)`. A supplied CommonJS dependency can run before the target module and replace `String.prototype.charCodeAt`, while the native target's literal value remains independent of that method. For such a graph, emitting the decoder is an unsound semantic admission.

The existing `src/core.js::mutatesDecoderIntrinsic` recognized direct `Object.getPrototypeOf("")` and `Reflect.getPrototypeOf(new String(""))`, but its `isStringPrototype` call-expression branch compared the intrinsic receiver's literal identifier spelling. The compiler already maintained conservative fixed-point alias sets for `Object` and `Reflect`; those sets were not used in this one branch. A caller could therefore take the prototype through `const O=Object; O.getPrototypeOf("")`, `const R=Reflect; R.getPrototypeOf(new String(""))`, or their `globalThis` member spellings and replace `charCodeAt` before the decoder was initialized.

The four new cases in `test/ambient-string-alias.test.js` construct three supplied CommonJS files. `entry.cjs` loads the mutator first, then the protected literal target. The baseline process returns the original literal. Each case separately runs SNO and COO obfuscation with `strings:true`; it checks compiler refusal and exact child-process output. The `Reflect` variants pass an actual String wrapper object, because `Reflect.getPrototypeOf` must throw on a primitive input, while `Object.getPrototypeOf` boxes primitives.

## Narrow repair

`src/core.js::isStringPrototype` now resolves `Object` and `Reflect` receivers with the same `isObjectIntrinsic` and `isReflectIntrinsic` predicates already used by the surrounding analysis. This recognizes their declared aliases and direct `globalThis` member spellings without disabling an ordinary graph's decoder. It introduces no runtime code and no additional obfuscation claim.

The relevant ECMAScript normative contracts are [Object.getPrototypeOf](https://tc39.es/ecma262/2026/multipage/fundamental-objects.html#sec-object.getprototypeof) and [Reflect.getPrototypeOf](https://tc39.es/ecma262/2026/multipage/reflection.html#sec-reflect.getprototypeof). The latter requires an object argument.

## Limits and next proof obligations

The proof is syntactic and bounded to the supplied file group. Unknown environmental preloads, dynamic code, caller-mutated intrinsics, opaque aliases and arbitrary execution paths remain outside a general closed-realm proof. Refusing eager strings prevents an observed class of emitted decoder corruption; it does not increase static reconstruction cost, enforce host authorization, prevent runtime extraction, or establish a 2.5x limit for other workloads. The source-level string-instance argument alias case requires separate examination; even complete intrinsic tracking would not solve full-control COO/SNO hostility.

## Follow-up: local string-instance aliases and observed output corruption

A second negative family, added at `90fda6d08e34ab879fe76e52610831ff890613f2`, varied the source of the `getPrototypeOf` input: a local primitive string, a transitive primitive string alias, and a local `new String("")` wrapper alias. The original analyzer accepted a decoder for all three. The [red two-OS validation 44250510811](https://github.com/FlareZ123/obfs/actions/runs/44250510811) reported the three corresponding SNO decoder-admission assertion failures on both platforms.

To prove actual semantic divergence rather than only unsafe admission, an independent historical branch `agent10/string-instance-parity-red-20261118` starts from the vulnerable `90fda6` source and changes the same tests to execute and compare emitted/native processes **before** checking decoder counts. At `0c9508d73ebc746a463df025ae2f676ed9235b11`, [CI run 44252150865](https://github.com/FlareZ123/obfs/actions/runs/44252150865) reported all three SNO cases as *changed behavior of a valid preloaded CJS graph* on Ubuntu. The generated decoder called an overwritten `charCodeAt`, corrupting the result while the original target literal remained unchanged. This is a real 1:1 miscompile witness, on source-visible input. The branch is intentionally a negative control and must not be considered safe to release.

The repaired `src/core.js::mutatesDecoderIntrinsic` uses an additional fixed-point `stringInstances` set. Literal strings, no-substitution template strings, `new String` expressions, and their direct variable/assignment alias chains can now feed recognized `Object/Reflect.getPrototypeOf` calls. This changes compiler admission only, preserving generated runtime shape for eligible programs. The [source-pinned green full Node/Chromium validation 44251268380](https://github.com/FlareZ123/obfs/actions/runs/44251268380) succeeded on Ubuntu and Windows at `2ec87f49c69f5899b94aa4d3d9a12139be177ce4`. Added positive controls verify that read-only `String.prototype` aliases and an unrelated numeric-prototype graph still transform their target literals where the bounded proof admits them. A later mainline test ordering change, `3fef3bf0ce4be84a857f6536ce9d6039e305e62c`, checks exact runtime parity before refusal, preventing future count-only reports.

This remains an intentionally partial source-visible intrinsic analysis: arbitrary function-return values, custom prototype objects and unrestricted aliases can expose the same prototype without matching these literal/value shapes. No cross-runtime strong obfuscation or general budget claim follows.

## Source-visible opaque-return prototype poisoning

A further independent family shows that identifying only statically recognized `String` / `Array` instances remains unsound. In supplied CommonJS input, `function owner(){return new String('u')}`, `Object.getPrototypeOf(String('u'))`, `Object.getPrototypeOf({__proto__:String.prototype})`, and `function owner(){return []}` can produce a decoder-sensitive prototype. Mutation of `P.charCodeAt` or `P[Symbol.iterator]` then affects the generated XOR decoder while the native target's literal stays unchanged.

`test/decoder-opaque-prototype-source.test.js` independently executes the original and emitted three-file CJS graphs in fresh Node processes. It compares the actual complete string output **before** the compiler's transformed-literal refusal metric. Its first four fixtures run in both COO and SNO, and a known numeric-prototype mutation is a separate positive transformed-work control.

- **Actual-output red:** [run 44252651775](https://github.com/FlareZ123/obfs/actions/runs/44252651775), source `629cab7bd009a1a00ec50fd3bf770fe044282fc5`, on the earlier compiler. The Linux job reported **all eight** COO/SNO opaque-prototype cases as native/generated output mismatches. Native success and original literal were checked first. This failure is separate from a concurrent Blob Web IDL test failure.
- **Scoped green:** compiler guard commit `2b7a58bd120e2b1073ca0f69694d1dd64aadfae3`, then [manual decoder gate 44253593584](https://github.com/FlareZ123/obfs/actions/runs/44253593584) at `e90195dd44dc60ef5cb8d8581be0ce9c9f4d0c55`. Both Ubuntu and Windows completed the fixed-arity, inherited prototype and source-visible opaque prototype test lane successfully; Ubuntu also completed the real Chromium fixed-arity checks and strict JSDoc gates. The prior numeric alias and read-only String positive rewrites remained eligible.

The `possiblePrototypes` may-alias analysis recognizes uncertain direct `Object/Reflect.getPrototypeOf` returns and propagates ordinary Identifier aliases. It checks decoder-sensitive character conversion, numeric inherited-index keys, unknown computed keys, iterator replacements, prototype-chain writes, reflective mutators and possible `prototype.constructor` aliases. A direct nonstring primitive literal is a bounded precision exemption. Static unrelated named fields may remain eligible, preserving useful obfuscation coverage. The guard declines rewriting of a supplied graph whenever these risky writes may affect the decoder, rather than trying to repair a runtime already subject to hostile source-visible mutation.

A wider set of ten opaque mutation fixture classes, each in COO and SNO, at `6a260f960363479aeeec6c390cac30ca47f8a248` passed its **20 native/emitted parity and zero unsafe-literal-admission subtests** on both runner platforms within [manual gate 44253799124](https://github.com/FlareZ123/obfs/actions/runs/44253799124). The overall jobs were red due to **three new independent Agent 27 `document.defaultView.String` aliases**, introduced concurrently in `test/ambient-string-alias.test.js`, which also produced actual runtime mismatches. The gate's passing opaque subsection does not certify the full run; Agent 27 was notified to triage its separate browser-global alias gap. The positive numeric-prototype controls passed in the same scoped execution. This source pin records the exact currently supported set of assertions, with no universal exhaustiveness claim.

The proof envelope remains explicitly limited: arbitrary reflection of descriptors, indirect captured getters and host-preloaded intrinsic mutation can escape the syntactic may-alias closure. `results/README.md` therefore correctly retains the strong-protection release block. A new browser ESM native/emitted and static recovery extension in `test/decoder-array-prototype-browser.js` covers opaque source aliases and nonzero safe decode yield, pending its separate source-pinned Chromium result.

## Real Chromium module and source-only recovery cross-check

The existing `test/decoder-array-prototype-browser.js` ESM/CSP harness was extended with four more fixtures. It evaluates native, generated and independent source-only reconstructed modules under real Chromium, with `String.prototype.codePointAt` used to measure the original payload without inadvertently calling the deliberately poisoned `charCodeAt` being tested.

The [full manual browser gate 44254106267](https://github.com/FlareZ123/obfs/actions/runs/44254106267), exact source `d3d05b59a70b48a10c4a4f95853b7237258d7fde`, **passed** on Linux/Chromium, including all other browser steps, and printed these directly observed scoped metrics:

| --- | ---: | ---: | --- |
| Opaque String.prototype `charCodeAt` write | 0 | 0 | Exact parity |
| Opaque Array.prototype iterator write | 0 | 0 | Exact parity |
| Direct known Number prototype unrelated write | 1 | 1 | Exact parity |

For all four, the native Chromium payload measurement was `{first:65,last:90,length:2049}`. Additional inherited index and unrelated Object.prototype fixtures also passed; the CI log contained a separate Agent 27 document.defaultView fixture that refused unsafe encoding. The source-only attack recovered the **entire transformed literal** in the two safe encoded cases, confirming that compatibility and protected-work yield are separate from confidentiality.

**Conclusions remain local to these fixtures and exact toolchain runs.** When source-visible mutation makes the generated decoder semantically unsafe, the compiler now refuses its emitted work for these cases, which should be treated as a safety fallback. For source-safe cases, a recoverable XOR table may be emitted, so confidentiality is still not established. Exact compilation source, runner OS/Node and browser engine are necessary to generalize any benchmark or threat-model claim.

## Two further source-visible alias failures and repairs

**Reflective method replacement invalidates native-type proof.** A graph can replace `Object.getPrototypeOf` through `Object.defineProperty(Object,'getPrototypeOf', {value: ...})` without an overt assignment to `Object.getPrototypeOf`. Even `Object.getPrototypeOf(7)`, ordinarily guaranteed to resolve Number.prototype, can then return String.prototype. A subsequent `charCodeAt` replacement corrupted the emitted XOR decoder while the source literal was correct. This is **observed output divergence** in both COO and SNO on Ubuntu and Windows: [red 44254921277](https://github.com/FlareZ123/obfs/actions/runs/44254921277), exact `a91db828d9872d0388cd64256e281813b16ab33a`. The guard at `67e66ab2606033536f42ab59fc46b33ba76efab4` declines eager decoding when mutators target `Object/Reflect.getPrototypeOf`, including descriptors and property bags, while unrelated named writes preserve encoded yield. [Two-OS fixed-arity and decoder gate 44255209731](https://github.com/FlareZ123/obfs/actions/runs/44255209731) passed; [44255289607](https://github.com/FlareZ123/obfs/actions/runs/44255289607) additionally passed native/emitted parity for safely mutated unrelated Object/Reflect fields.

**Opaque String constructor references can escape through reflection.** After `P=Object.getPrototypeOf(owner())` where the owner returns a primitive string, each of `Reflect.get(P,'constructor')`, `const {constructor:C}=P`, and `Object.getOwnPropertyDescriptor(P,'constructor').value` yields `String` under the tested native runtime. Overwriting `C.fromCharCode` then corrupted the emitted decoder. [Source-pinned red 44255415406](https://github.com/FlareZ123/obfs/actions/runs/44255415406) recorded exactly **six** output mismatches, three paths times COO/SNO, on both OS. Guard commit `632c433cbdc204c84c312e4f6168a6c2f8c61f06` extends `isPossibleConstructor` and fixed-point destructured-binding tracking. The corresponding two-platform [green 44255673563](https://github.com/FlareZ123/obfs/actions/runs/44255673563) passed. Additional read-only controls added at `4b7ac933fb713e87625e574bb1eb6a6ffea374e3` separately require a transformed literal and exact runtime parity (validation [44255728232](https://github.com/FlareZ123/obfs/actions/runs/44255728232)). A separate real Chromium ESM fixture extension at `16a849629c75cf123b79635846b96fc072fd1f24` checks both mutated and read-only constructor aliases.

All these results concern syntactically supplied source graphs. Full-control client/runtime extraction, arbitrary dynamic reflection and remote host environmental mutation remain unbounded. The repaired output may simply stay unobfuscated in cases with unsafe ambient state. Strong security and universal runtime-budget targets are still unsupported.

## Chrome ESM reflected String constructor confirmation

A second independent [real Chromium manual browser gate 44255842411](https://github.com/FlareZ123/obfs/actions/runs/44255842411), source `16a849629c75cf123b79635846b96fc072fd1f24`, passed its complete browser suite. In `test/decoder-array-prototype-browser.js`, opaque `Reflect.get(P,'constructor')` and `const {constructor:C}=P` mutations of `String.fromCharCode` each refused unsafe COO string decoding (zero target literals encoded), and both native/emitted/reconstructed output paths matched in actual Chromium. A third read-only `Reflect.get` constructor fixture retained one encoded target literal and one independently source-recovered string, while preserving native browser output. The same tests run under a restrictive same-origin module CSP and test-pinned browser, rather than a simulated DOM. These observations corroborate the bounded Node source-visible alias guard and demonstrate an explicit nonzero protection-work baseline, while independent recovery confirms the encoded literal remains statically accessible.

## Mutable reflection: `Reflect.get` cannot be assumed native

A final source-visible mutation test invalidated the remaining numeric-constructor provenance shortcut. A supplied module executes `Reflect.set(Reflect, 'get', (target,key) => key === 'constructor' ? String : target[key])`, followed by `P = Object.getPrototypeOf(7)`, `C = Reflect.get(P,'constructor')`, and `C.fromCharCode = () => '?'`. The obfuscator previously treated `P` as independent of String because its argument was a numeric literal. The original program's target string remains intact, while the generated decoder calls the replaced `String.fromCharCode`. [Red targeted run 44256172053](https://github.com/FlareZ123/obfs/actions/runs/44256172053), source `0d8ede5cf502b8fe141f2dc910465dc50e8e3748`, observed real emitted/native output divergence in both COO and SNO on Ubuntu and Windows. An analogous replacement of `Object.getOwnPropertyDescriptor` was already conservatively refused in that source.

The `src/core.js::mutatesDecoderIntrinsic` amendment `16ccd0f4c01793a4c18f445cfd9d11834e52be30` invalidates the decoder admission when supplied code mutates any relevant native Object or Reflect read method used by its inference, through Object/Reflect mutators. It retains string decoding in the deliberately tested unrelated named helper-field cases. [Two-platform green manual decoder gate 44256364517](https://github.com/FlareZ123/obfs/actions/runs/44256364517) completed successfully on Ubuntu and Windows at `e520b6deb76e7a706e83531d4b4558132f6d96a8`, whose parent is the fix commit. It includes all expanded opaque-prototype test cases, their positive transformed-work controls, fixed-arity neighbors, strict JSDoc checks, and the real Chromium neighbor on Ubuntu.

This is a **bounded admission-safety repair**. It does not establish the deeper invariant that ambient intrinsic methods remain native at runtime, especially under an externally instrumented process. String tables emitted in the safe cases were still statically recovered in the independent Chromium ESM tests. The global security objective and arbitrary-host proof obligations remain open.
