# Signed per-operation WebAuthn gate for SCO: stolen-cookie replay denied, online relay survives (2026-11-21)

**Agent:** 10. **Classification:** source-pinned bounded security/performance-candidate evidence; not a production implementation or released backend.  
**Preregistered design and falsifiers:** [charter](../workplace/sco-webauthn-per-operation-charter-2026-11-21.md).

## Primary question

Can a selected server-private SCO operation require more authority than a bearer cookie by verifying one-use WebAuthn signatures over **server-registered, operation-bound challenges**? Does this prevent copied-client requests with an exported cookie, and what residual capability remains under the project's unlimited authorized-query SCO attacker?

The prior source-pinned [post-WebAuthn session boundary](./sco-webauthn-session-origin-boundary-2026-11-21.md) established that WebAuthn at login cannot prevent later raw-client reuse of an exported conventional cookie. This experiment adds an operation-level proof check as a matched control in the **same** genuine `createScoHandler` instance.

## Architecture and trust assumptions

- A trusted Node server uses the real `createScoHandler` from `src/sco.js`, with the existing bearer-only `protectedSum` and a new proof-gated `proofSum`. Both execute the identical server-resident `(Number(value)*17+29)>>>0` computation. Separate counters distinguish private calls.
- Both operations first require the registered random 256-bit `HttpOnly; SameSite=Strict` session cookie previously minted by a correctly verified WebAuthn login assertion.
- `proofSum` additionally requires a per-operation `x-webauthn-proof` header. The trusted `/proof-challenge` route authenticates the cookie, accepts only one safe integer argument to `proofSum`, generates a random 256-bit challenge, and records the exact allowed method, integer argument and session token. The browser calls real `navigator.credentials.get` for the `localhost` RP with `userVerification:'required'`.
- During SCO `authorizeOperation`, Node decodes the assertion header, requires a known and **unused** challenge belonging to that session, verifies intended arguments, exact `clientDataJSON` challenge and origin, RP hash, UP+UV bits and the ES256 public-key signature. It consumes the challenge before the server-private method runs.
- The client attacker controls the authorized page's DevTools/cookie storage, can execute scripts at the allowed origin, and can send arbitrary HTTP requests from `127.0.0.1` while supplying `Host: localhost:<port>`. The server and authenticator private key remain trusted. The authenticator is Chrome CDP's virtual CTAP2 device, so human presence/hardware provenance are not demonstrated.
- The proof header is transferred as base64 JSON in this bounded numeric-argument fixture. Arbitrary JSON, multiple principals, concurrency/atomicity, counter persistence, and production credential enrollment need more robust parsing, cryptographic and authorization machinery.

## Source-pinned validation

Final focused Linux/Chrome and strict Node JSDoc [manual CI 44877076476](https://github.com/FlareZ123/obfs/actions/runs/44877076476) passed at source commit `5cec37caa23bf8c3b6284d832789d1c88b8131ce`, Node v22.23.5. Earlier first-implementation [CI 44876991480](https://github.com/FlareZ123/obfs/actions/runs/44876991480) also passed before the additional forged-signature/session-revocation controls.

| Matched test | Observed |
| --- | --- |
| Allowed-origin browser obtains challenge, signs and calls proof-gated RPC | **HTTP 200**, expected result |
| Copied-origin raw client with valid exported cookie, no proof | **HTTP 403** |
| Copied-origin reuses proof already accepted | **HTTP 403** |

| Cryptographically invalid signature with otherwise correct fresh challenge | **HTTP 403** |
| Fresh valid signature but no session cookie | **HTTP 403** |
| Valid but unused signature after trusted server revokes session | **HTTP 403** |
| Fresh proof generated by hostile code at allowed origin, forwarded with exported cookie to raw copied-origin client | **HTTP 200**, expected result |

| Independently configured browser at copied origin requests `localhost` credential | browser `SecurityError` |
| Original bearer-only comparator accepts copied cookie from raw client | **HTTP 200** |

Exactly two executions occurred for `proofSum`: one legitimate same-origin request and one **fresh online forwarded proof**. Negative cases generated no private-method side effects. The bearer-only comparator also executed twice, once from each origin-controlled client. Browser JavaScript remained unable to read the HttpOnly cookie; DevTools could export it. The emitted public facade disclosed neither private implementation.

A single virtual-authenticator WebAuthn-signing observation was **0.8 ms wall time** in the final run; this is not a robust cost distribution or a compute-ratio result. The proof flow additionally requires a challenge HTTP request, authenticator ceremony and signature verification. No 2.5x compute budget is established. High-frequency, short operations must be assessed against the exact original workload and may be unsuitable for this ceremony.

The experiment is in `test/sco-webauthn-origin-boundary-browser.js`, invoked by the existing manually dispatched `.github/workflows/manual-sco-ratchet.yml` with `webauthn_boundary_only=true`. The project JSDoc gates passed. No per-commit workflow was added.

## Security conclusion

A valid, unexpired **cookie alone** cannot execute the proof-gated method through a copied-origin raw HTTP request. This is meaningful hardening against **offline reuse of an exported bearer credential without access to the authenticator**. A fresh proof must match both the trusted server's intended operation and session, and replay is blocked by a consumed challenge.

The stronger intended objective, **only running outside the copied/original client execution environment**, remains unsatisfied under the stated SCO attacker: hostile code already running at the admitted RP can ask the authenticator for a fresh allowed operation, then forward that exact signed proof and cookie to an attacker-controlled raw client. The server cannot distinguish it from the authorized operation because the attacker is legitimately authorized to request that operation. The successful online relay is a **precommitted** witness, consistent with `workplace/sco-authorized-relay-stopline-2026-11-19.md`.

The new gate should be credited only for operation-level WebAuthn proof freshness and copied-cookie-only misuse prevention with an external authenticator trust assumption. It should not be credited as same-account anti-relay, proof of original-source secrecy, cross-account isolation, real hardware user-presence, arbitrary payload canonicalization, or generic ≤2.5x overhead.

## Research decision

**Retain as an optional, narrow SCO hardening hypothesis for coarse valuable operations**, subject to adversarial production-protocol review, original-versus-transformed full-session CPU measurement, and user-verification feasibility. This is not a general default obfuscation pass. The release decision remains **RELEASE-BLOCKED**.
