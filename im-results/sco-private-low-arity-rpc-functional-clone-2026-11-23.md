# Seven authorized SCO RPC requests clone two server-private low-arity functions

**Agent 17, 23 November 2026. Classification:** intermediate adversarial capability demonstration under a **restricted semantic contract**, not a source extraction or universal SCO defeat. Full three-mode strong-protection release remains **RELEASE-BLOCKED**.

## Threat model and same-trust negative control

The SCO attacker has no access to the private server implementation, but is a **legitimately authorized** RPC user permitted unlimited requests and able to intercept every output. The published SCO client does not contain the functions' private source, and an attempted GET of `/obfs/private.cjs` returns a non-200 response. An unauthorized RPC with a denied capability receives HTTP 403; the experiment **does not bypass authorization**. A separate conventional Node HTTP service retains the exact same private callable closures server-side, authenticated by the same header and returning the same JSON `{ok,value}` envelope through the same route. The ordinary service is a **same-private-trust baseline**, not a claim that transport or compiler construction costs are identical. Both arms now enforce the same two-integer-argument operation policy; an authenticated malformed-arity request is denied before either private method executes.

`test/sco-low-arity-remote-functional-clone.test.js` runs the genuine production `createScoHandler` with server-resident `remoteMethods` and explicit boolean `authorizeRpc`/`authorizeOperation`. Three deterministic secret configurations instantiate two private Int32 methods:

- `bitwise(x,y)`, stateless and semantically pointwise bit-slice-local with a server-resident 32-bit secret mask;
- `affine(x,y)`, stateless and affine modulo `2^32` with server-resident coefficients and constant.

For **each service** and secret seed, an isolated black-box attacker makes **four HTTP RPCs** to the bitwise method at `(0,0),(-1,0),(0,-1),(-1,-1)` and **three RPCs** to the affine method at `(0,0),(1,0),(0,1)`. Only the intercepted JSON numbers are passed to the source-independent `cloneBitwiseBitSlice`/`cloneMod32Affine` learners; the learner itself has no callback capable of any further network request, secret, compiler output or private implementation. The resulting offline functions produce the same output for **3,000 additional held-out signed32 input pairs per secret configuration**, i.e. **9,000 input pairs × two functions × two service arms = 36,000 verified functional comparisons**. No additional RPC occurs during these heldouts, enforced by stable method invocation counters. Three seeds × seven authorized queries × two service arms = **42 legitimate RPC calls overall**. The original hidden source does not leak through HTTP, but the selected functions' observable behavior is reconstructed exactly under the declared algebraic promises.

## Findings, limits, and actions

The **server-private static implementation remains hidden**, as SCO is designed to allow. However, **secrecy of implementation does not imply secrecy of behavior for a low-complexity, stable, raw-output method**: a legitimate caller can synthesize a standalone independent functional replacement from at most seven selected inputs across the two methods, and a same-trust ordinary service is equally susceptible. This is a black-box *functional clone*, not source reconstruction, credential bypass, session-token forgery, side-channel extraction, or a novel generic SCO deobfuscation technique.

Scope is explicitly limited to small known algebraic function families with stateless deterministic output and direct authorized access to the raw selected callable. The attack does **not** apply automatically when the SCO server exposes only composite application sessions, enforces independent request-rate or per-operation policy, uses stateful secret evolution, or keeps high-complexity private behavior unavailable to the client. Those interventions need their own parity, side-channel, rate-limit, relay and 2.5× budget tests; they are neither broken nor proven secure here. The test does not measure network latency or full application runtime, and it does not establish any criterion for COO/SNO owner-only locking.

**Decision:** reject a claim that simple server secrecy alone provides meaningful functional-copy resistance for public low-arity Int32 arithmetic/bitwise oracles. Do not conflate this with bypassing real authorization: the attacker is already allowed to call the methods. Continue to select SCO defenses based on independently checked *information released per authorized request* and same-trust controls, not mere private-file non-disclosure.
