# Intrinsic-independent string decoder: bounded candidate assessment

**Agent 1, 21 November 2026, preliminary engineering experiment. Not an established security result.**

## Candidate and falsifier

The current eager string decoder generated by `src/strings.js` uses `String.fromCharCode` and `String.prototype.charCodeAt`. `src/core.js::mutatesDecoderIntrinsic` conservatively declines selected transformations when source-visible code may alter these intrinsics. Multiple draft decoder PRs investigate complex `Object.create`/descriptor/call-target provenance. The alternative here is to remove those mutable intrinsic dependencies from the **generated decoder itself**.

A compiled literal is stored as an alphanumeric token string. An own-property object literal maps token keys back to individual UTF-16 code units. Runtime decoding uses only primitive string indexing, object own-property indexing, string concatenation, and loops. The source generator supports 62 distinct units per one-character token and up to 3,844 per two-character token; it preserves isolated UTF-16 surrogates in its bounded tests. There is **no dynamic eval, remote loader or anti-debugger**.

**Predeclared falsifiers:** (1) any exact-string mismatch after selected built-in prototype changes; (2) zero-query source-only recovery of the token table and raw payload; (3) strict observed startup or hot-work runtime ratios above 2.5 against an equal-input direct literal control. Only a trusted SNO or server-side SCO initialization phase may be excluded from the prompt's computation budget.

The code artifacts have been committed to GitHub, but their exact committed bytes have **not** yet passed pinned two-platform CI or the full compiler/browser integration. The measurements below came from functionally equivalent local development scripts on Debian Linux, Node v22.16.0. Do not conflate these development samples with a green source-pinned repository gate.

## Component semantic and cost observations

Five deterministic inputs cover 64 ASCII units, 2,048 ASCII units, 140 distinct Greek units, 20 mixed ASCII/Unicode/lone-surrogate units, and 2,000 Unicode units. Each generated dictionary returned the identical original UTF-16 string both normally and after selected modifications to `String.fromCharCode`, `String.prototype.charCodeAt`, `Object.prototype.AA` and inherited `String.prototype['0']`. The standalone current-style XOR-loop control returned a different string in each modified realm. This experiment does **not** demonstrate a current compiler regression: production guards may decline these cases before emission.

The dictionary's published `dictionary` and `raw` JSON can be parsed by an attacker without executing generated JavaScript. The added zero-query static reconstruction control recovers all five original strings exactly. Public-source secrecy is therefore **explicitly falsified** for this candidate.

One local 9-context × 100-executions-per-context component median trial, milliseconds per decoder execution (the original uses a literal and performs no decoding):

| Input UTF-16 units | Direct literal | Current-style XOR | Dictionary | Dictionary/direct |
|---|---:|---:|---:|---:|
| ASCII 64 | 0.00127 | 0.01538 | 0.00823 | 6.47× |
| ASCII 2,048 | 0.00130 | 0.12534 | 0.07587 | 58.48× |
| Distinct 140 | 0.00063 | 0.02991 | 0.04132 | 66.02× |
| Mixed 20 | 0.00062 | 0.00940 | 0.00392 | 6.30× |
| Unicode 2,000 | 0.00061 | 0.13312 | 0.06854 | 112.95× |

These samples are noisy and intentionally execute decoding for every measured invocation. They are component startup diagnostics, not a whole-application overhead model. **All five reported median dictionary/direct startup ratios strictly exceed 2.5×**. This finite sample rejects blanket COO client-startup approval; it makes no assertion about every individual trial or every possible input.

## Cross-file hot-loop observations

The separate SNO-like graph requires a mutator module before the target module, then calls a real exported function. The direct-literal target and both dictionary variants produced the exact same aggregate checksum for 9 × 2,000,000 timed calls plus warming. Timings exclude module initialization. Three execution orders were rotated across nine separate Node process groups. The dictionary was tested with a `helper[0]` read at each function call and with a module-level alias holding the decoded string.

One local run's **nine paired ratios** (transformed/native) were:

| Pair | Repeated table lookup | Module-level decoded alias |
|---|---:|---:|
| 1 | 2.136 | 2.082 |
| 2 | 2.420 | 2.252 |
| 3 | 2.029 | 2.572 |
| 4 | 2.227 | 2.503 |
| 5 | 2.348 | 2.410 |
| 6 | 2.057 | 1.923 |
| 7 | 2.261 | 2.275 |
| 8 | 2.030 | 1.819 |
| 9 | 2.169 | 1.982 |

Medians of the nine ratios were approximately **2.169×** (direct table) and **2.252×** (alias). The alias had **2/9 strict observed over-budget pairs** despite equivalent output. A separate preceding direct-table-only trial observed **1/9 strict over-budget pairs** and a median ratio around **2.103×**. Each subprocess used internal median timing; pairs come from different processes. Runner scheduling/JIT effects matter, and these samples establish neither a population confidence bound nor general compliance.

## Follow-up: process CPU is independently measured

The graph simulator was extended at source `bedf47747e5316d1690b24d8e9396229195ab757` to record `process.cpuUsage(start)` user+system microseconds and elapsed wall time **for the same completed hot loop**. Node 22 documents this differential CPU API in [process.cpuUsage](https://nodejs.org/download/release/v22.17.0/docs/api/process.html#processcpuusagepreviousvalue). Each subprocess records nine separate calls and reports both medians, keeping the process initialization outside the hot loop. One process handles each variant in a balanced nine-pair schedule, so different variants are still compared across separate processes.

Two more independent local Node 22.16 Linux nine-pair runs (measurements from a near-equivalent local development mirror, **not exact GitHub source-pinned CI**) produced:

| Local run | Direct lookup CPU median | Direct strict CPU breaches | Decoded-alias CPU median | Alias strict CPU breaches |
|---|---:|---:|---:|---:|
| Trial A | 2.22757× | 3/9 | 2.01675× | 0/9 |
| Trial B | 2.21793× | 1/9 | 2.09800× | 0/9 |

This is more appropriate to the prompt's compute budget than wall time alone. Even the revised sample keeps strict hot-work violations for the repeated-table-lookup variant, while the alias remains insufficiently tested across other workloads. Trial A included one **4.65654×** process CPU pair. The runner and JIT behavior are variable, and neither the medians nor absence of breaches in a finite alias sample proves universal compliance. A further assessment should include a minified same-trust control and an exact immutable source runner.

## Decision

**No promotion to the primary strong-obfuscation candidate.** Zero-query static reconstruction succeeds, client startup strictly exceeds the budget on tested short cases, and selected SNO-like work remains near the budget with strict local breaches. The proposed code is a narrow intrinsic-independent correctness option rather than a confidentiality mechanism.

A continuation would have to show source-coincident full `obfuscateFiles` multi-file native/emitted equivalence, positive encoded-work yield, an equal-trust minified control, correct CommonJS and real browser startup behavior, and 2.5× cost evidence across short and sustained sessions. A source observer or dynamic external API must still cause conservative refusal when semantics cannot be established. Until then, retain these negative controls and avoid replacing the production decoder or expanding CI.
