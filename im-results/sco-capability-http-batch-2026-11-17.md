# Real compiled SCO capability session: serial versus batch and simulated policy delay (17 November 2026)

**Status:** predeclared experimental scenario, no executed evidence yet for this exact source. This candidate measures the cost of authenticated, principal-scoped private state operations through an actual compiled public ESM facade and HTTP handler. Its performance claim cannot be generalized beyond the specific workload, and a zero reported CPU duration must remain an unresolved observation.

## Question

For a stateful server-private key, capability handle and 16 real HMAC operations over an 8 MiB private business payload, compare:

1. Native in-process execution of the identical HMAC operations with the same secret key, inputs, payload and counter.
2. A public facade that mints an authenticated handle, performs 16 serial step RPCs, and revokes the handle.
3. The same public facade that mints a handle, performs one batch RPC containing the 16 inputs, and revokes the handle.

The key, payload and state remain only in the trusted server. For each path the observed final outputs must match exactly, digest by digest. The actual public facade source is fetched from the handler and hashed, and contains neither the key, HMAC implementation nor the private canary. An unauthorized RPC must return 403.

A predeclared **25 ms wait in authorizeRpc** models a per-request policy/network delay. The experiment runs with zero delay and then with 25 ms delay using the same business operation; it does not claim to model WAN/TLS or a distributed host. The browser is not involved. The 25 ms wait is part of end-to-end session *wall time*, and must not be interpreted as CPU compute time.

## Method

Reproduce with Node 22:

~~~powershell
node sims/sco-capability-http-batch.js
npx tsc -p jsconfig.sco-oracles.json
~~~

A 256-bit random server key is generated at startup; it is never printed. The original native comparator shares only that private key with the server-private source. The same deterministic 16 input strings are used in all modes and all trials. The private source uses the real createScoPrivateHandles API and mutates a private counter; the actual facade is generated by partitionScoAsyncModule, exposed with createScoHandler and operated through ordinary authenticated HTTP. A 32-byte digest is returned for each step in all paths. The source bytes and canary are checked for absence from the public HTTP-served module.

One untimed full session of each mode precedes six alternating-order paired trials for each delay level. Timed HTTP sessions include handle issue and revoke in both serial and batched variants. Native CPU in the same Node process acts as the direct comparator. For every trial, process CPU milliseconds and wall elapsed milliseconds are recorded separately, with strict >2.5x pair-exceedance counts and maximum ratios. CPU is counted for the combined local server and client Node process, capturing actual server HMAC work and JSON/RPC overhead. Positive CPU-resolution assertions are deliberately avoided; null CPU ratios indicate that at least one measurement was zero.

**Decision criterion:** any observed protected/native CPU pair strictly above 2.5x vetoes a 2.5x claim for that mode on this workload, regardless of median; unresolved CPU measurements block a pass. Wall-overhead >2.5x is separately reported as end-to-end session evidence, not recast as extra CPU. The same-account online relay and small-state extraction remain possible in other experiments; this measures costs of a coarse, real protected operation.

## Limitations

The payload's 8 MiB HMAC input is a deliberately selected original business computation present in both paths. It cannot be added to an originally cheap operation merely to satisfy the overhead budget. Results concern one process, loopback HTTP, one authenticated test principal, and one Node runtime. The example session uses a synthetic 25 ms delay, not a measured internet RTT. Benchmarks may be sensitive to runner noise and JIT; the raw paired data and actual source revision must accompany any conclusions. No general browser, concurrency, adversarial service-level, or universal compute bound follows.
