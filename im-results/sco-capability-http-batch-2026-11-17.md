# Real compiled SCO capability session: serial versus batch and simulated policy delay (17 November 2026)

**Status:** bounded full two-OS cross-platform CPU and wall session experiment, green [manual SCO oracle workflow 44150242792](https://github.com/FlareZ123/obfs/actions/runs/44150242792), immutable executable SHA b9f0b61737881cbc4e6c7f4f1f5b2ef6f0759ad8, Ubuntu and Windows Node 22 plus strict SCO JSDoc. The candidate measures the cost of authenticated, principal-scoped private state operations through an actual compiled public ESM facade and HTTP handler. Its performance claim cannot be generalized beyond the specific workload; observed zeros are never treated as a ratio.

## Question

For a stateful server-private key, capability handle and 16 real HMAC operations over an 8 MiB private business payload, compare:

1. Native in-process execution of the identical HMAC operations with the same secret key, inputs, payload and counter.
2. A public facade that mints an authenticated handle, performs 16 serial step RPCs, and revokes the handle.
3. The same public facade that mints a handle, performs one batch RPC containing the 16 inputs, and revokes the handle.

The key, payload and state remain only in the trusted server. For each path the observed final outputs must match exactly, digest by digest. The actual public facade source is fetched from the handler and hashed, and contains neither the key, HMAC implementation nor the private canary. An unauthorized RPC must return 403.

A predeclared **25 ms wait in authorizeRpc** models a per-request policy/network delay. The experiment runs with zero delay and then with 25 ms delay using the same business operation; it does not claim to model WAN/TLS or a distributed host. The browser is not involved. The 25 ms wait is part of end-to-end session *wall time*, and must not be interpreted as CPU compute time.

## Method

Reproduce with Node 22:

~~~powershell
node sims/sco-capability-http-batch.js
npx tsc -p jsconfig.sco-oracles.json
~~~

A 256-bit random server key is generated at startup; it is never printed. The original native comparator shares only that private key with the server-private source. The same deterministic 16 input strings are used in all modes and all trials. The private source uses the real createScoPrivateHandles API and mutates a private counter; the actual facade is generated by partitionScoAsyncModule, exposed with createScoHandler and operated through ordinary authenticated HTTP. A 32-byte digest is returned for each step in all paths. The source bytes and canary are checked for absence from the public HTTP-served module.

One untimed full session of each mode precedes six alternating-order paired trials for each delay level. Timed HTTP sessions include handle issue and revoke in both serial and batched variants. Native CPU in the same Node process acts as the direct comparator. For every trial, process CPU milliseconds and wall elapsed milliseconds are recorded separately, with strict >2.5x pair-exceedance counts and maximum ratios. CPU is counted for the combined local server and client Node process, capturing actual server HMAC work and JSON/RPC overhead. Positive CPU-resolution assertions are deliberately avoided; null CPU ratios indicate that at least one measurement was zero.

**Decision criterion:** any observed protected/native CPU pair strictly above 2.5x vetoes a 2.5x claim for that mode on this workload, regardless of median; unresolved CPU measurements block a pass. Wall-overhead >2.5x is separately reported as end-to-end session evidence, not recast as extra CPU. The same-account online relay and small-state extraction remain possible in other experiments; this measures costs of a coarse, real protected operation.

## Limitations

The payload's 8 MiB HMAC input is a deliberately selected original business computation present in both paths. It cannot be added to an originally cheap operation merely to satisfy the overhead budget. Results concern one process, loopback HTTP, one authenticated test principal, and one Node runtime. The example session uses a synthetic 25 ms delay, not a measured internet RTT. Benchmarks may be sensitive to runner noise and JIT; the raw paired data and actual source revision must accompany any conclusions. No general browser, concurrency, adversarial service-level, or universal compute bound follows.

## Pinned empirical results

Each operating system ran six alternating-order trials per configured request delay. All 16 ordered HMAC digests matched the original native code on every session; the 256-bit random private key and private HMAC implementation were absent from the HTTP-delivered ESM facade, and unauthenticated RPC returned 403. Neither server source nor key is printed. The workflow emitted the raw paired CPU and wall measurements and machine-readable summaries at the exact SHA above.

| Ubuntu | 0 ms | 1.22501× / 0 of 6 | 1.04699× / 0 of 6 | 1.31441× / 0 of 6 | 1.11713× / 0 of 6 |
| Ubuntu | 25 ms | 7.46416× / **6 of 6** | 2.08806× / 0 of 6 | 1.31495× / 0 of 6 | 1.08646× / 0 of 6 |

**Combined 24 session pairs for each strategy:** no process CPU pair exceeded the 2.5× threshold for either serial or batch; the *wall time* of the 25-ms serial-RPC sessions exceeded 2.5× on all 12 relevant pairs. Batch stayed under 2.5× wall time for all 24 pairs, with a maximum of 2.23887× Windows at 25 ms. No process CPU pair was unresolved. The Windows serial CPU max of 2.39744× is close to the strict threshold; future different workload/runner samples may cross it. Six observations per cell do not establish a population tail or universal bound.

The 25-ms delay executes asynchronously in authorizeRpc for **each** authenticated request. Native work pays no such delay. Serial handles require 18 RPCs (issue, 16 steps, revoke); batched handles require 3 (issue, one 16-item batch, revoke). The CPU counter measures the whole single Node process including the server and client, whereas the wall counter additionally charges all asynchronous policy waits and local HTTP scheduling. These two quantities are **distinct** and neither establishes execution resistance against a same-principal online relay.

## Engineering selection for this application

For this 8-MiB HMAC and 16-operation stateful service, the observed real-HTTP batched version had the lower runtime overhead and preserved full output semantics. The serial version incurred substantially larger end-to-end wall cost when policy/network delay was injected, even though server CPU remained within the sampled 2.5× budget.

The batch operation consumes all 16 inputs and returns all 16 digests. It is a different public RPC granularity from 16 separate calls, so application migration has to preserve externally observable ordering, error handling and partial-progress semantics; the tested all-success sequence does not prove that such migration is legal for arbitrary applications. Offline source withholding is enabled by the trusted SCO boundary, while online same-account functional relay remains possible. Future test runs with actual remote RTT/TLS, variable session sizes, concurrency and browser work are necessary before any production target claim.

## Follow-up candidate: guarded prefix-preserving HMAC batch (predeclared)

After the pinned 6-trial serial/batch result, the implementation gained a separate real-HMAC guarded batch operation that validates each element **inside the trusted server** immediately before hashing, commits only a valid prefix and returns an explicit first-invalid position with prior digest outputs. Its bounded HTTP envelope policy allows a fixed-length array of strings for this method, and the private operation validates each string against the exact original input pattern before any corresponding HMAC/state mutation. A deterministic bad third input must result in two committed digest outputs; continuing with a fourth valid input must produce the same HMAC as the original third step. This is an independent semantic guard for the selected single-session contract, with different public error signaling from the old serial RPC contract.

The new cost experiment adds **guarded-rpc** as a fourth method and rotates all four modes over **eight** trials per delay level, two complete rotations per latency. It keeps the original 16 × 8 MiB HMAC business work identical for native, serial RPC, prevalidated batch and guarded-prefix batch, and preserves the 0 ms versus 25 ms per-request delay arms. The strict decision rule remains: any observed native/protected CPU ratio over 2.5x is a sampled veto; any unresolved native/protected CPU pair cannot pass. Separately report wall-time exceedances, including the guard's effect on full end-to-end sessions. No assumption is made that its cost must match the older prevalidated path, nor that a guarded batch automatically solves arbitrary application exception/await semantics.

**Strict paired CPU verdict:** The serial method had **1/32 sampled CPU pairs over 2.5×**, on Windows with 25 ms simulated policy delay. This is a sampled veto for the serial version on this workload. Both prevalidated and guarded batch methods had **0/32 sampled CPU violations**, with guarded maximum CPU ratio 1.20513× across the recorded runs. **Strict paired wall verdict:** serial at 25ms had 16/16 wall violations; both batch methods had 0/32 wall violations across all delay arms. The maximum guarded 25ms wall ratio was 2.23502×, on Windows.

The data justify a **conditional guarded-batch preference** for this exact coarse HMAC workload: it preserves the explicitly defined first-error-prefix/continuation contract and fits the observed 2.5× CPU pairs while also reducing end-to-end synthetic-delay wall overhead. They do not prove a general JavaScript semantics-preserving batch rewriter, nor a universal CPU bound. The Windows serial CPU violation in this larger sample supersedes any blanket interpretation of the older 6-trial serial result as a green compute guarantee.
