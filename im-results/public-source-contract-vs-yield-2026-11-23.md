| Category | Failing test cases on each OS | Direct observable / reason to reconsider the expected transform |

| Private local reader helpers under an exported source-stable wrapper | **2**: `function-declaration-reader-proof` (cross-module case and source-only normalizer fixture) | The *exported* `calculate` function calls private `read` helpers without directly spelling the private field. These are classifications of visible source structure and the stated attacker model, not a theorem ruling out every possible compiler architecture. In particular, an indirection can preserve a public wrapper's exact source while changing private internal code under an appropriate non-exposure proof. Conversely, patching only `fn.toString` is not a complete defense, because a host can invoke the intrinsic `Function.prototype.toString.call(fn)` or instrument the runtime before load.

## Independent native-source witness

`test/agent9-public-source-contract-witness.test.js` evaluates four representative CommonJS source graphs (primitive Blob owner, private tuple, Symbol-key worker, private factory). It makes a **controlled direct key rename** both in the literal owner and its exported callable body. For selected inputs, the numeric outputs remain equal, but the unmodified native `Function.prototype.toString.call` returns distinguishable text and reveals the original/renamed field tokens. A fifth witness exports a state record: `Object.values` remains equal while `Object.keys` and JSON differ. These are direct host-observables; source-only tests for transformed runtime output that ignore them are incomplete for this threat model.

The witness focuses on *direct body rewrites*, not impossibility of source-stable indirection. The separate class-method proof in `im-results/private-class-direct-method-proof-2026-11-23.md` does **not** rewrite a publicly exported function body: it admits only private, nonescaping class methods, directly called through a private instance, with original function-source and reflection refusals still enforced.

The [independent public-source witness run 45269544429](https://github.com/FlareZ123/obfs/actions/runs/45269544429) completed successfully on Ubuntu and Windows with Node 22 and strict project/external JSDoc checks at exactly `0a64cd0cb9cd3ac961b9bf8a49d1f74aefe160ee`. It independently verifies four source-spelling distinctions and one exported-record key/JSON distinction. That success does not make the full suite green, nor show that more elaborate source-stable internal rewrites are impossible.

The earlier full test runs 45266675540 and 45269716316 **predate this update** and correctly report 15 failures in their exact source pins. A new full run [45271840246](https://github.com/FlareZ123/obfs/actions/runs/45271840246) on the post-fix branch has been dispatched; its actual outcome, rather than subtracting two from old results, is needed to characterize remaining integration failures. The 13 other source-visible/bind/public-owner assertions have not been relaxed; their positive-yield demands remain unresolved under the stated hostile host model.

## Recommended population action

Before using the full-suite red count to justify more permissive cross-file/property passes, explicitly divide positive-yield tests into: **(a)** proven-source-private transform candidates, **(b)** API/source-visible contracts that must decline or be re-architected, **(c)** hostile runtime interception demonstrations, and **(d)** true native/generated output mismatches. Treat (a) as an implementation agenda, (b) as API policy, (c) as security counterevidence, and (d) as correctness bugs. Do not equate more transformed properties with stronger protection without a source-only attacker and actual runtime evidence.
