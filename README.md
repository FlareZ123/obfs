# Obfs research baseline

This repository is an experimental, conservative JavaScript obfuscator targeting Node.js 22+ and modern browsers. It offers three operational modes. The current version is a reproducible starting implementation; its security and performance guarantees are limited to the conditions described here.

## Install and verify

Install dependencies with `npm install`, then run `npm test`, `npm run typecheck`, and `npm run benchmark` from the repository root. All code is CommonJS with JSDoc annotations. Optional `npm run test:browser` runs a real Chromium headless integration test when Chromium is installed (`CHROMIUM_BIN` overrides the binary location). The parser dependency is Acorn 8.x, and the JSDoc static checker uses TypeScript with Node.js declarations as development dependencies. The default compiler avoids source-code `eval`. Experimental, explicitly opted-in register VMs execute bounded custom binary-operator tapes; those interpreters are publicly recoverable and require workload-specific performance assessment.

## Entrypoints

`bin/coo.js` transforms a directory into static browser files, preserving relative ESM import paths and non-JavaScript assets. Example:

```powershell
node bin/coo.js --root .\examples\browser --entry index.mjs --out .\dist-browser --closed-world
```

`bin/sno.js` produces a preobfuscated Node CommonJS directory plus `sno-entry.cjs`. It verifies the output files' SHA-256 digests at startup and then loads the actual entry through `require`. Example:

```powershell
node bin/sno.js --root .\examples\server --entry index.cjs --out .\dist-server
node .\dist-server\sno-entry.cjs
```

**Experimental multi-statement native CFG:** The opt-in
[`flattenStatementFlow`](src/statement-flow.js) backend accepts restricted
synchronous ESM/CommonJS function declarations with multi-statement if/else
branches. It emits native JavaScript using randomized switch-dispatch states;
whole native loops, switches, labels, and exception handling statements may
remain atomic. The `--statement-flow relative-file:functionName` CLI selector
is supported for COO and SNO. Unsupported lexical declarations, direct eval,
recognized function-source observers and unproved control flow decline rather
than silently changing behavior. See the [actual before-and-after example](examples/statement-flow/README.md).

A [pinned two-platform profile and browser gate](https://github.com/FlareZ123/obfs/actions/runs/43801792896)
recorded light-callback runtime ratios of **1.408× Ubuntu / 1.231× Windows**
and integrated SHA-256 callback ratios of **0.993× / 1.017×**, with
8,218 real Chromium differential evaluations passing. Those observations
come from a limited sample at a specific commit. A [subsequent tight
CPU-loop gate](https://github.com/FlareZ123/obfs/actions/runs/43804836672)
measured **2.781× Windows slowdown**, violating the required 2.5× ceiling
for that workload. Keep this backend experimental and do not deploy it
without representative performance profiling. A [seedless static attacker](sims/statement-flow-recover.js)
recovered 16/16 randomized native control-flow layouts; the technique
therefore raises structural inspection effort only, without demonstrated
source secrecy or hostile-runtime integrity.

The newer, **separately opt-in** `--statement-flow-compact` CLI flag (or
programmatic `experimentalStatementFlowCompact:true`) fuses uniquely reached
straight-line, branch and terminal CFG states into fewer native cases.
At the initial pinned two-platform [hot-path gate 43996692856](https://github.com/FlareZ123/obfs/actions/runs/43996692856),
a dense arithmetic fixture fell from 44 to 7 dispatch cases and its
runtime/native ratio from **4.97× to 1.33× (Ubuntu)** and **7.77× to
1.72× (Windows)**. A [three-module stateful
challenge](https://github.com/FlareZ123/obfs/actions/runs/43997435553)
confirmed 96/96 equivalent native/ordinary/compacted/seedlessly reconstructed
outputs on each platform, with 42% of source bytes in the selected module.
However, a [fresh-compilation profile](https://github.com/FlareZ123/obfs/actions/runs/43997119211)
measured **3.24× Ubuntu and 2.81× Windows** at 1,000 calls, exceeding the
2.5× budget. Seedless static program recovery remains successful, and
runtime/tamper secrecy is still unproved. Evaluate cold and warm workload
budgets separately before selecting this backend. See the
[dated, pinned report](im-results/statement-flow-compact-2026-11-17.md).

**SCO verified-account private-output binding:** An [executable two-account adversarial relay](sims/sco-audience-bound-relay.js) keeps the HMAC key and algorithm on a trusted server and binds results to a verified account identity. In a [pinned Linux/Windows run](https://github.com/FlareZ123/obfs/actions/runs/43835306239), an attacker holding only Account A's bearer replicated **32/32** A outputs but **0/32** B-account outputs across held-out challenges, while eight parallel A/B context checks passed. The A same-account relay still succeeds, and stolen or cooperatively forwarded B credentials restore B access; see the [scoped threat and runtime report](im-results/sco-audience-bound-relay-2026-11-16.md). This is server-side account authorization, not universal client anti-cloning, and the selected localhost heavy-workload timing is not a general 2.5× bound.

**Runnable advanced SCO example:** [`examples/sco-private/`](examples/sco-private/README.md) includes an original keyed ESM implementation, the **actual generated client RPC facade** saved as a before-and-after artifact, a deterministic reproduction/check script, and an authenticated localhost HTTP server. A live differential regression checks the generated client against the server-resident original. This demonstrates a genuine server-only source and key separation, with the runtime and oracle limitations documented in the example. Existing COO/SNO transformations cannot provide the same trusted-server confidentiality under their full-control threat models.

**Multi-module SCO example:** [`examples/sco-graph/`](examples/sco-graph/README.md)
contains three cooperating private ES modules, two exact compiler-generated

passed at source `b8ba88d3a337cd3a03ed588a0b34deeedd65cd3d`; see the
[publication safeguards report](im-results/sco-graph-publication-manifest-2026-11-16.md).
The previously measured 12,000-round HMAC operation met the 2.5× runtime
target on two localhost runners, with incomplete performance/security
coverage documented in
[`im-results/sco-graph-partition-2026-11-15.md`](im-results/sco-graph-partition-2026-11-15.md).
The composed `createScoGraphHandler` now requires the **original in-process
graph manifest** returned by `partitionScoAsyncGraph`, detects changes made
after partitioning, and publishes from a private compiler-owned snapshot.
This prevents accidental replacement of a reviewed facade with a byte-modified
private source under the same public filename. A [real HTTP source-leak

passed a [targeted Linux/Windows Node 22 and JSDoc gate](https://github.com/FlareZ123/obfs/actions/runs/43917301822).
Serialized or shallow-copied graph objects are rejected by the composed helper;
regenerate the graph on the trusted serving process. Explicit bare
`createScoHandler` calls remain a separate publication contract. This is a
deployment safety check, not resistance to a compromised server.
The graph additionally returns path-specific SHA-256 `privateSourceDigests`
for every original module. The [runnable example](examples/sco-graph/server.cjs)

This requires trusted, stable server files through module loading; it is
a startup consistency check with no proof against concurrent replacement.
The closed-graph scanner now refuses directly visible `eval` and `Function`
dynamic-code factories (including simple aliases) because [actual Node ESM
execution can import undeclared modules through those constructs](im-results/sco-graph-dynamic-evaluator-closure-2026-11-16.md).
The [Linux/Windows targeted graph gate](https://github.com/FlareZ123/obfs/actions/runs/43922733144)
passed native counterexample and refusal tests plus strict JSDoc.
Derived constructors and opaque runtime loaders remain outside the syntactic
closure proof; independently review the server's reachable modules.



**SCO authorized online-relay limit:** Keeping a random HMAC key and private ESM implementation server-side protects them from a source-only client; it does not prevent an attacker who has a legitimate unlimited-query account from using that same original server as an oracle for downstream users. A real attacker-operated loopback proxy reproduced **32/32 previously unqueried high-entropy outputs** without extracting the key, despite direct unauthenticated requests returning 403. Its heavy 8 MiB HMAC workload measured **1.304× Ubuntu / 1.345× Windows** end-to-end through two HTTP hops, measured only on local loopback without realistic RTT or TLS. The independently reproducible [server-private online relay attacker](sims/sco-relay-attack.js) and [SCO large-domain results](im-results/sco-large-domain-prf-2026-11-15.md) distinguish actual server-side source secrecy from functional anti-cloning under an authorized online relay.

`bin/sco.js` starts an HTTP server with the obfuscator library loaded server-side. It encodes served JavaScript afresh on each request, under `/obfs/`. Example:

```powershell
node bin/sco.js --root .\examples\browser --entry index.mjs --port 8080 --closed-world
```

SCO now serves only the named browser entry and its static ESM imports/reexports by default. Unreferenced JavaScript under the source root is **private by default**, even if it has a `.js`, `.mjs`, or `.cjs` extension. Use repeatable `--client relative/file.js` for independent browser scripts, **all** runtime `import()` dependencies (including literal specifiers), workers, and other runtime-loaded JavaScript files. Use `--asset relative/file.css` to explicitly serve non-JavaScript assets. The source root may contain server-only implementations or configuration; do not put those files in `--client` or import them from the client entry. The programmatic SCO handler continues to serve exactly the files provided by its caller. For source-private deployments, an opt-in `publicPaths:[...]` on `createScoHandler` now enforces an exact, independently reviewed positive allowlist of every distributed JavaScript file and asset, refusing unexpected source files before opening the route. It complements private-graph manifests, without providing request authentication; see [SCO source authorization](docs/SCO_AUTHORIZATION.md) and [the real HTTP publication regression](test/sco-public-file-allowlist.test.js).

**SCO origin authorization:** `createScoHandler({allowedHosts:[...]})` compares the incoming HTTP `Host` header. Attackers using ordinary HTTP clients can set this header to a permitted name while contacting the same server; the filter is therefore a routing convenience and **does not authorize source reads or private RPC**. Integrators must implement trusted `authorizeRead`, `authorizeRpc`, and `authorizeOperation` policies on the server. The regression `test/sco-host-header-spoof.test.js` demonstrates both the forged-Host read and independent policy denial. The test session header is a fixture, not production authentication. Dynamic imports are not implicitly authorized even when their specifier is a literal: a dormant or unreachable import must not accidentally publish a server-only file. An import() or script tag referring to an unlisted file receives HTTP 404 until the integrator explicitly declares it.

**COO closed-graph hostname checks:** with `obfuscateFiles(...,{mode:'coo',closedWorld:true,allowedHosts:['allowed.example']})`, a fully declared static ESM dependency group now receives an independent hostname guard in **each** emitted module body. This permits static import/reexport graphs whose dependencies are all supplied, while missing, opaque or externally resolved imports retain conservative refusal. An [exact generated three-module before/after](examples/closed-graph-host/README.md) transforms 2/2 private fields and guards every evaluated module body. The [intermediate threat and performance study](im-results/closed-graph-host-2026-11-16.md) includes native Node and real Chromium allowed/denied evaluation, a successful public-only guard-removal attack, and cross-platform short/sustained performance measurements near 1×. A [real Chromium import-map redirection counterexample](im-results/closed-graph-importmap-bypass-2026-11-16.md) confirms that browser import maps and custom resolution invalidate the declared-graph premise. Full-control attackers can bypass every client-side guard; for actual authorization, use a trusted server.

For browser module graphs that use `.js` rather than `.mjs` extensions, add `--js-module` to the COO or SCO CLI invocation. This explicitly treats every input `.js` file as an ES module; do not enable it for mixed classic-script or CommonJS `.js` trees. The flag is rejected in SNO. `.mjs` is recognized as a module without the flag. The SNO CLI detects explicit nested Node `package.json` module scopes for `.js` dependencies, allowing a CommonJS entry to dynamically import ESM modules.

The programmatic API is `require('./src')`, exporting `virtualizeExpressionGraphs`, `lowerWasmI32Functions`, `obfuscateFiles`, `createSnoLauncher`, `createScoHandler`, `createScoRpcClientSource`, `createScoBatchMethod`, `preflightScoBatchState`, `partitionScoAsyncModule`, `bindScoModuleExports`, `partitionScoAsyncGraph`, and `bindScoGraphExports`. A file is `{path,code,sourceType?}`. Modes are `coo`, `sco`, `sno`; supported source types are `script`, `module`, `commonjs`, `asset`.

## Implemented transformations

- Experimental private Symbol-key property representation via COO/SNO `--symbol-keys` or programmatic `experimentalSymbolKeys:true`. It admits only local privately owned objects under the same conservative proof as normal property renaming, generates unregistered `Symbol()` keys, and updates every proved member/destructuring reference. [Real before/after](examples/symbol-keys/README.md), [independent seedless attacker](sims/symbol-key-static-recover.js), and [cross-platform hot/cold evidence](im-results/symbol-key-backend-cold-attack-2026-11-15.md) show that this is **functionally reconstructable from public output**. The 250k-call hot kernel was near 1×, but several measured fresh-compilation cases exceeded the strict **2.5×** compute budget, up to 22.5×. It remains off by default, and is unsuitable for unprofiled short-running workloads.
- One-time Unicode-preserving XOR string decoding. The decoder's array is initialized once per file, with per-build randomness. Eager string encoding is **off by default for COO and SCO client files** and enabled for SNO; programmatic COO/SCO callers may explicitly request `strings:true`, accepting the measured cold-start tradeoff. String literals inside direct loop bodies, import specifiers, `require` arguments, directive prologues, and noncomputed property keys remain intact.
- Conservative AST-based private property renaming. It tracks immutable aliases, passes to local direct-call functions, identity returns, and simple statically keyed object destructuring. Immutable local arrow/function-expression readers of a proven own field are also tracked, including nested direct identity forwarding into reader calls. A statically keyed object-pattern declaration or discarded assignment may likewise destructure a directly proven identity return; unknown keys, rest properties, and escaped assignment values remain unproved. See the [generated reader before/after](examples/local-reader/README.md), [generated destructuring before/after](examples/forwarded-destructuring/README.md), and [pinned reader](im-results/local-reader-interprocedural-2026-11-15.md) and [destructuring evidence](im-results/forwarded-destructuring-2026-11-15.md). Own-property initializers may contain primitive literals or recursively literal-only arrays. A private top-level, single-use zero-argument function/immutable expression factory directly returning an inert object literal may also initialize the owned object; its own keys are renamed only after the same alias/use proof succeeds. The narrow case has a [generated one-file CommonJS before/after](examples/factory-ownership/README.md), [generated two-file closed-world ESM before/after](examples/factory-cross-file/README.md), and [pinned cross-platform/attacker evidence](im-results/private-factory-ownership-2026-11-15.md). It rejects aliases outside their lexical scopes and unknown method assignments that could inspect object keys. It refuses transformation when the alias escapes, encounters dynamic computed access, reflection, duplicate bindings, `eval`, or `with`. Known function-source observations such as `.toString()`, `String(fn)`, and statically keyed `Reflect.get` or descriptor retrieval of a toString method also suspend the relevant transformations.
- Opt-in `--closed-world` analysis of direct ESM named exports and imports. It renames own keys jointly across provided modules when the proof covers every importer in the declared module set. Direct calls to imported pure identity functions (`export function f(x){return x}`) and immutable expression-arrow identities (`export const f=x=>x`) can safely forward an object's ownership through tracked const aliases. The analysis also recognizes narrow exported reader helpers such as `export function get(x){return x.secretField}` and immutable exported arrow/function expressions with a single direct property return. It rewrites the helper's field access only after verifying that every importer call passes the same proven object at the correct argument position. Reader return values are never treated as aliases of the owner. A directly passed, proven identity-return call can also carry the owner into an imported reader. The proof declines impure, async, mutated, opaque or escaping wrappers. Dynamic imports, namespace imports, reexports, exported aliases, noncanonical URL/absolute/package import specifiers, unresolved relative files and mixed executable source groups cause refusal. Node ESM alternate module loaders and runtime code-generation constructs also disable this proof. CSS, raster-image and font assets may accompany an ESM graph when the integrator guarantees they cannot execute as JavaScript. HTML, SVG and other unknown assets prevent cross-file renaming. Turning this flag on asserts that no outside module accesses exported object shapes.
- Experimental opt-in nested-expression register VM through `experimentalExpressionVm` or the COO/SNO `--expression-vm relative-file:functionName` CLI flag. The compiler accepts strict one-argument, return-only arithmetic/bitwise expression trees, emits a seed-diversified multi-register instruction tape, and preserves the native operators' evaluation order. It extends the older linear-chain VM to branched binary expression trees, with a [real generated before/after and reproducible builder](examples/expression-vm/README.md). An [independent seedless attacker](sims/expression-vm-static-recover.js) reconstructs the full original sample expression from the public VM, so this is a research-only structure transform and has no proven full-control security barrier. Dense-call overhead can substantially exceed 2.5x; apply only after real workload measurement. See [intermediate evidence](im-results/expression-vm-graph-2026-11-15.md).
- Experimental **polyvariant native affine** integer-path obfuscation through programmatic `experimentalPolyvariantAffine` with `experimentalPolyvariantCount` set to 2/4/8, or COO/SNO `--polyvariant-affine relative-file:functionName --polyvariant-count 2`. It partitions the original ToInt32 input into disjoint low-bit classes, emits an independently seeded native-affine case for each class, and avoids a fully general fallback. The [actual checked-in before-and-after](examples/polyvariant-affine/README.md) is compiler-generated and reproducible. Its independent [offline AST attacker](sims/polyvariant-affine-static-recover.js) recovers the equivalent integer computation, demonstrating that syntax diversification alone is insufficient against full source access. On the tested Linux/Windows Node22 hot workloads, sampled 2/4/8-path ratios were within the 2.5× threshold but do not certify cold-start, arbitrary programs or host tamper resistance. [Pinned intermediate report](im-results/polyvariant-affine-2026-11-16.md). A [frozen three-module COO application](examples/polyvariant-app/README.md) selects 12.6% of its original source for this transform. Its [independent offline clone](sims/polyvariant-app-functional-clone.js) runs the delivered application outside the original environment; all 96 held-out stateful scenarios preserve host callbacks and reflection, and whole-app 1/50/1000/10000-event sessions measured 1.15–1.47× across Windows/Ubuntu. [Comparative attacker-cost evidence](im-results/polyvariant-app-attack-cost-2026-11-16.md). A later [three-way independent attacker and browser benchmark](im-results/polyvariant-app-three-way-cost-2026-11-17.md) proves 3/3 selected functions reconstructable from distributed source while the 10,000-event app actually invokes them 439,020 times. The rebuilt full ESM graph is 2,362 bytes versus 7,518 delivered bytes, preserves full state/host output on both Node and real Chromium, and reaches original-like runtime. A historical Chromium virtual-time nine-round sample reported 4.3/9.9/4.3 ms (original/delivered/rebuilt) on already-loaded code; that older clock requires separate validation for CPU timing. - Restricted lexical identifier renaming using unique-binding AST proofs; variable names change while external API names, object literal keys, and dynamic-scope constructs remain unchanged.
- Optional browser hostname check. It is a convenience restriction against accidental reuse, and **cannot withstand a client that can modify code**. Host-locked ESM files with static imports or reexports are refused, because those dependencies would execute before the guard. Use server-side authorization to protect such graphs.
- SNO local integrity check against incidental file corruption. Since the modeled adversary controls the server's files and runtime, this cannot establish a cryptographic trust boundary.

**Source disclosure:** COO, SCO, and SNO refuse `.map` sidecar assets, source-map JSON payloads regardless of filename, and real JavaScript `sourceMappingURL` directives, including inline `data:` maps. They also refuse CSS `sourceMappingURL` block comments in standalone `.css` files and in HTML/SVG `<style>` elements; these annotations can otherwise publish the original source inside a base64 map. SVG animation `values` URL sequences are checked state by state. They also refuse executable JavaScript and transpiler input files such as `.js`, `.jsx`, `.ts`, `.tsx`, and `.vue` when supplied as opaque assets. A standards-compliant HTML preflight (`parse5@7.3.0`) refuses static HTML assets containing inline scripts, event handlers, `srcdoc`, or embedded executable URLs while preserving files that reference external transformed scripts. An XML-conformant SVG preflight (`saxes@6.0.0`) similarly refuses embedded SVG scripts, event handlers, executable links and malformed or ambiguous SVG source while preserving static artwork. Remove original-source sidecars and source-map references before obfuscation. A source map can contain the original program in `sourcesContent`; see `docs/SECURITY.md` for the policy, compatibility consequences, and remaining asset-disclosure gaps.

## Important limitations

The experimental `--closed-world` property proof relies on an explicit deployment/environment contract beyond the declared ESM import graph. Source-visible intrinsic assignments, descriptor aliases, opaque host callbacks and Proxy traps have all produced real native-versus-generated key-spelling regressions in the regression matrix. Read the [property proof envelope and red/green acceptance lanes](docs/CLOSED_WORLD_PROPERTY_PROOF.md) before treating any cross-file property rewrite as compatible with a target host. A correct refusal preserves semantics but adds no protected-work coverage.


The nested-expression VM is intentionally disabled by default because its visible byte tape is statically recoverable and its selected-function hot-path cost has no universal 2.5x bound.

This prototype does not implement general closure or arbitrary cross-file property-flow reconstruction, encrypted remote execution, production general-purpose Wasm lowering, general-purpose VM virtualization, general lexical identifier mangling, or runtime anti-instrumentation. A restricted opt-in experimental register VM is available in [src/register-vm.js](src/register-vm.js), with a [real generated example](examples/register-vm/README.md) and a [seedless source-only reconstruction test](test/register-vm-static-recovery.test.js). It has no validated strong security boundary. Dynamic tooling, modified runtimes, and complete client visibility can extract code and bypass local checks. Direct source-introspection checks remain syntactic; implicit coercion, dynamic builtin aliases, and external observers can still expose transformed source. Bounded ECMA-402 guards now account for selected `Intl` constructors, methods and callback escapes, along with native Number/BigInt/Date/String locale-option coercions and arrays containing function values. A [pinned pre-fix red versus patched green comparison](im-results/intl-native-source-observation-2026-11-16.md) reproduces actual behavior differences in these supported paths. The guard deliberately preserves original source and sacrifices renaming coverage where the input's primitive nature cannot be proven; opaque wrappers and indirect calls remain limitations. The [six-module source-refusal yield ledger](im-results/application-challenge-refusal-yield-2026-11-16.md) measures 0/2 private-field renames in a source-observing original and 2/2 in a separately modified source-observer-free application, each with 84/84 native-versus-emitted outputs equal. The latter changes the input program intentionally, and its file changes do not prove increased attacker cost. It cannot guarantee 2.5x speed for arbitrary inputs. The benchmark is a limited sample, not a performance proof. Breaking API contracts through obfuscation is a correctness failure; ambiguous cases intentionally remain unchanged.

SCO's per-request source variation also declines across the entire published file group when a known source observer appears in any member, because another module may inspect an exported function through \`Function.prototype.toString\`; the reproduced compatibility regression and conservative repair are documented in \`im-results/sco-interfile-source-observation-2026-11-15.md\`. This is a syntactic safety guard, not a proof against arbitrary source introspection.\n\nFor SCO, the server can retain secrets that are never sent to the client. A programmatic `createScoHandler` accepts `remoteMethods`, `authorizeRpc`, and `maxRpcBytes` to keep sensitive computation on a trusted server via authenticated JSON POST `/obfs/rpc`. `createScoRpcClientSource` generates a same-origin browser ESM facade for named RPC methods, keeping their implementations server-side; see `docs/SCO_AUTHORIZATION.md` for usage and limits. Optional `createScoBatchMethod` groups explicitly named operations into one bounded authenticated RPC request, executing them sequentially to reduce transport overhead. Its one-time authorization preflight is a snapshot: state-dependent policies that change during a batch need a pure transition model such as `preflightScoBatchState` plus application-managed isolation, or must refuse those batches. The helper itself does not create a transaction. For dedicated private ESM modules with exported async functions, `partitionScoAsyncModule` emits public RPC proxies while `bindScoModuleExports` keeps the original functions server-resident. This has explicit JSON-compatible operation semantics and can optionally retain private top-level initialization and expose batched calls; see `docs/SCO_PARTITION.md`. See `im-results/sco-rpc-cost-2026-11-15.md` for measured budget tradeoffs and remaining failures. The reusable `createScoKeyedIsolation` helper can serialize authenticated SCO authorization and execution per principal with independent account queues. Its opt-in `{maxPendingPerPrincipal:N,maxPendingTotal:M}` bounds active and queued calls per verified identity and across the current server process, returning HTTP 429 on pre-execution admission denial; these caps contain queue growth without stopping authorized serial relays. See [`SCO authorization`](docs/SCO_AUTHORIZATION.md) and [the pinned queue-limit regression](im-results/sco-keyed-capacity-2026-11-16.md). It cannot protect shared state outside the process or prevent authorized client relaying. Cross-file property proof extensions and reproduced soundness limits are documented in `im-results/cross-file-reader-proof-2026-11-15.md` and `im-results/ambient-intrinsic-aliases-2026-11-15.md`. This API does not automatically rewrite ordinary JS into remote calls. Browser-delivered JS remains extractable. The `Host` header may be forged by HTTP clients; enforce real authorization on the server for privileged operations.


The opt-in `partitionScoSelectedAsyncExports` API also supports deliberately mixed modules: approved local public exports remain native JavaScript, while chosen async exports become authenticated private RPC calls. It retains directly called, unexported non-generator helpers (including async functions) server-side and can explicitly keep reviewed local helpers in the client via `publicHelperNames`; cross-boundary references and private helper identity escapes are conservatively refused. A [generated private/public helper graph](examples/sco-public-helpers/README.md) demonstrates the separate source locations, exact emitted bytes, and tests. [The generated mixed-module source pair](examples/sco-selective/README.md) and [pinned independent relay/performance challenge](im-results/sco-selective-2026-11-15.md) measure preserved ESM behavior and 1.12–1.20× warm localhost whole-session cost on a selected workload. An authorized third party relays all 20 held-out outputs through a separate proxy, so this architecture withholds implementation source under SCO trust assumptions but does not prohibit online functional cloning. The [server-private primitive-constant extension](examples/sco-private-const/README.md) permits literal module keys in selected async exports. Its [pinned adversarial and browser measurement](im-results/sco-private-primitive-constants-2026-11-15.md) found direct-client thin HMAC ratios of **23.87× Ubuntu and 22.54× Windows**, versus **1.31× and 1.23×** in a 100,000-local-operation session. Both tested platforms passed native, cross-realm source-withholding and authorization checks; only the amortized session satisfied the 2.5× bound.


**Selective SCO server-private imports (experimental, 2026-11-16):** A deliberately mixed ESM module can keep named Node builtins on the server with `allowServerImports:true` and explicitly listed relative `.mjs` dependencies with `privateModuleImports:['./private/engine.mjs']`. The compiler withholds those dependency bodies from the generated browser facade, refuses retained public use of their imported bindings, and attaches direct `privateModulePaths` metadata. With the optional `privateModuleSources:[{path,code},...]` static source graph, the compiler additionally enumerates transitive private ESM imports/reexports, refuses incomplete or ambiguous graphs and recognized cross-realm/runtime-loader hazards, and adds every discovered path to the manifest. `createScoHandler` rejects any public file group containing such a private path. The server-side `verifyScoPrivateSourceDigests(partition,absoluteRoot)` can check build-time source commitments against actual deployed files before the original ESM import; it adds no client request-time overhead. The [builtin HMAC before/after](examples/sco-static-imports/README.md) and [two-file private ESM graph before/after](examples/sco-private-graph/README.md) are genuine generated source examples. A reproducible [authorized online attacker](sims/sco-private-graph-relay.js) nevertheless relayed **30/30** held-out private outputs without seeing the source or key. A selected 12,000-round HMAC private call measured **1.177× Linux and 1.153× Windows** warm authenticated local RPC, and the two-module graph measured **1.188× and 1.144×** on the same class of workload. [Node import measurements](im-results/sco-private-imports-2026-11-16.md) and [graph/attacker tradeoff](im-results/sco-private-graph-relay-2026-11-16.md) include the limitations. Uninspected imported modules can have cross-realm ambient effects; the [private graph admission regression](test/sco-private-graph-admission-boundary.test.js) now verifies that the compiler refuses a known unsafe public intrinsic-state observer. The [direct-only HTTP 200 transitive-source disclosure counterexample, audited closure and SHA-256 preflight](im-results/sco-private-transitive-source-audit-2026-11-16.md) are independently reproducible and [fully validated on Linux and Windows](https://github.com/FlareZ123/obfs/actions/runs/43800013349). An [independent attacker child without the server HMAC key](test/sco-private-transitive-relay.test.js) still relayed **20/20 held-out audited three-file outputs** through its legitimate session with warm local clone/native medians of **1.404× Linux / 1.392× Windows** in [pinned CI 43801195059](https://github.com/FlareZ123/obfs/actions/runs/43801195059). These checks remain bounded and cannot prove general cross-realm equivalence. Only reviewable server-owned dependencies with tested public/private contracts should be selected. These experiments do not imply universal semantic preservation, prevention of authorized relaying, or compliance with 2.5× under network RTT and cheap calls.



**Composed selective SCO graph (experimental, 2026-11-17):** The new `partitionScoSelectedGraph` and `createScoSelectedGraphHandler` combine several independent mixed public/private ESM modules into one compiler-owned publication and server method registry. Shared audited private ESM dependencies stay unpublished. The composition rejects conflicting paths and source digests, uncommitted private imports, method collisions, and caller modifications to emitted facades. The [bounded API and deployment contract](docs/SCO_SELECTED_GRAPH.md) and [intermediate raw-data report](im-results/sco-selected-graph-composition-2026-11-17.md) include real Linux/Windows HTTP checks, two-module Chromium parity, and a public-only legitimate attacker relaying **64/64** held-out HMAC results. On one localhost two-module workload the warm heavy-call ratios were **1.09–1.12×** at eight million iterations; the one-iteration ratios reached **357–436×**, so universal 2.5× compliance is disproved for the tested thin-call case. A later conservative check refuses recognized private imported modules with mutable top-level state because a singleton server module can otherwise mix separate client sessions. Those newer state tests require a separate pinned green workflow. This is bounded source withholding under a trusted SCO server, with authorized online relaying still possible.

**Selected-SCO cross-host behavioral boundary (2026-11-16):** Source migration from a client JavaScript realm to a server changes observable local-time and default-Intl results, locale-sensitive primitive formatting, `Math.random` sequence state, and host crypto/performance clocks. `partitionScoSelectedAsyncExports` now conservatively refuses recognized selected-private occurrences, aliases, extracted methods and Date-instance escapes while retaining proved UTC/deterministic controls and operations that stay in the client. The [timezone](im-results/sco-host-configuration-boundary-2026-11-16.md), [implicit locale](im-results/sco-implicit-locale-methods-2026-11-16.md) and [entropy/clock](im-results/sco-random-clock-realm-2026-11-16.md) reports contain bounded counterexamples and pinned Linux/Windows validation. The [direct/transitive private ESM admission suite](test/sco-private-host-effect-closure.test.js) checks **24 expected refusals and 10 safe admissions**, with [reproduction notes](im-results/sco-transitive-host-effects-2026-11-16.md). `privateModuleImports` without `privateModuleSources` lacks child-source audit evidence, and complex higher-order host effects, different ICU datasets, network latency and unrestricted JavaScript semantics remain unproved. These are compiler compatibility guards, not runtime anti-analysis or a universal 2.5× guarantee.

## Independent external compatibility evaluation

The manually dispatched [JsDeObsBench evaluation workflow](.github/workflows/manual-jsdeobsbench.yml) transforms a pinned public corpus of 1,301 unrelated CodeNet JavaScript programs, verifies the upstream Git blob fingerprint, and compares native and transformed outputs under matching inputs in a CPU/memory/pid-limited, unprivileged, network-disabled Docker container. It has three distinct modes: COO classic script, SNO classic script, and SNO CommonJS file-module execution. Each lane passed all 2,199 eligible cases from the first two official tests per program; one of 2,200 original fixture executions failed independently of obfuscation. The [pinned evaluation report](im-results/jsdeobsbench-adapter-2026-11-15.md) records compatibility, source growth, transformation coverage, measured process-level timing, and remaining attack-simulation gaps. Reproduce the converter, corpus audit, coverage summary and differential harness through the scripts in sims/. Use npm run typecheck:external to check their JSDoc contracts. The external corpus provides independent behavioral regression evidence, not a proof of 2.5x hot-path overhead or deobfuscation resistance. A separate [pinned public-only static XOR string-recovery attack](im-results/jsdeobsbench-public-static-recovery-2026-11-16.md) now recovers every compiler-reported encoded literal reference across both SNO corpus grammars, with original source and official cases withheld from a separately mounted, unprivileged, network-disabled attacker container.
