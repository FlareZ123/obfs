# Obfs research baseline

This repository is an experimental, conservative JavaScript obfuscator targeting Node.js 22+ and modern browsers. It offers three operational modes. The current version is a reproducible starting implementation; its security and performance guarantees are limited to the conditions described here.

## Install and verify

Install dependencies with `npm install`, then run `npm test`, `npm run typecheck`, and `npm run benchmark` from the repository root. All code is CommonJS with JSDoc annotations. Optional `npm run test:browser` runs a real Chromium headless integration test when Chromium is installed (`CHROMIUM_BIN` overrides the binary location). The parser dependency is Acorn 8.x, and the JSDoc static checker uses TypeScript with Node.js declarations as development dependencies. The default compiler avoids source-code `eval`. Experimental, explicitly opted-in register VMs execute bounded custom binary-operator tapes; those interpreters are publicly recoverable and require workload-specific performance assessment.

**Validation status (2026-11-15):** The newest pinned [full Node 22 Linux/Windows gate 43760750888](https://github.com/FlareZ123/obfs/actions/runs/43760750888) passed at exact source `620b3acb49cfe3a0cd61bc1c312398a72a344555`: **1,076 passed, 0 failed, 1 skipped out of 1,077 Node tests on each OS**. Both strict JSDoc suites, sampled benchmarks, and 14 Ubuntu Chromium browser fixtures passed. The same immutable source also passed the [targeted SCO gate 43760746861](https://github.com/FlareZ123/obfs/actions/runs/43760746861), including real Chromium with a literal or runtime-injected Node environment secret. This builds on the earlier [source-spelled TypeError coverage repair](im-results/property-coverage-source-spelling-reconciliation-2026-11-15.md). The historical [five-failure triage](im-results/manual-validation-triage-2026-11-15.md) predates that repair. No full-control tamper-resistance proof follows from a passing integration suite. Authenticated online SCO relaying remains possible, and the measured one-call workload exceeds 2.5×; see the [private-constant threat/cost report](im-results/sco-private-primitive-constants-2026-11-15.md).

## Entrypoints

`bin/coo.js` transforms a directory into static browser files, preserving relative ESM import paths and non-JavaScript assets. Example:

```powershell
node bin/coo.js --root .\examples\browser --entry index.mjs --out .\dist-browser --closed-world
```

`bin/sno.js` produces a preobfuscated Node CommonJS directory plus `sno-entry.cjs`. It verifies the output files' SHA-256 digests at startup and then loads the actual entry through `require`. Example:

```powershell
node bin/sno.js --root .\examples\server --entry index.cjs --out .\dist-server
node .\dist-server\sno-entry.cjs
```

**Runnable advanced SCO example:** [`examples/sco-private/`](examples/sco-private/README.md) includes an original keyed ESM implementation, the **actual generated client RPC facade** saved as a before-and-after artifact, a deterministic reproduction/check script, and an authenticated localhost HTTP server. A live differential regression checks the generated client against the server-resident original. This demonstrates a genuine server-only source and key separation, with the runtime and oracle limitations documented in the example. Existing COO/SNO transformations cannot provide the same trusted-server confidentiality under their full-control threat models.

**Multi-module SCO example:** [`examples/sco-graph/`](examples/sco-graph/README.md)
contains three cooperating private ES modules, two exact compiler-generated
public RPC facades, an authenticated localhost service, and a native-versus-
remote integration test. `partitionScoAsyncGraph` explicitly selects which
private module exports become public facades; `bindScoGraphExports` merges
their private server methods into an authorized RPC registry. Its measured
12,000-round HMAC operation met the 2.5× runtime target on two localhost
runners, with incomplete performance/security coverage documented in
[`im-results/sco-graph-partition-2026-11-15.md`](im-results/sco-graph-partition-2026-11-15.md).

**SCO authorized online-relay limit:** Keeping a random HMAC key and private ESM implementation server-side protects them from a source-only client; it does not prevent an attacker who has a legitimate unlimited-query account from using that same original server as an oracle for downstream users. A real attacker-operated loopback proxy reproduced **32/32 previously unqueried high-entropy outputs** without extracting the key, despite direct unauthenticated requests returning 403. Its heavy 8 MiB HMAC workload measured **1.304× Ubuntu / 1.345× Windows** end-to-end through two HTTP hops, measured only on local loopback without realistic RTT or TLS. The independently reproducible [server-private online relay attacker](sims/sco-relay-attack.js) and [SCO large-domain results](im-results/sco-large-domain-prf-2026-11-15.md) distinguish actual server-side source secrecy from functional anti-cloning under an authorized online relay.

**Real-browser HTTPS SCO check:** [Ubuntu Chromium browser workflow 43762602922](https://github.com/FlareZ123/obfs/actions/runs/43762602922) at `9d490fe68a9078b61ba8da74f469a47ecdff9e30` ran the compiler-generated ESM facade through a local TLS 1.3 proxy and returned the exact server-private HMAC output. An isolated browser profile without trust for the self-signed fixture could not retrieve the result. Chrome's *test-only exact SPKI key exception* was used for the successful profile, not real production PKI validation. [Executable TLS browser report](im-results/sco-tls-browser-2026-11-15.md). An additional [pinned Chrome instrumentation run 43763160286](https://github.com/FlareZ123/obfs/actions/runs/43763160286) confirms a client-modified page can intercept the generated facade's authenticated fetch, recover the RPC method identifier, and observe the exact private-service response without recovering the server key.

**Certificate-validated SCO transport:** [Linux/Windows TLS test run 43761362939](https://github.com/FlareZ123/obfs/actions/runs/43761362939) at exact SHA `987b51ae2d7a55e8de6f6fc53a78fa5b991988a6` executed a compiler-generated RPC facade with a localhost TLS 1.3 authenticated server: **12/12** facade calls matched the private native HMAC, while an authorized online attacker relay matched **32/32** never-queried challenges. The relay measured **1.425× Ubuntu / 1.291× Windows** for the tested 8 MiB HMAC workload and exposed no private implementation/key. This confirms the authorization/relaying limitation in spite of TLS. A separate [TLS connection-granularity report](im-results/sco-tls-boundary-2026-11-15.md) demonstrates 2.5× budget failures for lighter operations. See the [generated facade TLS relay evidence](im-results/sco-tls-generated-facade-relay-2026-11-15.md); neither benchmark measures physical WAN latency or proves general compatibility/security.

**Experimental COO sharding sample:** [`examples/coo-shards/`](examples/coo-shards/README.md)
includes a checked-in four-module before/after transformation of two string
constants, a source-only offline reconstruction witness, and paired cold/hot
Node measurements. It remains outside the production transform: its public
UTF-16/XOR masks are reversible, and the tested graph-load wall time exceeded
the project's 2.5× target. See
[`im-results/coo-shard-layout-2026-11-15.md`](im-results/coo-shard-layout-2026-11-15.md).

`bin/sco.js` starts an HTTP server with the obfuscator library loaded server-side. It encodes served JavaScript afresh on each request, under `/obfs/`. Example:

```powershell
node bin/sco.js --root .\examples\browser --entry index.mjs --port 8080 --closed-world
```

SCO now serves only the named browser entry and its static ESM imports/reexports by default. Unreferenced JavaScript under the source root is **private by default**, even if it has a `.js`, `.mjs`, or `.cjs` extension. Use repeatable `--client relative/file.js` for independent browser scripts, **all** runtime `import()` dependencies (including literal specifiers), workers, and other runtime-loaded JavaScript files. Use `--asset relative/file.css` to explicitly serve non-JavaScript assets. The source root may contain server-only implementations or configuration; do not put those files in `--client` or import them from the client entry. The programmatic SCO handler continues to serve exactly the files provided by its caller.

**SCO origin authorization:** `createScoHandler({allowedHosts:[...]})` compares the incoming HTTP `Host` header. Attackers using ordinary HTTP clients can set this header to a permitted name while contacting the same server; the filter is therefore a routing convenience and **does not authorize source reads or private RPC**. Integrators must implement trusted `authorizeRead`, `authorizeRpc`, and `authorizeOperation` policies on the server. The regression `test/sco-host-header-spoof.test.js` demonstrates both the forged-Host read and independent policy denial. The test session header is a fixture, not production authentication. Dynamic imports are not implicitly authorized even when their specifier is a literal: a dormant or unreachable import must not accidentally publish a server-only file. An import() or script tag referring to an unlisted file receives HTTP 404 until the integrator explicitly declares it.

For browser module graphs that use `.js` rather than `.mjs` extensions, add `--js-module` to the COO or SCO CLI invocation. This explicitly treats every input `.js` file as an ES module; do not enable it for mixed classic-script or CommonJS `.js` trees. The flag is rejected in SNO. `.mjs` is recognized as a module without the flag. The SNO CLI detects explicit nested Node `package.json` module scopes for `.js` dependencies, allowing a CommonJS entry to dynamically import ESM modules.

The programmatic API is `require('./src')`, exporting `virtualizeExpressionGraphs`, `lowerWasmI32Functions`, `obfuscateFiles`, `createSnoLauncher`, `createScoHandler`, `createScoRpcClientSource`, `createScoBatchMethod`, `preflightScoBatchState`, `partitionScoAsyncModule`, `bindScoModuleExports`, `partitionScoAsyncGraph`, and `bindScoGraphExports`. A file is `{path,code,sourceType?}`. Modes are `coo`, `sco`, `sno`; supported source types are `script`, `module`, `commonjs`, `asset`.

## Implemented transformations

- Experimental private Symbol-key property representation via COO/SNO `--symbol-keys` or programmatic `experimentalSymbolKeys:true`. It admits only local privately owned objects under the same conservative proof as normal property renaming, generates unregistered `Symbol()` keys, and updates every proved member/destructuring reference. [Real before/after](examples/symbol-keys/README.md), [independent seedless attacker](sims/symbol-key-static-recover.js), and [cross-platform hot/cold evidence](im-results/symbol-key-backend-cold-attack-2026-11-15.md) show that this is **functionally reconstructable from public output**. The 250k-call hot kernel was near 1×, but several measured fresh-compilation cases exceeded the strict **2.5×** compute budget, up to 22.5×. It remains off by default, and is unsuitable for unprofiled short-running workloads.
- One-time Unicode-preserving XOR string decoding. The decoder's array is initialized once per file, with per-build randomness. Eager string encoding is **off by default for COO and SCO client files** and enabled for SNO; programmatic COO/SCO callers may explicitly request `strings:true`, accepting the measured cold-start tradeoff. String literals inside direct loop bodies, import specifiers, `require` arguments, directive prologues, and noncomputed property keys remain intact.
- Conservative AST-based private property renaming. It tracks immutable aliases, passes to local direct-call functions, identity returns, and simple statically keyed object destructuring. Immutable local arrow/function-expression readers of a proven own field are also tracked, including nested direct identity forwarding into reader calls. A statically keyed object-pattern declaration or discarded assignment may likewise destructure a directly proven identity return; unknown keys, rest properties, and escaped assignment values remain unproved. See the [generated reader before/after](examples/local-reader/README.md), [generated destructuring before/after](examples/forwarded-destructuring/README.md), and [pinned reader](im-results/local-reader-interprocedural-2026-11-15.md) and [destructuring evidence](im-results/forwarded-destructuring-2026-11-15.md). Own-property initializers may contain primitive literals or recursively literal-only arrays. A private top-level, single-use zero-argument function/immutable expression factory directly returning an inert object literal may also initialize the owned object; its own keys are renamed only after the same alias/use proof succeeds. The narrow case has a [generated one-file CommonJS before/after](examples/factory-ownership/README.md), [generated two-file closed-world ESM before/after](examples/factory-cross-file/README.md), and [pinned cross-platform/attacker evidence](im-results/private-factory-ownership-2026-11-15.md). It rejects aliases outside their lexical scopes and unknown method assignments that could inspect object keys. It refuses transformation when the alias escapes, encounters dynamic computed access, reflection, duplicate bindings, `eval`, or `with`. Known function-source observations such as `.toString()`, `String(fn)`, and statically keyed `Reflect.get` or descriptor retrieval of a toString method also suspend the relevant transformations.
- Opt-in `--closed-world` analysis of direct ESM named exports and imports. It renames own keys jointly across provided modules when the proof covers every importer in the declared module set. Direct calls to imported pure identity functions (`export function f(x){return x}`) and immutable expression-arrow identities (`export const f=x=>x`) can safely forward an object's ownership through tracked const aliases. The analysis also recognizes narrow exported reader helpers such as `export function get(x){return x.secretField}` and immutable exported arrow/function expressions with a single direct property return. It rewrites the helper's field access only after verifying that every importer call passes the same proven object at the correct argument position. Reader return values are never treated as aliases of the owner. A directly passed, proven identity-return call can also carry the owner into an imported reader. The proof declines impure, async, mutated, opaque or escaping wrappers. Dynamic imports, namespace imports, reexports, exported aliases, noncanonical URL/absolute/package import specifiers, unresolved relative files and mixed executable source groups cause refusal. Node ESM alternate module loaders and runtime code-generation constructs also disable this proof. CSS, raster-image and font assets may accompany an ESM graph when the integrator guarantees they cannot execute as JavaScript. HTML, SVG and other unknown assets prevent cross-file renaming. Turning this flag on asserts that no outside module accesses exported object shapes.
- Experimental opt-in nested-expression register VM through `experimentalExpressionVm` or the COO/SNO `--expression-vm relative-file:functionName` CLI flag. The compiler accepts strict one-argument, return-only arithmetic/bitwise expression trees, emits a seed-diversified multi-register instruction tape, and preserves the native operators' evaluation order. It extends the older linear-chain VM to branched binary expression trees, with a [real generated before/after and reproducible builder](examples/expression-vm/README.md). An [independent seedless attacker](sims/expression-vm-static-recover.js) reconstructs the full original sample expression from the public VM, so this is a research-only structure transform and has no proven full-control security barrier. Dense-call overhead can substantially exceed 2.5x; apply only after real workload measurement. See [intermediate evidence](im-results/expression-vm-graph-2026-11-15.md).
- Experimental hot-path native-register graph through `experimentalNativeGraph` or COO/SNO `--native-graph relative-file:functionName`. It recognizes the same bounded expression grammar, then generates ordinary native-JS binary operations with seed-diversified register identifiers and masked integer constants directly inside the original function. The actual [generated before/after](examples/native-graph/README.md) and [independent public-AST reconstruction](sims/native-graph-static-recover.js) make its performance and confidentiality tradeoff reproducible. A rejected helper-call version cost 17.873x Ubuntu / 24.918x Windows on the dense-call sample; the final inline version measured **1.003x Ubuntu / 0.995x Windows** on the same workload in [pinned cross-platform CI](https://github.com/FlareZ123/obfs/actions/runs/43739846096). This is a workload-specific measurement, and the output remains statically reconstructable. Do not infer a universal 2.5x bound. An [80-expression deterministic differential and source-only reconstruction fuzz](test/expression-graph-fuzz.test.js) verified 3,040 typed/stateful test cases across both backends on Ubuntu and Windows in [run 43741266407](https://github.com/FlareZ123/obfs/actions/runs/43741266407). See [intermediate evidence](im-results/native-graph-backend-2026-11-15.md).
- Experimental opt-in signed-Int32 WebAssembly lowering through `experimentalWasmI32` or the COO/SNO CLI `--wasm-i32 relative-file:functionName`: selected single-parameter return-only bitvector functions are compiled into small, seeded/diversified WebAssembly modules embedded in JS wrappers. The real [generated before/after](examples/wasm-i32/README.md) and [pinned Windows/Linux/Chromium evidence](im-results/wasm-i32-pipeline-2026-11-15.md) cover 19,680 finite typed comparisons, source-only executable cloning and exact AST reconstruction for 120/120 seeded samples from the public binary, and sample-specific hot ratios below 2.5×. Callers must prove primitive signed-Int32 Number inputs, compatible Wasm runtime/CSP, and no source/stack introspection contract; output is publicly extractable and startup must count for COO. The [pinned cold-start experiment](im-results/wasm-i32-pipeline-2026-11-15.md#pinned-cold-to-hot-crossover-budget-counterexample) exceeded 2.5× on both OSes for short-lived executions. A hoisted ESM helper now preserves the tested early cyclic-import calls. This is an experimental syntax/binary diversification technique with no hostile-runtime confidentiality or integrity claim.\n- Experimental opt-in native-superblock control-flow flattening via `experimentalBranchBlocks`: safely recognized, return-only nested ternaries become seed-shuffled basic blocks that retain native JS operators. [Real generated before/after](examples/branch-blocks/README.md), [focused differential tests](test/branch-blocks.test.js), [pinned performance and seedless reconstruction report](im-results/branch-superblocks-2026-11-15.md). The tested sample met the 2.5x hot-runtime limit, but an independent static attacker recovered every branch and operand; this is reversible structure hiding, without a general 2.5x guarantee.
- Restricted lexical identifier renaming using unique-binding AST proofs; variable names change while external API names, object literal keys, and dynamic-scope constructs remain unchanged.
- Optional browser hostname check. It is a convenience restriction against accidental reuse, and **cannot withstand a client that can modify code**. Host-locked ESM files with static imports or reexports are refused, because those dependencies would execute before the guard. Use server-side authorization to protect such graphs.
- SNO local integrity check against incidental file corruption. Since the modeled adversary controls the server's files and runtime, this cannot establish a cryptographic trust boundary.

**Source disclosure:** COO, SCO, and SNO refuse `.map` sidecar assets, source-map JSON payloads regardless of filename, and real JavaScript `sourceMappingURL` directives, including inline `data:` maps. They also refuse CSS `sourceMappingURL` block comments in standalone `.css` files and in HTML/SVG `<style>` elements; these annotations can otherwise publish the original source inside a base64 map. SVG animation `values` URL sequences are checked state by state. They also refuse executable JavaScript and transpiler input files such as `.js`, `.jsx`, `.ts`, `.tsx`, and `.vue` when supplied as opaque assets. A standards-compliant HTML preflight (`parse5@7.3.0`) refuses static HTML assets containing inline scripts, event handlers, `srcdoc`, or embedded executable URLs while preserving files that reference external transformed scripts. An XML-conformant SVG preflight (`saxes@6.0.0`) similarly refuses embedded SVG scripts, event handlers, executable links and malformed or ambiguous SVG source while preserving static artwork. Remove original-source sidecars and source-map references before obfuscation. A source map can contain the original program in `sourcesContent`; see `docs/SECURITY.md` for the policy, compatibility consequences, and remaining asset-disclosure gaps.

## Important limitations

The nested-expression VM is intentionally disabled by default because its visible byte tape is statically recoverable and its selected-function hot-path cost has no universal 2.5x bound.

This prototype does not implement general closure or arbitrary cross-file property-flow reconstruction, encrypted remote execution, production general-purpose Wasm lowering, general-purpose VM virtualization, general lexical identifier mangling, or runtime anti-instrumentation. A restricted opt-in experimental register VM is available in [src/register-vm.js](src/register-vm.js), with a [real generated example](examples/register-vm/README.md) and a [seedless source-only reconstruction test](test/register-vm-static-recovery.test.js). It has no validated strong security boundary. Dynamic tooling, modified runtimes, and complete client visibility can extract code and bypass local checks. Direct source-introspection checks remain syntactic; implicit coercion, dynamic builtin aliases, and external observers can still expose transformed source. It cannot guarantee 2.5x speed for arbitrary inputs. The benchmark is a limited sample, not a performance proof. Breaking API contracts through obfuscation is a correctness failure; ambiguous cases intentionally remain unchanged.

SCO's per-request source variation also declines across the entire published file group when a known source observer appears in any member, because another module may inspect an exported function through \`Function.prototype.toString\`; the reproduced compatibility regression and conservative repair are documented in \`im-results/sco-interfile-source-observation-2026-11-15.md\`. This is a syntactic safety guard, not a proof against arbitrary source introspection.\n\nFor SCO, the server can retain secrets that are never sent to the client. A programmatic `createScoHandler` accepts `remoteMethods`, `authorizeRpc`, and `maxRpcBytes` to keep sensitive computation on a trusted server via authenticated JSON POST `/obfs/rpc`. `createScoRpcClientSource` generates a same-origin browser ESM facade for named RPC methods, keeping their implementations server-side; see `docs/SCO_AUTHORIZATION.md` for usage and limits. Optional `createScoBatchMethod` groups explicitly named operations into one bounded authenticated RPC request, executing them sequentially to reduce transport overhead. Its one-time authorization preflight is a snapshot: state-dependent policies that change during a batch need a pure transition model such as `preflightScoBatchState` plus application-managed isolation, or must refuse those batches. The helper itself does not create a transaction. For dedicated private ESM modules with exported async functions, `partitionScoAsyncModule` emits public RPC proxies while `bindScoModuleExports` keeps the original functions server-resident. This has explicit JSON-compatible operation semantics and can optionally retain private top-level initialization and expose batched calls; see `docs/SCO_PARTITION.md`. See `im-results/sco-rpc-cost-2026-11-15.md` for measured budget tradeoffs and remaining failures. The reusable `createScoKeyedIsolation` helper can serialize authenticated SCO authorization and execution per principal with independent account queues; see `docs/SCO_AUTHORIZATION.md`. It cannot protect shared state outside the process or prevent authorized client relaying. Cross-file property proof extensions and reproduced soundness limits are documented in `im-results/cross-file-reader-proof-2026-11-15.md` and `im-results/ambient-intrinsic-aliases-2026-11-15.md`. This API does not automatically rewrite ordinary JS into remote calls. Browser-delivered JS remains extractable. The `Host` header may be forged by HTTP clients; enforce real authorization on the server for privileged operations.


The opt-in `partitionScoSelectedAsyncExports` API also supports deliberately mixed modules: approved local public exports remain native JavaScript, while chosen async exports become authenticated private RPC calls. [The generated mixed-module source pair](examples/sco-selective/README.md) and [pinned independent relay/performance challenge](im-results/sco-selective-2026-11-15.md) measure preserved ESM behavior and 1.12–1.20× warm localhost whole-session cost on a selected workload. An authorized third party relays all 20 held-out outputs through a separate proxy, so this architecture withholds implementation source under SCO trust assumptions but does not prohibit online functional cloning. The [server-private primitive-constant extension](examples/sco-private-const/README.md) permits literal module keys in selected async exports. Its [pinned adversarial and browser measurement](im-results/sco-private-primitive-constants-2026-11-15.md) found direct-client thin HMAC ratios of **23.87× Ubuntu and 22.54× Windows**, versus **1.31× and 1.23×** in a 100,000-local-operation session. Both tested platforms passed native, cross-realm source-withholding and authorization checks; only the amortized session satisfied the 2.5× bound.

## Repository organization

`src/` is the implementation; `test/` contains behavior/integrity/regression suites and a benchmark; `im-results/` contains intermediate empirical results and limitations, including the [mode-by-mode threat and performance scorecard](im-results/mode-threat-scorecard-2026-11-15.md); `results/` is reserved for reproducible established research conclusions; `agents/` is persistent research coordination state. Read `docs/SECURITY.md` before deployment.

## Independent external compatibility evaluation

The manually dispatched [JsDeObsBench evaluation workflow](.github/workflows/manual-jsdeobsbench.yml) transforms a pinned public corpus of 1,301 unrelated CodeNet JavaScript programs, verifies the upstream Git blob fingerprint, and compares native and transformed outputs under matching inputs in a CPU/memory/pid-limited, unprivileged, network-disabled Docker container. It has three distinct modes: COO classic script, SNO classic script, and SNO CommonJS file-module execution. Each lane passed all 2,199 eligible cases from the first two official tests per program; one of 2,200 original fixture executions failed independently of obfuscation. The [pinned evaluation report](im-results/jsdeobsbench-adapter-2026-11-15.md) records compatibility, source growth, transformation coverage, measured process-level timing, and remaining attack-simulation gaps. Reproduce the converter, corpus audit, coverage summary and differential harness through the scripts in sims/. Use npm run typecheck:external to check their JSDoc contracts. The external corpus provides independent behavioral regression evidence, not a proof of 2.5x hot-path overhead or deobfuscation resistance; direct model and source-reconstruction adversarial evaluation remains outstanding.
