No peer-review-level or independently reproduced obfuscation-security result has yet been established. This directory remains intentionally empty of asserted discoveries. The Node.js SCO, COO, and SNO prototype and its limits are described in [the root README](../README.md) and [the threat-model boundaries](../docs/SECURITY.md). ## Current intermediate decision evidence

The [architecture decision matrix](../im-results/decision-matrix-2026-11-15.md) is the principal comparative entry point. It records pinned source, executable attackers, compatible transformations, protected-work and application overhead, and decisions for the main AST compiler, the independent checker compiler, the experimental public postfix VM, and SCO server-private RPC. Its [three-file ESM comparison](../im-results/decision-attack-grid-2026-11-15.md) supplies a controlled cross-platform challenge with native behavior and attack scripts. The [historical mode threat scorecard](../im-results/mode-threat-scorecard-2026-11-15.md) remains useful context, but its 205-test and five-Chrome-fixture snapshot has been superseded by later validation. It should not be treated as the newest release status.

Subsequent experiments sharpen the decision. [Runtime decoder extraction](../im-results/runtime-decoder-extraction-2026-11-15.md) demonstrates native Node and Chromium interception of the eager XOR decoder, including a dormant string literal. [Source-observer regression and coverage evidence](../im-results/source-observer-proof-coverage-2026-11-15.md) documents a passing cross-platform repair and the coverage sacrificed by a whole-group refusal guard. The [typed numeric WebAssembly candidate](../im-results/wasm-numeric-candidate-2026-11-15.md) reports exact numeric differential checks, executable copying from distributed Wasm bytes, a hot-work result within the budget, and cold-start cases exceeding 2.5×. It remains an isolated experimental backend, as its report states. [SCO polynomial-oracle reconstruction](../im-results/sco-polynomial-oracle-2026-11-15.md) independently measures chosen-input functional reconstruction despite keeping implementation source server-private.


## Newly reproduced evidence and unresolved coverage

The [external JsDeObsBench differential study](../im-results/jsdeobsbench-adapter-2026-11-15.md) compiled a pinned corpus of **1,301** public CodeNet-style JavaScript programs in COO script, SNO script, and SNO CommonJS modes. Pinned [three-lane run 43704598450](https://github.com/FlareZ123/obfs/actions/runs/43704598450) matched the **2,199 executable original cases** in each lane out of 2,200 selected official cases; the complete upstream corpus offers 2,984 cases, so 784 published inputs were untested. The same experiment counted **zero renamed private-property keys** in all three modes, despite nonzero identifier changes and SNO literal encodings. This is valuable independent compatibility evidence, with minimal coverage of the project's central cross-file property-flow requirement and no measured reconstruction resistance. A later seeded [run 43706326751](https://github.com/FlareZ123/obfs/actions/runs/43706326751) passed all three lanes after a Math.random-dependent comparison had exposed a nondeterministic baseline confounder. These results must not be treated as a hot-path performance bound or full JavaScript semantic proof.

A [paired original-source asset disclosure attack](../im-results/asset-source-disclosure-2026-11-15.md) demonstrated that an older output pipeline copied source maps, inline HTML and disguised transpiler inputs, exposing the original canary without attacking the obfuscated program. The updated policy rejects those tested cases in all three modes, with a [green paired Linux/Windows attack run 43706739931](https://github.com/FlareZ123/obfs/actions/runs/43706739931). It is a bounded build/serve refusal improvement; it says nothing about hostile-runtime integrity or recovering the remaining delivered JavaScript. Later SVG and encoding changes require their own integration validation.

## Verification and promotion discipline

An earlier full manual Linux/Windows validation was [run 43696715738](https://github.com/FlareZ123/obfs/actions/runs/43696715738), pinned to `998c00bb421a2bcf347b5d5daa66fd56cf9b612d`. It passed behavior and adversarial tests, JSDoc typechecking, sampled benchmarks, and an Ubuntu live-Chromium fixture. A later [browser-only run 43696954625](https://github.com/FlareZ123/obfs/actions/runs/43696954625) separately validates the instrumentation fixture. The [Wasm candidate run 43698242446](https://github.com/FlareZ123/obfs/actions/runs/43698242446) validates that experimental study. These green runs apply to their own pinned commits and selected workflows, rather than certifying all future repository HEAD changes.

A newer complete Linux/Windows baseline [run 43705836027](https://github.com/FlareZ123/obfs/actions/runs/43705836027) passed at commit `19e1a14b78a5aa985ed398f041300c1790b7aa10`. The subsequent [run 43706323035](https://github.com/FlareZ123/obfs/actions/runs/43706323035) at `b7faf8b2540eb43790ac5562203a825fba38713b` failed **two HTML-asset regression cases on both operating systems**, each raising the new inline-source refusal during tests that expected opaque asset acceptance. Typechecks, sampled benchmarks and the Ubuntu Chromium checks completed successfully in that run. The separately green external-corpus run at the same commit is not a full-suite release gate. Treat the newer mainline as **unverified for a complete green integrated baseline** until a subsequent exact-head validation passes; retain the refusals as an intentional policy change and reconcile their compatibility tests explicitly.

For new architecture claims, update the comparative evidence with exact commit, workload, native semantic contract, transformed coverage, independent attacker success, setup/runtime separation, and measured 2.5× compliance. Keep negative controls and counterexamples. Reserve cross-platform full-suite manual CI for coherent integration gates, preserving the repository rule against per-commit workflows. A passing test suite demonstrates tested compatibility; it does not itself demonstrate unreadability, tamper resistance, or execution authorization under an attacker-controlled runtime.
