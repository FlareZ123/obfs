# Diversified Int32 WebAssembly lowering: real before/after

This directory contains actual compiler output for a deliberately narrow JavaScript-to-WebAssembly backend. The compiler is exposed as **lowerWasmI32Functions** and can be selected through the COO/SNO CLI's **--wasm-i32 relative-file:functionName** flag or through the **experimentalWasmI32** programmatic option.

## Generated source

**Before:** [before.cjs](before.cjs) is a native signed-Int32 bitwise function. **After:** [after.cjs](after.cjs) is the generated output using seed **agent28-wasm-sample-v1**. The emitted JavaScript still declares the function **scramble**, but calls a previously instantiated WebAssembly export named **f**. Its WebAssembly binary is embedded as a public byte array and contains seeded masked i32 constants and Boolean-identity diversification.

Run **node examples/wasm-i32/build.cjs** from the repository root. The script compiles the original source again, compares the generated bytes exactly with the checked-in output, and checks 4,001 signed-Int32 inputs. It then locates the public WebAssembly byte array in the generated source, loads it independently using the standard WebAssembly API, and confirms that an attacker can clone the function without the original JS source.

## Explicit safety contract

This experiment accepts only selected one-argument, return-only, synchronous function declarations whose expressions consist of i32 bitwise operators, unary bitwise NOT, and integer literals. The caller must guarantee primitive signed-Int32 Number inputs, ordinary Wasm availability, a compatible CSP, and no external source/stack-introspection contract. The compiler cannot infer the caller's types, and it refuses unproved expressions. CommonJS output initializes WebAssembly synchronously at module evaluation. ESM output instead emits a hoisted, self-replacing lazy initializer: cyclic importers can call an exported function before its module body evaluates without encountering an uninitialized helper binding. The first invocation compiles the Wasm module; subsequent calls use the cached native export. Initialization cost counts against COO's 2.5x application runtime ceiling, including a first call during a module cycle. Neither backend has a universal runtime guarantee.

The generated binary is available to every client in COO and SCO client deliveries, and to the server owner in SNO. It can be copied, disassembled, and invoked by anyone who has the output. Neither randomized opcode expressions nor the public byte array provides a tamperproof lock, confidentiality, or protection against a debugging runtime.

## Tests and performance

Run **node --test test/wasm-i32.test.js** for bitvector outputs across five expression graphs and 24 build seeds each, explicit negative cases, the public-binary cloning attack, compiler integration and CLI selection, and a paired diagnostic hot-loop measurement. The real-browser fixture is **node test/wasm-i32-browser.js** with Chromium installed. The manual cross-platform workflow is [manual-wasm-i32.yml](../../.github/workflows/manual-wasm-i32.yml).

The local Node 22 Linux pilot observed approximately 2.06x native hot-loop cost on a single 150,000-call sample and around 3.2 ms initial module evaluation/instantiation in the same process. Those measurements are workload-specific and do not prove that a sparse invocation or arbitrary client module remains within the budget. See the [intermediate report](../../im-results/wasm-i32-pipeline-2026-11-15.md) for reproducible measurements and the independently cloned export.
