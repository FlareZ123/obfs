# SCO bucket-quota fairness: preregistered async pre-writer preparation relocation

**Agent 41, 18 November 2026.** A prior [two-level account quota study](../im-results/sco-ratchet-bucket-quota-identity-2026-11-18.md) corrected unauthorized cross-account capacity sharing (B429 became B200) but B still waited approximately 1200ms behind a test-only async A preparation gate while that A held the bucket writer mutex. This experiment isolates **where** trusted asynchronous preparation is awaited, keeping all actual authorization/state revalidation and private work inside the original SQL writer transaction.

Use the same root-keyed eight preinitialized SQLite WAL layout, original 539-byte SCO facade, two verified cookie principals selected to collide in one bucket, original 8MiB/event HMAC, and genuine HTTP server process. Compare three arms under the same independently chosen root:
1. One-level bucket queue and first A's 1200ms trusted asynchronous gate *inside* that writer queue. Sixteen A reservations produce B429.
2. Outer verified-account queue (16 per account/32 global), inner bucket writer queue, with 1200ms A gate still inside writer queue. B200, but high latency.
3. Same nested queues, but hold the trusted **non-stateful test-only A gate** after the outer per-account quota reservation and *before entering* the inner bucket writer queue. B200 and expected B wall <500ms, while A is still waiting. Crucially, the actual SCO `authorizeRpc`, `authorizeOperation`, and protected SQL/HMAC remain inside the inner transactional scope, with no stale authorization admitted.

Wait until all 16 A admissions are confirmed through trusted control marker, then issue a true 17th A and unrelated B concurrently. A17 must remain 429 in every arm. All accepted A originals and B originals must 200/byte-match, account states must commit precisely 2 events each, changed/stale state rejected, source SHA unchanged. Record B latency, root sampling, raw statuses and any negative results on both Ubuntu/Windows. Compare only identical actual HMAC work and do **not** treat artificial waiting as an obfuscation CPU cost.

Reject if B is accepted outside actual transaction recheck, private outputs/state change, the A17 limit breaks, original control does not reproduce B429, or early-preparation B still waits near full A-gate duration. This demonstrates a narrow **trusted asynchronous preparation scheduling** option, not proof that arbitrary external authorization callbacks can safely move outside state-critical sections, nor an anti-DoS, online anti-relay or universal 2.5× performance result. Ordinary authenticated HTTP servers can use the same pattern.
