# Source visibility, contextual equivalence and the host-trust frontier

**Agent 1, 28 November 2026. Status:** research-direction theorem/contract proposal, **not** an established new security result and **not** evidence that any candidate meets the primary objective.

## A precise incompatibility to stop finite-sink whack-a-mole

Consider a delivered source file with exact byte string `s`, and any obfuscator producing `t = T(s)` at the **same host-observable path**, where `t !== s`. Assume the set of admissible program contexts includes one that can read the bytes at that path and report them as a trace component. Define such a context `C` by `trace(C,p) = (ordinary_outputs(p), readBytes(path))`. Then `trace(C,s) !== trace(C,t)` trivially, regardless of whether `ordinary_outputs(s) = ordinary_outputs(t)`.

The same distinction is reachable *inside* program execution without a visible filesystem import in the analyzed program: an embedding Node host can first replace an inherited method, e.g. `Array.prototype.flat`, with a closure that reads the published file, and the supplied ESM entry calls `[0].flat()`. The call can return the original-key membership bit (or full byte text). Browser hosts can similarly supply external getters, patched methods or source-reading callbacks. A static checker whose only input is the declared ESM graph cannot prove that a host-owned inherited method is the native, side-effect-free implementation. Additional finite lists of syntactically forbidden identifiers may reduce admitted cases, but they do not solve this universal contextual-equivalence requirement.

**This is a conditional mathematical statement**, not a new obfuscation attack on any exact pinned compiler; a concrete finite reproducer and a completed CI receipt are independently required for a claim about a particular compiler. Agent 3's [explicit inherited-method and implicit ToPrimitive witness branch](https://github.com/FlareZ123/obfs/tree/agent3/source-island-inherited-method-red-20261128) is a relevant unvalidated-at-writing implementation-level falsifier; it deliberately keeps host patch source outside the compiler's declared ESM graph. Its CI queue status must be checked before reporting a result.

## Two different compatibility contracts

1. **Ordinary or stipulated trusted host:** input code executes with documented, unmodified native intrinsics and explicitly reviewed callbacks; the compiler tests equality of return values, imported/exported behavior, DOM semantics and relevant source observers under that environment. Nontrivial local own-property rewrites may be admitted with a verified closed-world ownership proof. It is reasonable to optimize protection yield here, *but the assumption must be recorded next to every acceptance claim*.
2. **Host-parametric adversarial context:** an attacker may patch an external intrinsic, replace the Node loader or browser host, read the shipped source file and inspect all running code. If the original program can reach that context, **no changed source at the observed path can preserve all source-byte-observing contextual traces**. A zero-rewrite refusal, an explicit trusted-host qualification, or an environmental architecture that never exposes the secret at that path are the meaningful options. No syntactic blacklist can simultaneously guarantee universal host-parametric parity and positive changes of publicly readable bytes.

The general statement applies to **COO and SNO's owner-controlled visible file boundary**. It does not establish the same failure for **SCO server-private modules** that are never distributed; server authorization and remote secrets are a different trust boundary. Nor does it assert that arbitrary source changes provide zero practical attack friction: *finite empirical attacker cost* is still a valid, separately measurable goal.

A related constraint: when an implementation inserts a fixed strictly positive overhead `h` into a workload with native compute `c>0`, the ratio `(c+h)/c` exceeds 2.5 whenever `c < h/1.5`. A universal ratio over arbitrarily small native operations is therefore not justified by any finite benchmark; acceptable performance claims need explicit workloads and accounting boundaries, especially for per-operation SCO RPC and COO cold initialization.

## Impact on this repository's integration decisions

- Keep the current [frozen V1 PR #384](https://github.com/FlareZ123/obfs/pull/384) **NO-GO**. The positive-yield failures, equal-trust minifier comparison, SCO relay, SNO owner bypass, and strict CPU breaches are independent actual vetoes; contextual impossibility is **not** a substitute for those measured receipts.
- The source-island option should be labelled **experimental, restricted trusted-host compatibility**, not strong anti-host instrumentation or universal tamper resistance. The native-source/output parity tests need explicit *positive rewrite controls* and adversarial host variants; source-byte counterexamples must be kept as red tests until a narrower contract or a safe veto is chosen.
- Prefer one reproducible closed decision packet per exact source SHA over an unbounded growing denylist of host method names. Document exactly which intrinsics, external callbacks and filesystem readers are excluded by the chosen positive-yield contract.
- For increased protection, pursue mechanisms that have measured attacker-cost advantage over equal-trust ordinary-minified controls and keep their compute cost within a declared 2.5× **workload** boundary. In SCO, distinguish actual trusted server-resident secrecy from the facade syntax; in COO/SNO, report limitations rather than claiming unbreakable locking.
