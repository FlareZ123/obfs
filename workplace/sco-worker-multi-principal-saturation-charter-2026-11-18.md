# Precommitted resident SCO worker multi-principal saturation challenge

**Agent 7, 18 November 2026 ~05:40 UTC. Classification:** question, test design and stop condition. No results recorded in this charter.

The bounded SCO worker pilot `sims/sco-ratchet-worker-http-contention.js` gave 0/14 selected loaded B/direct-original >2.5× session latency breaches with one verified A/one verified B, while the identical synchronous original was 14/14 over. Its private HMAC roots and machines remain server-side, but `makeWorkerServer` starts **one native OS thread per granted principal** with no total queue/admission budget. The more threads admitted, the more Linux/Windows scheduler contention can affect a B session even when Node HTTP itself is responsive.

**Challenge:** keep the exact original per-event 8,388,608-byte HMAC, exact generated SCO facade, one B 16-event batch, one A0 64-event batch with an actual A private-start timestamp/atomic signal, and a separately launched B HTTP child that begins during A0 private work. Simultaneously admit and submit a *known number* of other independently verified A principals each with 64 original HMAC events, never reusing B credentials. Test A-principal counts **1, 4, 8**, with **four independent trials each**, prestarting all trusted worker threads before measured B HTTP. Validate every private A/B/quiet output and HTTP 200 against separate source-level original machine, independently match quiet B cold-client overhead and B submission timestamp inside A0. Record per-trial B/direct-original, B/quiet HTTP ratios, A0 private duration, all worker count/CPU cores and exact source pin. Do not assert an overbudget outcome in the simulation; measure it.

**Decision:** the hypothesis is that 8 independent authenticated A workers sharing a typical 2- or 4-core runner may erode isolated B latency and perhaps create >2.5× strict observed B/direct-original pairs; either positive or negative measurement is useful. A single account with only one allowed principal is a different threat case: **multiple independently verified A principals are conditional on an attacker actually acquiring them** and must not be silently claimed from the prompt's unlimited *requests* alone. This is a resource/availability test, not obfuscation secrecy or incremental compute overhead. No native server with an equally large worker pool is in this initial test, so any observed degradation cannot be attributed to SCO syntax.

**Falsification:** 8-A workload returns clean native parity, real A0 overlap, and 0/4 strict B/direct-original breaches on both operating systems. That would narrow the observed pool-saturation risk but still not prove unlimited-client admission safe. An observed >2.5× pair does not automatically invalidate the prompt's 2.5× *compute time* constraint; it demonstrates a bounded authorized service-latency capacity failure. CPU summation and equivalently provisioned conventional server remain independent comparisons.

Keep the result in `im-results/`, not `results/`. Pin Ubuntu/Windows Node22 source and retain full raw series, worker counts and explicit credential assumptions.
