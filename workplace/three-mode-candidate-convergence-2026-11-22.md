## Additional evidence since the initial snapshot

- **SCO rank-three functional cloning is now tighter.** Agent 22's source-pinned matched attack [run 44959535485](https://github.com/FlareZ123/obfs/actions/runs/44959535485) clones every output of 20 width-32 functions under the explicit rank(V)<=3 promise with at most 631 distinct forward queries and failure below 1e-10. On the same sources, generic degree-three interpolation used 5,489 queries each; the specialized attack used 232–503, 14.39x fewer aggregate queries. This is a restricted algebraic source-family attack and an attacker-query measurement, not a claim about arbitrary JS, protected-runtime overhead, or a new obfuscation advantage. The exact finite probability peer check is [run 44959801369](https://github.com/FlareZ123/obfs/actions/runs/44959801369).
- Agent 20's [CEGAR ablation](https://github.com/FlareZ123/obfs/actions/runs/44965364236) reports about 3.68x fewer chosen queries for three existing synthetic families, with all 576 held-out targets recovered. This is another attacker-side query reduction, not a protected-code runtime measurement or a minifier comparison.
- **SCO operation binding improved but remains experimental.** The signed `-0` versus relayed `+0` mismatch in the WebAuthn operation callback was fixed with `Object.is`; exact signed values remain accepted and mutated values are rejected in the source-pinned post-merge run [44962019844](https://github.com/FlareZ123/obfs/actions/runs/44962019844). This closes the specific numeric fixture, not general JSON canonicalization, same-account online relay, test enrollment, or the workload-dependent 2.5x concern.
- **SRI is a compatibility boundary, not protection.** The source-pinned Chrome test [44965974237](https://github.com/FlareZ123/obfs/actions/runs/44965974237) verifies original and safe complete-graph scripts load while an SRI-mismatched mutated script is blocked. The compiler now conservatively preserves committed source bytes; this can veto a transformation but does not hide distributed source or authorize execution.

These changes improve attack evidence and compatibility/correctness. They do not change the no-candidate decision.

- **A new compiler-correctness gap is reproduced for exported ESM callables.** In an isolated branch based on the current Agent 6 CommonJS-source-protection work, property-key rewrites inside an exported function and an exported object method change the source observed by an external importer's `Function#toString`; an identifier-only pass likewise renames an exported function parameter and changes its source. Ordinary return values remain equal. The paired fixture shows an unexported helper parameter can still be renamed, so the appropriate proof is per-callable rather than a blanket ESM veto. Both Linux and Windows fail the exact regression in [run 44979154437](https://github.com/FlareZ123/obfs/actions/runs/44979154437); details and fixtures are in [the intermediate finding](../im-results/esm-exported-callable-source-observability-2026-11-22.md) and [the isolated branch](https://github.com/FlareZ123/obfs/tree/agent8/esm-exported-callable-source-20261122). This is a semantics-preservation defect, not an obfuscation candidate or security win.


## What is not a candidate

- The four-module shared-owner property-renaming experiment at source SHA `763e684f55c6bdbe86be662014f748886ef7084c` establishes a useful semantic admission capability: the compiler renames two private fields while preserving same-spelled reflective public fields. It does not establish confidentiality or attacker-cost advantage. Configured esbuild property mangling can also rename both names when reflection is not in the graph; the compiler's advantage is conservative behavior preservation, not secrecy. See [the report](../im-results/single-graph-shared-key-selective-property-renaming-2026-11-21.md).
- The 22 November public-artifact GPT-6 probes are qualitative only. The expression VM was reconstructed in 21.594 seconds; the arithmetic probe was 2/3 exact on first pass, with one consequential error. Both use the same model family, source and artifacts coexist publicly, and no equal-trust minified LLM control has been completed. They do not establish an LLM resistance boundary. See [probe synthesis](../im-results/llm-deobfuscation-probe-synthesis-2026-11-22.md).
- The low-rank affine-residual constructions and quadratic interpolation results are valuable candidate-elimination/stress evidence. They are not positive obfuscation candidates and do not imply attacks against arbitrary stateful JavaScript outside their stated algebraic promises.

## Convergence rule

Until a candidate changes the decision, use the above applications as falsification targets and do not create another backend merely to generate activity. A successor proposal should first identify:

1. The exact protected asset and mode-specific attacker authority.
2. A genuinely transformed multi-file application and nonzero executed protected work.
3. The exact emitted bytes and source SHA.
4. An equal-trust ordinary minifier/service control.
5. A precommitted independent attacker task, budget, and held-out set.
6. Separate outcomes for source recovery, functional cloning, runtime extraction, integrity bypass and environment-lock bypass.
7. Paired real Node/browser/server measurements on the same source pin, retaining every strict >2.5x breach and same-code/placebo control.

A candidate is plausible only if it demonstrates a material attacker-cost advantage over the equal-trust control without behavior changes or a strict compute-budget violation. If no such candidate exists, report **none** rather than promoting a semantic-coverage improvement or a passing test count.

This document is a coordination snapshot. It does not supersede individual reports, promote anything into `results/`, or change the release decision.
