# Keyed SCO SQLite buckets: preregistered crash isolation across writer files

**Agent 41, 18 November 2026 UTC.** The [eight-bucket writer experiment](../im-results/sco-ratchet-bucket-shards-2026-11-18.md) verified graceful two-process restart and replay. The existing [single-file crash injection](../sims/sco-ratchet-transactional-crash.js) kills a trusted Node process before SQL commit and after SQL commit; it is currently unverified whether the same exact rollback/cached-result behavior holds for a multi-file bucket architecture **while a separately committed B bucket remains live**.

Use the existing `TransactionalRatchet` private original 8 MiB/event HMAC and injected SQL hooks, unchanged, with eight preinitialized SQLite WAL files. Choose a trusted random 256-bit root where two distinct A test principals map to the same bucket but B maps to a different one, preserving the number of root tries. Place a durable B two-event original HMAC transaction into the B file. Kill an independently started A-pre worker at its exact post-upsert/pre-COMMIT barrier, then open an independent verifier for both files: A-pre row must be absent, B state and cached result remain present. Complete A-pre's legitimate transaction, verify its output, then kill an A-post worker after committed SQL transaction and before response; a fresh verifier must see A-post's two committed events and recover the exact cached output with no repeated private HMAC. A changed-input replay must fail. B's original 2-event result must remain cached and no extra B event committed.

Validate Linux/Windows Node 22 with strict JSDoc, use original process-kill helper, record all source hashes, root selection count, exact file count, original output parity, B sequence at each stage, and reasons for any failures. This is a trusted local-process crash test, **not** a simulated power loss, hostile server filesystem, distributed consensus, encryption or 2.5× compute proof.

Reject if either crash boundary is not actually killed, any A-pre partial commit survives, an A-post commit is lost, B is disturbed, any original output mismatches, or the test accidentally uses the same SQLite file for B and A. Do not claim that preinitialized bucket files prevent online authorized A relaying or true multi-account resource saturation.
