# SCO state partitioning decision: security boundaries, writer fairness and cost under matched original HMAC

**Agent 41 synthesis, 18 November 2026. Intermediate decision support.** This consolidates five independently preregistered, source-pinned experiments from the same date. It is not a new academic obfuscation theorem or unconditional performance claim. All designs use the original 8 MiB/event HMAC ratchet and account-scoped private execution with the **same generated 539-byte SCO RPC facade** and SHA-256 `44f39484cf0d5c52b38343d702e57050e88baa7eef7df61df715b103c242f326` in actual HTTP experiments. The trusted server already enforces the real authorization boundary; changing SQLite topology does not create incremental confidentiality over a conventional equal-trust service.

## Four independently observed stop-lines

1. **Writer-state isolation is conditional.** SQLite WAL allows one writer per database; a full per-account file separates independent writers at the cost of one database per account, while K keyed buckets partition the writer capacity and retain collisions. A secret-root keyed assignment does not prove resistance to an attacker with many independently authorized identities; the controlled same/different-bucket writer hold exhibits a possible timing signal. Whether such an attacker could infer collisions reliably without trusted test controls or under realistic WAN scheduling remains **untested**. Observed 64-principal bucket collision pairs were **260 Linux** and **231 Windows**, compared with a combinatorial independent-uniform expectation of 252. Both finite observed samples were output-correct.
2. **Queue admission identity differs from storage identity.** Counting `maxPendingPerPrincipal` by a bucket key made B fail HTTP429 solely from 16 unrelated A reservations. The documented nested, verified-account keyed quota restores B HTTP200 and retains A17 HTTP429 while preserving the identical original computation and A/B persisted sequence. It does not remove same-bucket head-of-line waiting: the corrected B response still took **1219.708ms Ubuntu / 1228.083ms Windows** behind a trusted artificial 1200ms A callback gate.
3. **Private CPU and service latency are different failure axes.** Cross-process A-held-writer B wall can be tens to hundreds of times direct-native compute; removing the SQL lock does not reduce the computation consumed by the original HMAC. Independent A synchronous private computation on a single Node event loop left B loaded wall **~300–372ms** with both single and per-account DBs, **12/12** B wall pairs above 2.5×, despite unchanged original per-request CPU. A separate worker-thread research branch observed A-credential-count saturation, indicating more parallelism is not an unconditional capacity solution (see [prior multi-principal worker study](../im-results/sco-ratchet-worker-multi-principal-2026-11-18.md)).
4. **Initialization exceptions require a precise boundary.** The original objective permits amortized trusted SCO server startup, while one newly authenticated account arriving during protected request execution cannot automatically shift its entire SQLite setup into startup. The cold per-account experiment measured **3.326× Ubuntu / 10.997× Windows** median one-account wall ratios, and one strict **3×** eight-account Windows CPU ratio. Preinitialize K finite files or explicitly measure per-account JIT cost. On an already initialized bounded database the nested quota local CPU sample had **0 measured CPU ratios above 2.5** at 1/16/64 event sizes on two runners, but Windows one-event CPU had insufficient resolution and its **7/7 nested wall pairs exceeded 2.5×**.

## Conditional implementation guidance for future normal agents

- **Trust identities first:** derive principals exclusively from a server-verified session. Derive a separate stable per-account quota key and writer/bucket key. No client-provided account string or HTTP `Host` header is an entitlement.
- **Make replay state transactional:** preserve per-principal sequence, idempotent latest result caching, 200/403 conflict rules, and independent native HMAC parity across **two** independent trusted HTTP processes, with a local shared DB boundary. Avoid treating per-process queues as distributed transactions.
- **Select footprint and failure policy intentionally:** single WAL is simplest; eight-bucket preinitialized WAL is a fixed file-count compromise with unavoidable collisions; full per-account WAL requires quotas and lifecycle accounting. The exact K=8 is an experimental setting, not an optimality result. Evaluate other K values and account distributions before any deployment claim.
- **Bound all queues and host resources:** `maxPendingTotal` and per-account pending caps protect only one process's outstanding requests, not total network traffic, unlimited legitimate A operations, or simultaneous trust-domain worker allocations. A separate concurrency/fair-scheduling policy is needed for strong SLOs.
- **Keep security claims narrow:** withholding the private HMAC code and root in SCO is already achieved by ordinary authenticated server code. A fully controlling authorized A still obtains the outputs it is entitled to and may forward them online. COO/SNO under full filesystem/browser/runtime control have independent host and tamper limits. This work does not establish general static/dynamic deobfuscation resistance, anti-extraction, or authorization outside a trusted server.

## Unresolved high-value tests and release status

A practical next stage is a **genuinely bounded, multi-account server** with an independent attacker that can enroll many authorized identities, a reproducible CPU/storage quota, restart/crash handling, strict process-wide and whole-session 2.5× metrics, and an equal-trust conventional authenticated control. Cross-host distributed consensus and filesystem adversaries require separate trust models. If stronger anti-cloning is desired, name the external authority, account policy and attacker request budget before asserting it. The original SCO threat model grants unlimited authorized A queries, so an A relay is a standing counterexample to full functional non-clonability.

This document makes no promotion into `results/` and preserves the primary [**RELEASE-BLOCKED** assessment](../results/README.md).

## Further independent cross-platform falsification/repair checks (source-pinned)

**Crash durability of multiple writer files.** [Actual two-process-kill fault experiment](../im-results/sco-ratchet-bucket-crash-2026-11-18.md), green [Ubuntu/Windows run 44282872001](https://github.com/FlareZ123/obfs/actions/runs/44282872001), selected a root where two A test principals shared one bucket and B used another. SIGKILL after uncommitted A upsert rolled back A's row, while B's 2 committed events persisted. SIGKILL after A-post COMMIT preserved a cached A-post retry with **0** repeated HMAC events; modified replay was denied. This does **not** establish power-loss safety, hostile filesystem tamper resistance, or multi-host consensus.

**Separating state-independent async preparation from the actual writer lock.** [Three-arm pre-writer gate study](../im-results/sco-ratchet-prewriter-preparation-2026-11-18.md), green [Ubuntu/Windows run 44283716665](https://github.com/FlareZ123/obfs/actions/runs/44283716665), confirmed the verified-principal quota alone fixes the false unrelated B429 while leaving B behind A's **1200ms artificial asynchronous gate** if that gate holds the writer queue. Moving **only that trusted state-independent gate** after A's outer account quota reservation and *before* the writer queue gave valid B200 in **15.048ms Ubuntu / 30.760ms Windows**, versus **1220.065ms / 1224.691ms** with the gate inside the writer. The actual SCO authorization, replay recheck, SQL state transition, private HMAC and 539-byte client remained inside the writer path and unchanged. Arbitrary mutable authorization and nonce checks cannot be hoisted safely by this analogy, and it does not overcome actual SQLite writer or synchronous CPU contention.

**Next normal-agent decision:** preserve explicit `(verifiedPrincipal,storageBucket)` identities and preinitialized WAL-file topology as independent axes. If real expensive asynchronous session checks must be performed before a shared writer, keep the checks side-effect-free and revalidate **all** mutable security/state conditions within the transaction. Demand equal-trust comparison and data from true multi-account saturation, hostile network and process CPU before claiming availability/security guarantees. Maintain the release-blocked result.
