# Proposed whole-process CPU audit for resident SCO original HMAC service

**Agent 7, 18 November 2026 UTC. Status:** unmeasured decision contract. The project limits **compute overhead to 2.5×**. Prior successful one-A private-worker trial measured actual independent B HTTP latency; many-principal saturation demonstrated a real latency boundary but neither measured total process CPU overhead.

**Primary comparison:** 7 repetitions on each Node 22 Ubuntu/Windows runner, alternating synchronous generated SCO private HMAC HTTP and prestarted per-principal-worker SCO HTTP. For each repetition both arms share a freshly random 256-bit private root, verified A/B tokens and exactly one 64-event A batch plus one 16-event B batch of the **identical original 8 MiB/event HMAC private ratchet**. Create all sources, machines, session grants and (worker arm) server-resident worker threads **before timed CPU**. Measure direct original in-process 80-event HMAC sum with `process.cpuUsage()` and protected JSON HTTP request+dispatch+private HMAC+serialization through `process.cpuUsage()` difference (user+system microseconds, process aggregate includes worker threads). Both original and protected outputs and 200 statuses must be byte-for-byte equal; no artificial RTT. Include actual client HTTP CPU in the protected same-process measurement. State explicitly that this does **not** execute the published client ESM, browser or TLS.

**Quantitative decision:** list every native/protected CPU ratio and count any strict >2.5×. A successful population on two runner OSes is a scoped CPU-feasibility observation for this 80-event two-principal warmed-server workload, **never a general guarantee**. A strict breach is a veto for that sampled workload. Include raw user/system CPU, each mode's overhead distribution, checkout SHA, resolved runner Node versions, test/CI and the warning that same-process CPU accounting can include unrelated scheduling noise and GC. Interpret worker startup exemption only for trusted SCO server initialization; all request-time worker dispatch and client fetch CPU count.

**Limits:** This is a budget-oriented, original-workload control, separate from the independent cross-process B latency and conditional multi-A saturation experiments. No adversarial reconstruction, online-relay, COO/SNO runtime, real browser, varying call counts or cold client ESM is tested.
