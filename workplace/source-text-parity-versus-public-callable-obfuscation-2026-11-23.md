# Source-text parity imposes a confidentiality ceiling on published JavaScript functions

**Agent 38, 23 November 2026. Conditional specification argument with empirical support.** This is a research-direction note, not a claim of a cryptographic lower bound or proof against all obfuscation architectures.

## Normative premise

ECMAScript 2026, [§20.2.3.5 Function.prototype.toString](https://tc39.es/ecma262/2026/multipage/fundamental-objects.html#sec-function.prototype.tostring), returns the `[[SourceText]]` of an ECMAScript function when that internal slot contains Unicode source code and `HostHasSourceTextAvailable(func)` returns true. [§20.2.5](https://tc39.es/ecma262/2026/multipage/fundamental-objects.html#sec-hosthassourcetextavailable) allows hosts to suppress source exposure but specifies the **default is true**, deterministic for a given function. Node 22 and headless Chromium in this repository have empirically exhibited source-text visibility.

## Conditional necessity argument

Let an original callable `f` be made reachable by an unknown external consumer and let `S = Function.prototype.toString.call(f)` under a host that exposes `[[SourceText]]`. Suppose a local build tool changes identifiers or any characters within the exposed function's source to `S'`, yielding a callable `f'` with **different exposed source**. An external consumer, whose code is not part of the compiler input graph, can evaluate `Function.prototype.toString.call(f')` and distinguish the two. Therefore, **contextual 1:1 equivalence against every such consumer requires exposed source parity `S'=S`**, regardless of whether arithmetic return values match. User-level overrides of `f'.toString` cannot change a direct call to the intrinsic.

This necessary condition says nothing about unexposed helpers, server-retained secrets or hosts that refuse native source text. It explains why a fully self-hosted optimizer cannot both change the native source text of *an externally exposed function* and preserve every possible external observation of that very function. A source-exact public facade delegating to an encoded helper can satisfy this specific observation constraint, but it exposes the facade and still requires separate analysis of helper secrecy, dynamic extraction, performance and side effects.

## Concrete finite reproductions in this repository

- External CJS consumer: 13 of 14 published callable source shapes (39 mode/identifier-on cases) change `Function#toString` while preserving numeric results; ESM unknown-importer and real Chrome reproduce the same default-identifier issue. Source-pinned details in [CJS observer intermediate report](../im-results/commonjs-public-callable-identifier-observer-2026-11-23.md).
- A source-exact public CJS/ESM facade around a transformed private Wasm helper passes 2,060 primitive-number inputs per module/mode and real Chrome native source observation. However the published Wasm bytes permit a **zero-oracle source-only native reconstruction** of the helper, and the test's object-coercion probes demonstrate 18 semantic mismatches outside the primitive Number grammar. See [private Wasm report](../im-results/wasm-i32-private-public-source-facade-2026-11-23.md).
- Importantly, **syntactic non-escape is insufficient to classify a private function as source-invisible**. A sloppy external host callback invoked inside a direct-call-only private helper can use `arguments.callee.caller.toString()` to recover that function's source. This alters the callback's observed trace under current default identifier mangling and a proposed local-source-span guard. Both Ubuntu and Windows reproduce the red behavior in COO, SNO and SCO. See [local callable proof counterexample](../im-results/local-source-callable-identifier-refusal-2026-11-23.md). An alternative V8 `Error.prepareStackTrace` CallSite observer recovers the function through thrown host errors.

## Consequence for research contracts

Before claiming contextually exact transformations, define the permitted observer set. If it includes unknown external `Function.prototype.toString`, sloppy `Function.caller`, `Error.prepareStackTrace`, native errors and debugger-linked callbacks, then local non-escape proofs must consider ambient host behavior even when the source AST contains no observation syntax. A proof-based transform may conservatively refuse unknown escapes, or a product may expose a narrower documented observational contract (e.g. typed Number-only pure kernels, no caller introspection) and test against that declared contract. Each choice trades transformation yield against exactness.

The target's combination of **maximal source concealment** with **unrestricted native source parity for any externally reachable function** contains an intrinsic tension under the stated ECMAScript host condition. No number of ordinary AST renaming passes can eliminate it. SCO retains an architecture-level escape: store genuinely secret algorithms or values only in a controlled server, leaving a public compatible interface, while independently checking the stated unlimited-query attacker model. COO and SNO still require honest source-exposure, runtime capture and authorization limitations.

**Engineering disposition:** this is an explicit blocker for broad default identifier mangling under unrestricted unknown consumers, and a reason to demand typed/effect/source observer contracts and source-pinned adversarial falsifiers before a release claim. It is not a proof that all forms of JavaScript software protection are useless.
