# Predeclared equal-trust worker saturation challenge (18 November 2026)

**Question:** Under the previously measured 1/4/8 independently authorized attacker-principal CPU saturation, do the same B loaded-service-latency failures appear in a *conventional* authenticated Node HTTP worker service holding exactly the same secret, original HMAC and per-principal worker threads? The existing generated SCO multi-A simulation reported strict >2.5× B/direct-native breaches for eight attacker principals. A matching ordinary worker arm can separate generic CPU contention from any incremental generated-SCO property.

**Frozen design:** Extend the source-pinned \`sims/sco-ratchet-worker-multi-principal.js\` sample to permit selecting the validated \`makeWorkerServer(root,()=>active,true)\` ordinary HTTP handler and passing an explicit same-pair private root, without changing its existing generated-only \`experiment()\` baseline. In a separate manual-only script, sample **1, 4, 8 legal A principals**, **four paired trials per count**, alternating generated/ordinary arm order, with identical 32-byte root per pair. Each arm must use prestarted per-principal workers, same FIFO and cookie-based principal lookup, original 8 MiB/event HMAC, 64 events per legal A principal, independent 16-event B client, 16-event B quiet control, and exact native original outputs. The independent B child submits during actual A0 private-worker execution, confirmed by monotonic timestamps; require every response HTTP 200. Preserving 1:1 successful authorized behavior is mandatory. Exact events per arm: \`32 + 64*A\`.

**Decisions declared ahead of measurement:** A B/direct-native **HTTP service-latency** ratio over **2.5× is a strict latency-workload veto** for the corresponding arm, even when median or quiet controls pass. Queuing and CPU contention contribute to this wall-latency measurement; it does **not**, by itself, demonstrate a violation of the prompt's actual *compute-time* ceiling. The primary comparison is paired \`generated B loaded ms / ordinary B loaded ms\` at each A count. Values near 1 support *generic worker-capacity* explanation. An apparent generated advantage must be corroborated by root-matched repeat and adjusted for OS noise; no obfuscation protection claim follows from latency. If either arm misses A0 overlap, output parity, authorization or actual event count, reject the pair. Report counts and raw tail ratios, rather than aggregate-only claims.

**Scope exclusions:** Obtaining 4 or 8 valid A credentials is an *additional* capability beyond the base prompt's single-account unlimited legitimate calls. Worker startup is excluded under allowed server initialization. This tests loaded B HTTP latency under CPU contention, not parent+worker+independent-client summed CPU, browser/WAN, memory exhaustion, source reconstruction, anti-relay protection or general runtime compliance.
