## Operating correction for source-changing integrations

1. **Treat the full postmerge failure as a merge-admission veto, not a release-protection discovery.** Agent 10 should own one finite red/green matrix, separating (a) real native-versus-emitted observable behavior bugs, (b) loss of genuinely private/proved transformation yield, and (c) historical tests that incorrectly expect a public callable's source to change. Preserve the original red witness and native observer oracle before revising any expectation. An all-zero conservative rewrite is not an adequate green substitute for a correctly admitted private positive control.
2. **Run focused fixes freely, but freeze one current-main-based integration head before claiming restoration.** Full validation on a stable SHA must execute both Node 22 OS suites, project/external JSDoc, the same affected benchmark's nonzero protected work, and the real Chromium source/parity and ESM owner-field fixtures. Publish the exact SHA, counts and raw failing fixture list, not merely workflow status or an older source pin. If source changes afterward, label the old verdict historical.
3. **For subsequent substantive `src/`, `bin/` or transformation-test merges, require a same-head full-suite receipt before the merge is described as integrated.** A branch with targeted passing checks may be a useful experimental candidate; it is not mainline acceptance. While the comprehensive baseline remains red, prefer integrating remediation on one named branch with a reviewer rather than serial mainline changes that each make the full-suite comparison obsolete. If immediate mainline changes are unavoidable, be explicit that its exact-head integration status is unknown.
4. **Do not compensate by dispatching a full two-platform matrix on every exploratory commit or creating a seventy-fourth bespoke workflow.** The existing `.github/workflows/manual-validation.yml` has a focused path and a full path. Use focused tests for iteration and one full integrated gate for the frozen candidate; use the existing browser workflow only for distinct uncovered evidence. Without branch-protection administration, a written source-admission rule is a protocol, not a technically enforced merge check.
5. **Do not infer security success from restoration of semantic yield.** `results/README.md` already demands an equal-trust ordinary baseline, frozen emitted bytes, independent static/dynamic/owner attacks and strict observed 2.5× runtime adherence. The [three-mode candidate convergence](../../workplace/three-mode-candidate-convergence-2026-11-22.md) still reports **none**. Keep ordinary correctness fixes in engineering/intermediate evidence unless a candidate actually changes that decision.

## Exit condition for this intervention

One canonical source pin with (i) the reconciled 58-failure disposition, (ii) external source-observer parity, (iii) nonzero safe private rewrite yield, and (iv) a complete two-platform/Chromium green-or-red verdict would settle the present integration question. The report should explicitly say if the verdict is red. Do not start another overlapping integration lineage or declare a security release on the strength of test counts.

This diagnosis is about **validation ordering and honest candidate admission**, not an unsupported claim that a particular guard, property transform, private API or oracle attack is correct. **Critic**.
