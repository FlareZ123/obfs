# Agent 41: SCO storage-state synthesis and finite-account quota correctness gate

**18 November 2026 UTC.** Several independent source-pinned Linux/Windows experiments are now consolidated in [the SCO state topology decision](../../workplace/sco-ratchet-state-topology-decision-2026-11-18.md). Scope is server-side availability, replay, CPU and account authorization. **No new security/anti-relay release claim.**

The most actionable correction is a subtle queue identity mistake: mapping verified accounts into eight root-HMAC SQLite WAL buckets and using the **bucket ID** as `createScoKeyedIsolation`'s `maxPendingPerPrincipal=16` key let sixteen authenticated A pending calls force independently authenticated B to **HTTP429** whenever they share a bucket. [Two-platform original versus nested quota witness 44279941027](https://github.com/FlareZ123/obfs/actions/runs/44279941027): original B429, nested real-principal-quota + separate bucket writer queue B200, A17 always429, protected HMAC parity and state exact. Merely layering the queues did not prevent a B **~1220ms** wait behind A's artificial state-independent async preparation while A held its bucket writer.

A [preregistered three-arm Linux/Windows extension 44283716665](https://github.com/FlareZ123/obfs/actions/runs/44283716665) moved **only that trusted state-independent preparation** after A's per-principal quota reservation and before acquisition of the writer queue. B remained HTTP200 and completed in **15.048ms Ubuntu / 30.760ms Windows** instead of ~1220ms. Actual authorization/replay/state checks and private HMAC remained inside the SQL transaction. This does **not** authorize moving arbitrary state-dependent checks out of the lock.

A separate [real OS SIGKILL cross-bucket WAL test 44282872001](https://github.com/FlareZ123/obfs/actions/runs/44282872001) preserved B data while rolling back a killed uncommitted A writer, and recovered a separately committed A cached result after a second kill. The tested server topology remains subject to bucket collisions, cold new-principal cost, same-process synchronous CPU starvation, many-account resource saturation, authorized A online relay, and the unresolved universal 2.5× rule. The [strict local nested queue CPU profile 44281149397](https://github.com/FlareZ123/obfs/actions/runs/44281149397) has insufficient Windows one-event CPU resolution to certify thin requests.

**Direction:** If building any resource-bounded authenticated SCO backend, preserve **two distinct trust-derived identities**: a verified *account* for quota and a WAL *bucket* for serial writer use. Keep mutable state security checks transactional. Reevaluate actual multi-account workloads and compare with a conventional equal-trust HTTP service before promoting. Please leave `results/README.md` release-blocked.
