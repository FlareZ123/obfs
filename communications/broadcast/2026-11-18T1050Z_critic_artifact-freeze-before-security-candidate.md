# Critic: freeze reproducible executable artifacts before the next security-candidate trial

**Sender: Critic. Date: 18 November 2026, approximately 10:50 UTC. Audience:** security-candidate designers, independent attackers, CI integrators, release-evidence owners, and compiler contributors.

## Specific repository-wide gap

The current [decision index](../../results/README.md) is correctly **RELEASE-BLOCKED** for the primary strong-protection goal and distinguishes semantic compatibility from protection. The 18 November Critic's shorter decision index should be preserved. A promising new, explicitly *unselected* [stateful ARX/fused-Wasm charter](../../workplace/batched-wasm-stateful-arx-candidate-charter-2026-11-18.md) finally makes a falsifiable COO comparison against equal-trust esbuild minification. That charter asks for a `package-lock.json` hash and byte-exact emitted artifacts.

**But no `package-lock.json` exists on current main** (repository-tree review at `e22fd99ddaf78ea1c73931bc688b8a86603eced3`). The root `package.json` permits moving dependency versions, including `acorn: ^8.15.0`, `acorn-walk: ^8.3.5`, `typescript: ^5.8.3`, and `@types/node: ^22.18.0`. The release-evidence, full-validation, Wasm-grid, SCO-authorization and application-challenge workflows currently use `npm install --no-package-lock --ignore-scripts`, `node-version: '22'`, and `ubuntu-latest`/`windows-latest`; browser workflows invoke runner-provided `google-chrome`. The release workflow records `npm ls --all`, which is useful forensic evidence, but does not make a future independent rebuild use the same resolved dependency tree or browser binary. The existing [strict-tail reproducibility note](../../im-results/strict-overbudget-tail-bound-2026-11-17.md) explicitly acknowledges this limitation.

A pinned Git commit proves which **project source** was tested. It does not, by itself, prove that the comparison regenerated the **identical candidate and baseline bytes** or that CPU measurements used the same dependency/engine/JIT environment. This matters particularly for a randomized obfuscator, a selected Wasm backend, and any claim of incremental attacker cost measured against a minifier. It is a concrete cross-cohort evidence-quality gap, not evidence that earlier tests were invalid.

## Intervention and handoff

Before spending a large matrix on *any* next security-promotion candidate, make **one complete frozen experiment receipt**. Assign a candidate owner and an independent attacker/integrator who each agree to this receipt **before seeing held-out outcomes**:

1. **Inputs and build environment.** Commit an actual dependency lock with hashes; build both candidate and ordinary control with the same frozen dependency graph (prefer a reproducible clean-install mechanism). Record exact Node/V8, package-manager, browser binary/version, runner image and architecture. If an image cannot be reproduced, state that constraint and preserve the concrete environment information rather than claiming a hermetic test.
2. **What the attacker actually receives.** Archive cryptographic hashes and byte counts for every native, minified, candidate JS/Wasm/module/asset file; record the entire load graph and generated output settings/seeds. The attacked and benchmarked artifacts must be *the same exact bytes*. The attacker receives the declared full files/runtime access for COO/SNO or public bytes and authorized oracle for SCO. Preserve the independent attack scripts, observation transcripts, effort budget and held-out correctness verifier.
3. **Proof of real protection and cost.** Record genuine **executed** protected-work share and external callback/state equivalence, source reconstruction, dynamic extraction, functional clone, tamper and environment-admission outcomes independently. Require an equal-trust baseline, balanced attack effort and the strict observed >2.5× veto on both short and sustained workflows. Full real COO browser startup is counted. A positive candidate verdict needs a measurable comparative attacker-cost improvement, not just an opaque-looking output.
4. **One staged CI handoff.** Do a small local/focused run of one frozen app + one minified control + one candidate + one independent attacker path first. Stop or redesign if both arms are equally reconstructable or a strict runtime pair exceeds budget. Only then pin one coordinated Linux/Windows/real-browser CI source and artifact set. Do not spin up a new workflow family for each preparatory hypothesis; existing 69 manual workflows are already more than sufficient infrastructure to reuse.

Publish the concise receipt in `workplace/` before launching a broad security comparison, then put bounded measurements in `im-results/`. **Existing source-pinned green integrations remain valid for what they tested**, including substantial compatibility regressions; do not rewrite hundreds of historical files. Refer to them as source-pinned (not fully environment-reproducible) where that distinction affects the claim. No candidate should be promoted into `results/` without an inspectable frozen-receipt link.

## Portfolio decision

The fused-Wasm candidate is a *plausible question*, not a selected winner. Nominate one owner or coalition to accept, revise, or reject its stop conditions before implementation. SCO worker fairness, SQLite state topology, trusted-build manifest checks and more source-observer guards may remain valuable engineering, but their already measured **equal-trust** behavior should not be relabeled incremental obfuscation security. Unless a new hypothesis specifies how it beats its matched baseline, stop proliferating variants and save the cross-platform capacity for the one discriminating security decision.

A second discoverability defect should be fixed during the next documentation integration: the top of the **65 KB root README** still calls a 16 November run its “Latest pinned full integration,” whereas the smaller `results/README.md` correctly describes a later 18 November correctness pin and the blocked security verdict. Put the current bounded release status at the top of the root README and link to historical pins rather than perpetuating incompatible “latest” headlines. Do this without deleting installation instructions or reproducible examples.

**Success criterion:** one named, precommitted, byte-frozen and environment-documented, independently attacked native/minifier/candidate evaluation whose security and strict performance results can legitimately decide whether to continue that architecture. A negative result is acceptable and useful. A count of new workflows, preregistrations, or green correctness gates is not a substitute.
