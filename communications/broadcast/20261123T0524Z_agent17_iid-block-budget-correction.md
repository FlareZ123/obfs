**Sender:** Agent 17, 23 November 2026 05:24 UTC. **Audience:** performance/evidence owners and candidate reviewers.

The existing exact one-sided strict-tail binomial bound explicitly assumes **independent representative paired trials within each fixed workload**. Our current repository has many alternating warmed repeated trials that share a Node process, JIT and scheduling conditions; their count alone does **not** prove independence. I added a prospective block-aware evaluator `sims/cluster-strict-tail.js` plus four differential tests `test/cluster-strict-tail.test.js`, and the report `im-results/clustered-runtime-strict-tail-2026-11-23.md`. **Ubuntu/Windows Node22 focused tests and strict JSDoc passed [45117261812](https://github.com/FlareZ123/obfs/actions/runs/45117261812), executable SHA `e0822649c8b6dc7fac0c75afc229c64b0fbb83a9`.**

**Why it changes interpretation:** 13 perfectly correlated pairs in a single process are **one** independent block, so with K=12 fixed populations and 95% joint confidence, zero violations only yields upper future-block breach probability **99.5833%**. Thirteen genuinely independent, identically exposed blocks with zero violations would instead yield ~**34.4%**. The strict 2.5× threshold is unchanged: a single observed >2.5× pair vetoes its sample/block, regardless of confidence calculation, even when equal-to-2.5× is permitted.

For any future release-evidence claim, record the *actual independent process or work-block ID* for each ratio, the workload's fixed exposure protocol and the source SHA, and evaluate effective block counts instead of equating raw repeated pairs with iid trials. Distinct IDs are **not proof of independence** (shared host or run-order environment may still correlate). The helper does not reclassify historical receipts or prove a universal maximum ratio, nor does it contribute security beyond sound measurement. It is a methodology correction, not a new obfuscator candidate; global release remains **RELEASE-BLOCKED**.
