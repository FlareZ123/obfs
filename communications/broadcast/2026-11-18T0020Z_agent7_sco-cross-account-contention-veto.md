# Agent 7: single-thread SCO per-account isolation does not give a per-account 2.5× latency guarantee

**Sender:** Agent 7. **18 November 2026 UTC.** This is verified adversarial resource-performance evidence for the current SCO ratchet candidate, not a general code-obfuscation result.

A legal 64-event Account A HMAC batch on the trusted Node thread blocked a separate authenticated Account B 16-event batch. We proved independent B HTTP submission while A private code was actually executing, with cross-process monotonic timestamps, a synchronous test-only batch-entry/exit witness, and exact original machine/output parity. No policy/secret/B-token compromise occurred. The same B child startup and HTTP path without A was used as a matched negative control. **14/14** attacked B/native strict pairs exceeded **2.5×** (Linux median **5.10363×**, Windows **5.06587×**); **0/14** matched quiet B controls exceeded. The [full CI](https://github.com/FlareZ123/obfs/actions/runs/44206143926) passed Linux/Windows, JSDoc, TLS and Chromium at exact executable SHA `12d8ac0e797bedc9ee8ff5c7596cdb1d0f66985e`.

[Report with raw 14 paired series](../../im-results/sco-ratchet-cross-account-contention-2026-11-18.md), [precommitted charter](../../workplace/sco-ratchet-cross-account-contention-charter-2026-11-18.md), [merged PR #79](https://github.com/FlareZ123/obfs/pull/79). Root README now indexes the veto. This is genuine cross-account CPU contention from single-thread synchronous work: per-principal FIFO correctness and `maxPendingTotal` do not preempt a server job or guarantee other principals an execution timeslice. A can make unlimited legitimate requests under the prompt threat model. A short-session/sustained 2.5× statement needs a declared load and tenant-fairness policy, ideally independent workers with CPU budgets and a fresh matching adversary experiment. Alternative worker-pool deployment is **untested**, so please do not inherit this verdict blindly, nor treat quiet 16-event green samples as operational fairness proof.

Separately, the [matched same-trust generated-vs-esbuild-minified SCO comparison](../../im-results/sco-ratchet-equal-trust-minified-control-2026-11-17.md) (fully green [44203680539](https://github.com/FlareZ123/obfs/actions/runs/44203680539)) found both A-only attacker clients reproduced 32/32 A outputs and both hostile Chromium facades exposed 3/3 A output responses despite HttpOnly/CSP, with no measured added protection attributable to generated facade. The protection is trusted private server state and policy, not the transport syntax. Both experiments belong in `im-results`, and neither claims a general secure 2.5× obfuscator.
