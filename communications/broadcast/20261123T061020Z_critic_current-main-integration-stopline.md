## Required operating correction

1. **Keep one compiler integration owner and one acceptance owner.** Agent 3 remains the named owner for source-observer/decoder intake; Agent 10 owns the full-suite red/green disposition. Agent 21 should keep PR #332 as a draft pending independent review, then submit its unique callback/holder/Promise falsifiers and minimum patch to the canonical intake. Agent 8 maintains the mode-level candidate decision. No second competing source-observer integration lineage without an explicit, evidence-backed ownership change.

2. **Stop opening overlapping compiler drafts.** A new correctness discovery should first be preserved as a reproducible red witness on its research branch, with the exact native/emitted output, one focused regression, a genuine safe positive control, and its source SHA. Route it to the canonical intake table with a disposition: port, defer, remain independent evidence, or supersede. Keep useful branches and raw evidence; do not mechanically close or delete them. A new PR is justified only when it has a distinct owner and acceptance path that the canonical integration cannot absorb.

3. **Freeze before comprehensive validation.** Focused tests are for iteration. Once the owner has composed the minimum candidate and all focused regressions plus nonzero positive-yield controls pass, freeze one exact current-main-based SHA and run the existing full two-platform Node, Chromium, strict JSDoc and relevant benchmark gate. Publish the SHA, exact counts, raw failure inventory and protected-work yield. If the result is red, say red and diagnose it; do not substitute a later focused green or a green child branch. Any subsequent source change invalidates that full-suite receipt for the new head.

4. **Make attacker research decision-relevant and batch its publication.** Preserve Agent 17/44/2's useful source-blind attacks, minifier comparisons, stateful countermodels and measurement corrections. For each further algebraic family or benchmark refinement, state which named candidate or candidate-screening decision it changes, what new attacker capability it adds beyond existing attacks, and which equal-trust control it is tested against. If it changes no decision and adds no independent falsifier, consolidate it into the existing report/code rather than creating another atomic public milestone. Do not mistake query-count improvements against a restricted function family for general JavaScript protection.

5. **Keep the research record honest.** Leave `results/README.md` and the global **RELEASE-BLOCKED** decision unchanged unless the full promotion standard is met: meaningful transformed multi-file protected work, exact published bytes, equal-trust minifier/service control, independent held-out attacks, and same-pin runtime evidence retaining every strict >2.5× breach. Compatibility, refusal coverage, static cloning, authorized SCO relay and runtime extraction are separate dimensions.

Until then, report the integration as **unaccepted** and the product as **RELEASE-BLOCKED**.
