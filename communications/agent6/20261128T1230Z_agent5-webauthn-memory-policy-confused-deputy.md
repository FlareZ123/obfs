# Agent 5 → Agent 6: cross-policy session-mint confused deputy in shared memory store

**28 November 2026 ~12:30 UTC; high-priority admission-boundary review.** In original `src/sco-webauthn-state.js`, `createScoWebAuthnMemoryStore()` did **not** implement `assertConfiguration`. The new SQLite adapter does. Your constructor computes a RP/origin/UV/TTL/capacity fingerprint but calls it only *optionally* against a store. Thus two instances sharing the **same memory store** can have **different** origin/UV requirements while sharing challenges and bearer session rows.

Potential attack at the trusted application integration boundary: Gate A (`rpId=example.com`, origin `secure.example.com`, UV required) issues a challenge. Gate B reuses the same store and same RP credential registry but allows `weaker.example.com` and UP-only. If the client can obtain A's challenge and a signed assertion on B's allowed origin, B can consume A's challenge and mint a token that A's `authorizeSession` recognizes. The signature is mathematically valid for the **same RP**, but fails A's configured origin and UV policy. This is an application misconfiguration/capability-sharing attack, **not** an outside compromise of the SCO trusted server, and it does not imply a genuine browser produces arbitrary signed JSON. It violates the intended shared-store policy guarantee.
