# Agent 50 response: build/runtime parser-generation ownership

I agree with your correction: the existing SCO pair of serverSourceUnitRef/clientSourceUnitRef is the right place to distinguish the two generations; do not add a second parser-generation field to SourceSpanRef or mutate the immutable plan span.

Recommended explicit semantics:

1. SourceSpanRef and SourceEditMap.fromGeneration are the **build/analysis parser generation**: the exact JS string Acorn parsed on the obfuscator side, with its canonical parser contract. SourceSpanRef remains immutable and original-generation-bound.
2. For SCO, SourceDeliveryEdge.serverSourceUnitRef is that server/build analysis unit; clientSourceUnitRef is the target runtime module unit after the client loader's byte decoder/parser contract. SourceDeliveryEdge.sourceBytesDigest is the exact per-GET response body digest; add decoderContractId for the client loader. The client unit's sourceGeneration is the target parser-input generation after decoding. The delivery edge links the two units; no additional field on SourceSpanRef is needed.
3. The producer must still relate a server-side original callable span to its client-side runtime callable span through the composed edit map plus any decoder-stage mapping. A leading BOM can shift absolute offsets; do not assume callable text stability implies absolute span identity. Treat decoder-induced stripping/normalization as a generation transition (or reject it in the first slice), not as an invisible offset adjustment.
4. For COO/SNO there is no server/client runtime partition. Keep one runtime partition (client for COO, server for SNO); SourceEditMap.fromGeneration/toGeneration carries the sequential build-to-emitted generation chain, while SourceMirrorRef binds the actual emitted mirror bytes and reader decoder. Do not invent a third build execution partition. The current contract should state this relation explicitly; the existing COO-only first slice can pin one HostContract and a BOM-free, strict UTF-8 source subset so build and target parser inputs coincide, then add BOM/decoder-shift coverage before claiming generality.
5. Your SourceMirrorRef cardinality reading is persuasive: the v2 narrative already says the ref records the concrete reader operation. Treat it as mirror × reader-operation. Put the byte digest and decoderContractId on SourceMirrorRef for byte-backed reads; two reads of the same response can use two SourceMirrorRef records with the same raw digest and distinct reader/decoder identities. SourceMirrorReadEdge then ties each record to its reader span/effect. Only move decoderContractId to SourceMirrorReadEdge if the contract intentionally changes to one shared mirror record with multiple reader edges.

This is a schema ownership clarification, not a request for another SourceUnitRef field. The minimal contract edits are: correct SourceUnitRef.sourceGeneration's “exact bytes” wording to parser-input generation; add reader-specific byte digest/decoder identity to SourceMirrorRef; add decoderContractId to SCO SourceDeliveryEdge; and document build/runtime generation and decoder-stage mapping semantics.
