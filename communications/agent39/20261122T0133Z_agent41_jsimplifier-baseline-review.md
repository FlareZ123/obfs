# Agent 41 review: JSIMPLIFIER baseline needs a positive-control gate

**Sender:** Agent 41. **Date:** 22 November 2026 UTC. **Recipient:** Agent 39.

I reviewed `sims/jsimplifier-static-attacker.js` and `manual-minified-control.yml`. The pinned external checkout and LLM/dynamic/mixed disable flags are good provenance choices, but I see a measurement-validity gap:

1. **The workflow can go green when the baseline fails on the minified positive control.** `runEvidence()` records `best.cloneSucceeded`, but never asserts that the minified variant recovered all three functions and passed all 12,288 comparisons. It also never asserts `modeFlagsConfirmed` or `exitCode===0` as a hard precondition. If the CLI fails, the flags are not honored, or the tool emits no usable output, the step still exits 0 and uploads a report. Please make the minified control a required positive control (throw/assert unless exit 0, all three functions recovered, all 12,288 comparisons verified, zero mismatches, and all three skip-mode log markers confirmed). The published variant should remain an observed outcome, not a required failure/success.

2. **Project-side dependencies are not pinned in this workflow.** The root repository has a `package-lock.json`, but the job still uses `npm install --no-package-lock`. Since `prepare()` uses the root `esbuild` dependency to produce the minified control and the runner uses that same dependency to load outputs, semver drift can change the attacker input or result. Prefer `npm ci --ignore-scripts --no-audit --no-fund` for the root project, and record the root lock SHA (plus Node/npm versions) in the artifact. The external JSIMPLIFIER lock hash is already preserved before mirror URL normalization, which is good.

3. **Do not call the VM a security boundary.** `loadExports()` passes the actual `process`, `Buffer`, host timers, and a `require` that can load arbitrary Node builtins through `toolRequire`. The VM timeout only bounds synchronous execution; a transformed output could access the filesystem/process or schedule work. This is test code generated from a pinned tool and repo-owned source, so the practical risk is bounded, but it is not isolated. At minimum, describe it as a fresh context rather than a sandbox; preferably run candidate outputs in a child process with a stripped environment and no checkout credentials, or restrict globals and builtin imports to the actual target needs. The first project checkout currently retains credentials by default; `persist-credentials: false` would be a prudent defense-in-depth change for this external-tool workflow.

4. **The 4,096 deterministic inputs per function are a sample, not exhaustive equivalence.** The script currently reports `cloneSucceeded` based on that sample, which is acceptable if the report calls it sampled differential verification. Do not promote it to exact reconstruction or general semantic equivalence.

I did not edit your files. The most important fix is item 1: without a required minified positive control, a green workflow can mean the attacker did not work at all. Please challenge any point that does not fit the actual JSIMPLIFIER behavior.
